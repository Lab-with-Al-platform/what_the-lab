## 2. ALB 권장에 대한 우리 검토

강사님 말씀(#4)처럼 ALB는 "트래픽이 늘 때" 의미가 커요. 우리 구조에서 정리하면 이래요.

| ALB가 해 주는 것 | 우리 구조에서의 의미 |
|---|---|
| 서버 여러 대에 요청 나누기 + Auto Scaling | **바로는 못 씀**: backend 안에서 예약 작업(만료·아침 브리핑·알림)이 돌고, 디스코드 봇도 1개여야 해요. 서버를 2대로 늘리려면 먼저 **API 서버와 작업·봇 서버를 나눠야** 해요 |
| 헬스체크로 고장 난 서버 빼기 | 서버가 1대면 뺄 곳이 없어요. 고장 난 서버 교체는 ALB 없이 Auto Scaling(최소 1대)만으로도 가능해요 `[UNVERIFIED: 구성 시험 필요]` |
| ACM 무료 인증서로 HTTPS | 오리진 Let's Encrypt 설정이 필요 없어져요 (운영이 조금 쉬워짐) |
| 비용 | ALB 시간 요금 $16.43 + LCU 약 $1~3 + ALB 공인 IPv4 약 $7.30 → **월 약 $25** |

**판단 (팀 결정 필요)**:
- 지금 사용자 규모에서는 ALB 비용($25)이 EC2(micro $7.59, small $15.18)보다 커요.
- 그래서 **첫 배포는 ALB 없이** 시작하고, 아래 신호가 오면 "API/작업 서버 분리 + ALB + Auto Scaling"으로 넘어가는 것을 제안해요.
  - micro·small 부하 테스트에서 동시 접속 목표를 못 버틸 때
  - 실제 사용자가 늘어 CPU 크레딧이 자주 바닥날 때
- 강사님께 다시 확인할 점: "ALB + micro"가 **지금 바로** 필요하다는 뜻인지, **사용자가 늘 때의 확장 방향**이라는 뜻인지.

## 2-2. 팀 결정 (2026-11-10)

- **ALB는 나중으로 미뤄요** `[DECIDED]`. 당분간은 팀 자체 테스트와 일부 사용자를 모집한 **베타 운영 기간**이라 사용자 수가 적고, 월 약 $25.2를 쓸 단계가 아니에요.
- **베타 운영 기간의 기본 구성**: S3 프론트 + EC2 1대(**micro로 시작**, 부족하면 small) + 비공개 RDS, ALB 없음 → AWS 월 $36.31 (small이면 $43.90).
- **팀 결정 (2026-11-13)**: 첫 배포는 **`t4g.micro`로 시작**해요. 배포 후 **2주는 테스트 기간**이고, 회원을 모집해도 **50명 내외**로 예상해요. ALB는 **이용자 수 추이를 보고 정하는 향후 계획**이에요.
- **ALB를 다시 검토할 신호**:
  1. 베타가 끝나고 정식 공개 일정이 잡힐 때
  2. 부하 테스트나 실제 사용에서 EC2 1대가 목표 동시 접속을 못 버틸 때 (CPU 크레딧이 자주 바닥나는 경우 포함)
  3. 배포 중 잠깐 끊기는 것도 허용되지 않게 될 때
- **ALB는 이용자 수 추이에 따른 향후 계획이에요 (2026-11-13 팀 결정)**. 다시 검토할 때 볼 숫자 `[PROPOSED: 기준값은 베타 기록을 보고 조정]`:
  - 회원 수가 예상(50명 내외)보다 크게 늘어 **200명**을 넘을 때
  - 몰리는 시간대 동시 접속이 **small 1대로도** 응답이 느려지는 수준일 때
  - 정식 공개 일정이 잡혀 배포 중 잠깐 끊기는 것도 피해야 할 때
- ALB 비용 조건(시간 요금 $16.43, 공인 IPv4 $7.30, LCU 계산법, NAT를 피하는 방법)은 [08](08-cost-estimate.md) 2.2절에 있어요.
- 다시 검토할 때는 **API 서버와 예약 작업·봇 서버 분리**를 먼저 하고 ALB + 서버 2대를 함께 계획해요. 분리 계획은 [16](16-api-worker-split.md)에 있어요.

## 3. 이번 피드백으로 바뀐 것 요약

1. 비용표를 **EC2 / DB / 네트워크 / 저장소 / 기타**로 나눠서 보여 줘요 ([08](08-cost-estimate.md) 0절).
2. 비교안에 **ALB 포함안**과 **RDS 없는 안**을 숫자로 추가했어요 ([08](08-cost-estimate.md) 2.1절).
3. "로컬 테스트" 범위는 **공용 Supabase 개발 DB 하나를 모두가 같이 쓰고, 데이터를 최신으로 맞춘다**로 정리했어요. v4에서 제안했던 RDS 안의 별도 테스트 DB(`labbridge_test`)는 보류해요 ([04](04-database-storage.md) 6절).
4. t4g.micro 부하 테스트를 배포 전 확인 항목으로 올렸어요 ([09](09-deployment-roadmap.md) B8).
5. CI/CD는 **강의자료 예제를 기준**으로 만들고, "테스트가 모두 통과해야 배포" 조건을 지켜요 ([14](14-ci-cd-pipeline.md)).
