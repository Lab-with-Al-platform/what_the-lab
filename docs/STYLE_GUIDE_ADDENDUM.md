# LabBridge — UI/UX 스타일 가이드 보강안

> 버전: 0.1 (기존 `docs/STYLE_GUIDE.md`에 병합할 제안 문서)  
> 목적: 확정 디자인과 작업 중인 시안을 구분하고, 3명이 일관된 UI를 구현하도록 돕는다.  
> **주의:** 이 파일은 기존 스타일 가이드를 직접 수정한 결과가 아니다. 기존 문서와 대조해 중복·충돌을 확인한 뒤 병합한다.

## 1. 디자인 확정 상태를 먼저 관리한다

| 화면 | 현재 상태 | 개발 적용 기준 |
|---|---|---|
| 메인페이지 | 디자인 방향·주요 레이아웃 합의 | 최신 승인 시안을 기준으로 구현. 로고/서비스명 표기는 별도 확정 필요 |
| AI 연구 협업 사례 상세 | 공통 인사이트 상세 레이아웃 합의 | 본문 중심, 왼쪽 목차, 출처/관련 기술/전문가 연결 구조 |
| AI 트렌드 상세 | 사례 상세와 **공통 템플릿 사용** 방향 합의 | 콘텐츠 섹션 구성만 유형에 맞게 변경 |
| AI 연구 협업 사례 목록 | 시안 정리 중 | 기존 시안의 정보 구조를 참고하되 디테일 임의 확정 금지 |
| AI 트렌드 목록 | 시안 정리 중 | 사례 목록과 공통 UI 재사용, 구분 색상은 최종 승인 후 확정 |
| AI 전문가 목록 | 시안 정리 중 | 전문가 정보·필터·연결 방식은 승인 후 확정 |
| AI 전문가 상세 | 시안 정리 중 | 프로필·역량·연구 적합성 중심, 협업/연락 동작은 승인 후 확정 |
| 로그인·회원가입 | 별도 확정 상태 확인 필요 | 요구사항과 최신 Figma 확인 후 구현 |

**상태 표기:** `확정(Approved)` / `검토 중(Review)` / `제안(Proposed)` / `보류(Deferred)`를 각 화면·컴포넌트별로 기록한다. 정적인 이미지 시안은 실제 동작 구현의 증거가 아니다.

## 2. 브랜드와 디자인 톤

- 브랜드: **LabBridge(랩브릿지)**. 기존 시안에 `WHAT THE LAB` 표기가 남아 있을 수 있으므로 교체 시점과 로고를 별도로 승인한다.
- 인상: **연구자에게 신뢰를 주는 정돈된 에디토리얼 UI**. 기술적이지만 과도하게 미래지향적이거나 장식적인 느낌은 피한다.
- 정보 전달 우선: 본문 가독성, 충분한 여백, 명확한 제목 계층, 일관된 카드 스타일.
- 메인과 상세를 구분: 메인은 서비스 탐색과 콘텐츠 발견, 상세는 **긴 글을 읽는 데 최적화**한다.
- 과한 그림 느낌의 카드, 의미 없는 3D 아이콘, 불필요한 그라데이션·발광·애니메이션은 지양한다.
- 연구 이미지와 도표는 실제 콘텐츠 설명에 도움이 될 때 사용한다. 생성 이미지로 연구 결과처럼 오해하게 하지 않는다.

## 3. 디자인 토큰은 단일 출처에서 관리

Figma에서 **승인된 값만** 디자인 토큰으로 등록한다. 아래는 이름의 예시이며, HEX·px 값은 아직 이 문서에서 확정하지 않는다.

```text
color.brand.primary
color.text.primary / secondary / muted
color.surface.page / card / subtle
color.border.default
color.semantic.success / warning / error
font.family.body / display
font.size.body / title / caption
space.*
radius.card / button / input
shadow.card
layout.contentMaxWidth / articleMaxWidth
breakpoint.mobile / tablet / desktop
```

- `frontend`의 CSS 변수/Tailwind 테마를 실제 값의 **단일 출처**로 삼는다.
- 페이지별 임의 HEX, margin, radius 하드코딩을 피한다.
- 사례와 트렌드의 구분 색은 **보조 의미**로만 사용하고, 텍스트 라벨을 함께 제공한다.
- Figma와 코드 토큰이 달라지면 PR에서 변경 사유와 영향 화면을 설명한다.

## 4. 공통 컴포넌트 목록 및 책임

| 범주 | 권장 컴포넌트 | 원칙 |
|---|---|---|
| 공통 구조 | `SiteHeader`, `SiteFooter`, `PageContainer` | 모든 화면의 기준 정렬과 폭 통일 |
| 탐색 | `NavLink`, `Breadcrumb`, `Pagination` | 현재 위치와 다음 행동을 명확히 |
| 콘텐츠 | `ArticleCard`, `ArticleMeta`, `KeywordTag` | 사례/트렌드 간 구조 재사용 |
| 전문가 | `ExpertCard`, `SkillTag`, `ProfileSection` | 연구자에게 필요한 역량 정보를 우선 |
| 입력 | `Button`, `TextField`, `FilterChip` | 크기·상태·접근성 일관화 |
| 상태 | `LoadingState`, `EmptyState`, `ErrorState` | 모든 목록·API 화면에서 대응 |
| 긴 글 | `ArticleLayout`, `TableOfContents`, `SourceList`, `ExpertCTA` | 인사이트 상세에서 재사용 |

이름은 예시다. 기존 코드의 명명과 중복 여부를 확인한 뒤 채택한다. **공통화는 시각·행동이 실제로 같을 때** 적용하고, 차이가 큰 컴포넌트를 억지로 하나로 합치지 않는다.

## 5. 인사이트 상세페이지 규칙 (사례·트렌드 공통)

### 공통 정보 구조

1. 카테고리, 제목, 한 줄 설명, 날짜, 출처/저자, 읽는 시간(계산 가능한 경우)
2. **30초 핵심 요약**: 문제/기술의 의미/검증된 결과 또는 활용 가능성
3. 본문: 문제/배경 → AI 역할/기술 변화 → 결과·한계 → 연구 적용 가능성
4. 관련 AI 기술 키워드: 쉬운 설명과 근거
5. 원문·논문·공식 자료 출처
6. 관련 인사이트 및 해당 기술을 가진 개발자 탐색 진입점

### 유형별 본문 소제목

- **연구 협업 사례:** 연구 배경 → 기존 어려움 → AI 적용 방법 → 검증 결과 → 한계·적용 조건 → 관련 기술
- **AI 트렌드:** 기술 소개 → 기존과의 차이 → 쉬운 작동 개념 → 연구 활용 분야 → 한계·주의점 → 관련 기술

### 콘텐츠 신뢰성

- 원문 종류(논문/기술 블로그/분석글), 제목, 저자, 발행일, URL/DOI(있는 경우)를 표시한다.
- 원문에 명시된 **검증 결과**와 LabBridge 작성자의 **해석·제안**을 구분한다.
- 실험 수치·성과를 임의로 만들거나 다른 연구 조건에 일반화하지 않는다.
- 원본 이미지·도표의 라이선스와 출처를 확인하고 캡션을 표시한다.

## 6. 목차와 반응형 동작

### PC

- 목차는 **본문 왼쪽**에 배치한다.
- 읽는 동안 목차가 사용 가능하도록 sticky 동작을 검토하되, 고정 헤더와 겹치지 않도록 한다.
- 본문은 적절한 읽기 폭을 유지하고, 좌측 목차가 본문을 지나치게 좁히지 않도록 한다.
- 현재 읽는 섹션을 시각적으로 표시한다.

### 모바일

- 본문은 한 열로 구성한다.
- 초기 목차는 일반 문서 흐름에 배치하고, 스크롤로 상단에 도달하면 **한 줄짜리 접이식 sticky 목차**로 표시한다.
- 고정 헤더가 있으면 그 **아래에** 배치한다.
- 접힌 상태에서는 현재 섹션명을 표시하고, 펼치면 전체 섹션으로 이동할 수 있다.
- 목차 선택 시 제목이 헤더 뒤에 가려지지 않도록 `scroll-margin-top` 등을 적용한다.
- 본문 마지막에서 목차가 불필요하게 계속 남지 않도록 sticky 범위를 검토한다.
- 스크롤 감지 방식(예: IntersectionObserver)은 구현 선택 사항이며 성능과 접근성을 확인한다.

> **상태:** 위 동작은 정적 이미지 시안의 실제 구현이 아니라 팀이 합의한 **인터랙션 요구사항**이다. 구현 후 모바일 실기기/브라우저 테스트가 필요하다.

## 7. 목록과 전문가 화면의 미확정 항목

다음은 **개발 전에 확정하거나 Mock으로 명시할 항목**이다.

| 화면 | 결정 필요 사항 |
|---|---|
| 사례/트렌드 목록 | 대표 글 위치, 카테고리 필터 종류, 카드/행 형태, 정렬, 페이지네이션, 모바일 노출 정보 |
| 전문가 목록 | 키워드 탐색/필터 방식, 카드 필수 정보, 경력·연구 분야 표시, 정렬 기준, 빈 결과 상태 |
| 전문가 상세 | 연구자에게 중요한 역량·프로젝트 경험의 표시 순서, 협업 가능 상태, 연락/연결 CTA의 실제 동작 |
| 로그인/회원가입 | 연구자/개발자 구분 방식, 필수 입력 항목, 인증 실패·탈퇴·개인정보 동의 흐름 |

**주의:** 메인페이지에서 제거한 검색 입력을 임의로 복원하지 않는다. 전문가 목록 내부의 검색·필터는 해당 화면의 요구사항으로 별도 확정한다.

## 8. 접근성 및 UI 상태

- 모든 버튼·링크는 목적을 분명히 표시한다.
- 키보드 포커스가 보이고, 클릭/터치 영역이 충분해야 한다.
- 색상만으로 상태나 콘텐츠 유형을 구분하지 않는다.
- 이미지에는 대체 텍스트를 제공하고, 장식 이미지는 적절히 숨긴다.
- 입력 오류 메시지는 해당 필드와 연결하고, 오류 해결 방법을 설명한다.
- 목록·상세·로그인 화면에서 **로딩/오류/빈 상태**를 정의한다.
- 모바일에서 가로 스크롤, 헤더·목차 겹침, 글자 잘림이 없는지 확인한다.
- 동작이 필요한 UI는 hover만으로 제공하지 않는다.

## 9. 시안 승인과 변경 관리

1. 담당자가 PC·모바일 시안을 준비한다.
2. 기존 메인·상세의 토큰·타이포그래피·컴포넌트와 비교한다.
3. 팀에서 승인 여부를 기록한다 (`Approved/Review/Proposed/Deferred`).
4. 승인된 변경만 Figma와 `STYLE_GUIDE.md`에 반영한다.
5. 구현 PR에 디자인 출처(Figma 프레임/링크), 화면 캡처, 변경 사항을 적는다.
6. 공통 UI 변경은 다른 화면 영향도와 함께 검토한다.

### 디자인 결정 기록 예시

```md
| 날짜 | 화면 | 결정 | 상태 | 근거/시안 | 담당 |
|---|---|---|---|---|---|
| YYYY-MM-DD | 인사이트 상세 | PC 왼쪽 목차 / 모바일 접이식 sticky 목차 | Approved | Figma 링크 | 담당자 |
```

## 10. 화면 PR 검수 체크리스트

- [ ] 최신 승인 Figma 시안을 기준으로 구현했다.
- [ ] PC·모바일 화면을 모두 확인했다.
- [ ] 공통 토큰·컴포넌트를 사용했다.
- [ ] 사례와 트렌드 상세가 공통 템플릿을 재사용한다.
- [ ] 목록/상세의 로딩·빈 상태·오류를 처리했다.
- [ ] 키보드 포커스·대체 텍스트·대비를 확인했다.
- [ ] 출처·날짜·키워드 표시가 콘텐츠 사실과 일치한다.
- [ ] 모바일 sticky 목차의 헤더 겹침·이동 위치를 확인했다(상세 화면).
- [ ] 승인되지 않은 기능이나 스타일을 임의로 추가하지 않았다.
- [ ] 변경 화면 캡처와 검증 결과를 PR에 첨부했다.
