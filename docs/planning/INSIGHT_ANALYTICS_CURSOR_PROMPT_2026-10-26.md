## 1. 현재 상황과 작업 원칙

- 기존 운영 요약·회원 관리·연구 등록·인사이트 관리가 하나의 관리자 좌측 사이드바에 통합되어 있습니다.

## 3. 구현 범위와 진입점

### A. 게시글 탭: 글별 조회수

- 기존 게시글 목록과 편집 동작을 유지합니다.
- `기간 조회수` / `측정 이후 누적 조회수` 열과 `통계 보기` 진입점을 추가합니다.
- 기본은 최신 게시순을 유지하고, 선택 기간 조회수순·누적 조회수순 정렬을 제공합니다.
- 조회수 열의 기준 기간을 목록 위에 표시합니다. 기간 선택은 오늘 / 최근 7일 / 최근 30일 / 이번 달, 기본 최근 30일입니다.
- 기간 변경·검색·필터 변경 시 첫 페이지로 이동하고, 기간 조회수 정렬은 새 기간으로 재계산합니다.
- 기존 6건 페이지 표시와 페이지 번호 정책은 보존합니다. 제목·분야·키워드를 숨겨 조회수만 남기지 마세요.
- 통계는 행마다 개별 요청하는 N+1 방식 대신 목록 응답 또는 한 번의 일괄 요청으로 붙입니다.
- 미수집·미연결은 `—`와 설명으로 표시합니다. 실제 수집된 0회와 구분합니다.
- 전체 목록·수집후보에 공개 글의 조회수가 필요하면 연결된 공개 원고 기준으로만 표시합니다. 미게시 후보에 가상 조회수 0회를 부여하지 마세요.

### B. 인사이트 관리: 통계 탭

탭 순서는 **전체 목록 / 수집후보 / 게시글 / 통계 / 자동수집 설정**입니다.
통계·설정 탭에는 글 개수 배지를 붙이지 않습니다. 기존 3개 목록 탭의 개수 의미는 유지합니다.

위에서 아래로 배치하세요.

1. 공통 탭 아래 기간 선택·사례/트렌드 필터·새로고침·데이터 모드.
2. 측정 시작일, 집계 기준 시각, Asia/Seoul, 수집 상태 안내.
3. 요약 카드 4개:
   - 현재 공개 게시글 수: 현재 상태 값임을 표시. 선택 유형을 반영하되 기간 중 게시 수와 혼동하지 않음.
   - 선택 기간 조회수(PV).
   - 측정 이후 누적 조회수(PV).
   - 선택 기간 조회가 발생한 글 수: 콘텐츠 고유 수이며 방문자 수가 아님.
4. 조회 추이 그래프와 사례/트렌드 조회 비중 그래프.
5. 같은 필터 기준 인기 글 상위 5개: 제목·유형·기간 조회수·전체 조회 중 비중·통계 보기.
6. 글별 성과 목록: 글 제목·유형·공개일·기간 조회수·측정 이후 누적 조회수·통계 보기.

기간·유형 조건은 카드·그래프·상위 목록·성과 목록에 일관되게 적용합니다.
누적 지표는 기간과 독립적인 측정 이후 값임을 명시하세요. 현재 게시글 수는 ‘현재’, 누적 조회수는 ‘측정 이후’로 구분합니다.
글 검색은 성과 목록에만 적용할 경우 검색 영역에 이를 명시하고 전체 카드 수치가 검색 결과의 합인 것처럼 보이지 않게 하세요.

- 조회 추이는 일/주/월 집계 단위를 제공합니다. 날짜 선택과 집계 단위는 별개입니다.
- 주는 한국 시간 월요일 시작, 월은 달력 월 기준이며 범위 양끝의 부분 주/월을 표시합니다.
- 좁은 화면에서도 축·날짜·툴팁을 읽을 수 있게 하고, 정확한 수치를 표로도 확인할 수 있게 합니다.
- 큰 숫자는 카드에서 한국식 천 단위 구분을 사용합니다. 비교 그래프를 위해 0을 숨기거나 축을 임의 절단하지 마세요.

진입 주소는 `/admin/insights?tab=stats`처럼 새로고침·뒤로가기가 가능한 형태를 권장합니다.
현재 탭은 로컬 state이므로 URL 동기화를 추가할 때 자동수집 설정의 미저장 이동 경고를 우회하지 마세요.
통계 탭을 기존 workspace API의 `scope=stats`로 보내지 말고 기존 허용 범위와 통계 API를 구분하세요.

### C. 글별 통계 상세

- 권장 경로: `/admin/insights/statistics/[contentId]`. 기존 관리자 공통 프레임과 인사이트 권한을 유지합니다.
- 제목·유형·실제 공개일·현재 공개 상태·측정 시작일을 표시합니다.
- 기간 조회수·측정 이후 누적 조회수와 날짜별 추이를 보여 줍니다.
- 원고 편집 화면과 실제 공개 글로 이동할 수 있게 합니다. 편집 중이면 기존 미저장 보호를 지킵니다.
- 돌아가기 시 이전 기간·유형·정렬·페이지 조건을 복원합니다.
- 게시글 목록과 편집 상세의 ‘통계 보기’는 동일한 콘텐츠 통계로 연결합니다.
- 기존 편집·승인·게시·수정 판본·본문 미리보기 모달을 통계 UI로 교체하지 마세요.
- 통계 화면 자체를 공개 글 조회로 집계하지 않습니다.

### 4.2 레이아웃

- 공통 SiteHeader·PageContainer·AdminShell을 유지합니다. 중복 헤더·중복 사이드바·중첩 PageContainer를 만들지 않습니다.
- 좌측 최상위 메뉴는 그대로 4개입니다. ‘인사이트 통계’를 별도 최상위 메뉴로 중복 추가하지 않습니다.
- PC 공통 프레임의 현재 기준은 사이드바 210px, 본문 minmax(0,1fr), 간격 28px입니다. 실제 공통 CSS를 우선하고 통계 화면에서 따로 재정의하지 않습니다.
- 기존 인사이트 탭은 본문 패널 상단의 얇은 하단 강조선 형식을 유지합니다. 새 통계 탭만 큰 카드/알약 모양으로 만들지 않습니다.
- 카드 → 그래프 → 인기 글/성과 목록 순서로 정보 위계를 만듭니다. 제목 옆에 작은 아이콘을 둘 수 있으나 장식 일러스트·배경 이미지는 넣지 않습니다.
- 필터와 버튼은 한 도구 영역에 정렬합니다. 후보 가져오기·등록 버튼을 다시 제목 우측 상단으로 빼지 않습니다. 통계 화면에는 관련 없는 후보 버튼을 반복하지 않습니다.

## 6. 수집·저장·조회 구조

### 콘텐츠 식별

- 변경되지 않는 콘텐츠 ID를 사용합니다. 제목·slug·판본 변경 때 조회수가 초기화되지 않아야 합니다.
- Publication UUID를 정적 글이 갖고 있다고 가정하지 말고, 필요한 최소 콘텐츠 매핑/등록부를 설계합니다.
- 실제 공개되는 정적 글과 DB 게시본이 같은 콘텐츠일 때만 연결합니다. 대응이 없으면 ‘연결 확인 필요’로 표시하고 임의 제목 매칭을 하지 않습니다.
- 후보·Publication·정정 판본을 각각 다른 공개 글로 중복 집계하지 않습니다.
- 본 작업을 이유로 공개 사이트 전체를 DB 원고로 전환하거나 정적 원고를 덮어쓰지 마세요.

### 수집 API

- 작은 프론트 수집 함수와 FastAPI 수집 엔드포인트를 사용합니다. 브라우저가 분석 테이블에 직접 쓰지 않습니다.
- 한 방문에 하나의 event ID를 생성하고 재시도는 같은 ID를 사용합니다. 서버/DB의 고유 제약으로 동시 재전송까지 중복을 막습니다.
- 최소 필드는 event ID, 검증된 콘텐츠 ID, 서버 수신 시각입니다. 클라이언트 시각이 필요하면 목적·허용 범위·지연 전송 처리와 집계 기준을 문서화하고 서버에서 검증합니다.
- 이벤트 종류·콘텐츠 ID·크기·허용 Origin·요청 빈도를 검증합니다. 집계 숫자를 클라이언트가 직접 지정하도록 하지 않습니다.
- 로그인한 관리자의 제외 여부는 서버의 기존 권한으로 확인합니다. 클라이언트의 `is_admin` 값을 신뢰하지 않습니다.
- 개발 환경·미리보기·자동화 검증의 이벤트를 실사용 지표에 섞지 않습니다. 테스트에서만 수집을 켤 수 있는 별도 설정을 둡니다.
- 공개 수집 엔드포인트는 통계 조회 권한을 제공하지 않습니다. 수집의 위조·봇을 완벽히 판별할 수 있다고 주장하지 말고 최소 차단과 한계를 기록합니다.
- 비동기 수집 실패가 기사 표시·탐색을 막으면 안 됩니다. 무한 재시도·무한 대기열을 만들지 않습니다.

### 집계·권한·운영 상태

- 기존 PostgreSQL/Supabase·FastAPI 구조와 마이그레이션 관례를 따릅니다. 운영 SQL을 대신 실행하지 마세요.
- 필요한 최소 이벤트 중복 방지와 콘텐츠별 날짜 집계를 설계하고, 원본 수락·집계 갱신이 어긋나지 않게 합니다.
- 일별 PV의 합으로 주/월 PV를 만들 수 있습니다. 향후 고유 방문자 수를 같은 방식으로 더할 수 있다고 일반화하지 마세요.
- 통계 API에는 기존 인사이트 관리자 권한 검사를 적용하고 비로그인 401·일반 회원 403을 서버에서 검사합니다.
- 운영 전용 권한만 있는 계정에 인사이트 통계가 자동 공개되지 않게 합니다. 새 공개 통계 API를 만들지 않습니다.
- 원고 목록·전체 통계·글별 상세는 같은 집계 소스를 사용합니다. 원고 수는 별도 콘텐츠 카탈로그 원천을 명시합니다.
- 미수집·오류·집계 지연·부분 수집·실제 0을 응답 계약으로 구분하고, 프론트가 모두 0으로 바꾸지 않게 합니다.
- 보관·삭제·수집 거부 정책의 기존 합의를 확인합니다. 없으면 최소 정책안을 문서화하고 실제 수집은 비활성 기본값으로 유지하되 코드·테스트·데모는 끝까지 완성하세요.
- 이번 PV 범위에는 새 방문자 식별 쿠키·브라우저 지문이 필요하지 않습니다. 수집 거부 상태는 전송 전에 반영하고 사용자 식별로 확장하지 않습니다.
- 원본 정리 후 누적값과 기간 조회를 어떻게 보존하는지 정의합니다. 삭제된 원본으로 과거 값을 복원할 수 있다고 가정하지 않습니다.
- Discord ID·이메일·연락처·JWT·쿠키 값·IP의 영구 저장·본문·검색어·URL query·입력값을 분석 자료에 넣지 않습니다.
- 기본 수집 상태와 실제 측정 시작일은 코드 배포일·첫 조회 발생일과 구분합니다. 수집 중단·재개 구간도 품질 정보로 남깁니다.
