## 1. 사용자 결정 기록 — 답변 반영

아래 결정된 범위는 다시 미답변으로 돌리지 않는다. 남은 선택을 개발자가 임의로 확정하지 않는다.

| 항목 | 값 |
|---|---|
| 대상 데이터 | 연구 등록과 협업 프로젝트를 구분 관리. 미완료 등록의 중단 원인 파악 포함 |
| 허용할 관리자 조치 | 회원 정지·해제, 실제 공개 대상 숨김·복구. 강제 삭제·강제 완료 제외 |
| 운영 역할 | 2명. 인사이트는 당분간 사용자 본인만 관리. 다른 운영자에게 콘텐츠 변경 권한 제외, 실제 계정 지정은 별도 |
| 이번 결과물 | 실제 운영 가능한 수준. 가상 DB 검증과 실제 연결·배포 경계는 유지 |
| 방문 분석 | 필요한 방문·인사이트·등록 과정 분석을 자체 개발하기로 확정. 외부 분석 SDK·API 도입 안 함 |
| 분석 제외 | 녹화·히트맵·개인별 전체 이동 이력·실시간 접속 지도·범용 분석기는 현재·후속 로드맵에서 제외 |
| 방문 식별·보관·거부 정책 | 미확정: 분석 수집 활성화 전에 확정 |
| 이번에 승인한 단계 | 미확정 |

## 3. 승인 후 공통 구현 지침

아래 문장은 각 구현 단계의 프롬프트 앞에 함께 전달한다.

```text
이번에 사용자가 명시적으로 승인한 단계와 기능만 구현하세요.
최신 AGENTS.md·제품 범위·의사결정 로그·디자인·코딩 규칙 및 관리자 기획을 다시 확인하세요.

기존 변경은 사용자·팀의 작업입니다. reset/stash/일괄 덮어쓰기/자동 정리를 하지 마세요.
구현 전 브랜치와 변경 상태를 보고하고, 팀 규칙의 최신 develop 기반 feature 브랜치를 사용하세요.
현재 변경을 안전하게 분리할 수 없다면 그 충돌만 설명하고 확인을 받으세요.
요청 없는 커밋·push·PR 생성·병합·원격 DB 변경·배포는 하지 마세요.

공통 컴포넌트·토큰·쿠키 인증·기존 인사이트 권한을 재사용하세요.
인사이트 전용 허용 목록을 전체 관리자 권한으로 확대하지 마세요.
운영자 2명의 권한은 추가 명세의 고정 묶음으로 설계하되, 실제 계정 배정은 사용자 선택 전 바꾸지 마세요.
인사이트 작성·수정·검토·승인·게시·수집 설정 변경은 당분간 사용자 본인 전담입니다.
다른 운영자를 is_admin=true로 지정해 콘텐츠 권한까지 열지 마세요.
기존 로그인·Origin 보호·판본 기능은 보존하되, 기존 허용 목록/관리자 필드가 본인 전담 정책을 우회하지 않도록 기능별 권한을 분리하세요.
클라이언트 메뉴와 별개로 서버의 모든 관리자 API에서 권한을 검사하세요.
단순한 함수·타입과 짧은 학습용 주석으로 작성하고 변경 이유를 한국어로 설명하세요.
아직 승인되지 않은 추적·원격 전송·가입/협업 상태 변경은 추가하지 마세요.
분석은 자체 API·저장·집계로 구현합니다. 외부 분석 SDK·서비스 계정·조회 API를 추가하지 마세요.
화면 녹화·히트맵·개인별 전체 이동 이력·실시간 지도·범용 분석기는 미래 대비 코드도 만들지 마세요.

임의의 통계 숫자·가짜 성공률·가짜 운영 로그를 실제 데이터처럼 표시하지 마세요.
미수집/0건/지연/오류를 구분하고 단위·기간·측정 시작일을 표시하세요.
테스트에는 가상 데이터와 격리된 로컬 DB를 사용하세요.
이미 적용된 초기 SQL을 덮어쓰지 말고 필요하면 기존 migration 흐름에 맞는 변경안을 만드세요.
실제 DB 적용은 별도 승인입니다.

완료 보고:
무엇을 해결했는지 → 핵심 동작 → 선택 이유 → 실행한 검증·미검증 → 학습 힌트.
```

## 4. 1단계 — 공통 관리자와 읽기 전용 운영 현황

사용 조건: D1·D4의 제품 방향은 확정됨. D3 개인별 역할·조회 권한 범위를 정하고 이 단계 구현을 승인했을 때.

```text
승인된 범위에서 공통 관리자 틀과 회원·등록 연구의 읽기 전용 조회를 구현하세요.
이번에는 상태 변경·권한 변경·방문 추적을 구현하지 마세요.

목표:
- 운영 요약, 회원 현황/목록/상세, 연구 등록 현황/목록/허용된 상세.
- 기존 /admin/insights 주소와 기능을 보존하는 공통 진입 메뉴.
```

## 5. 2단계 — 승인된 계정 조치와 운영 이력

사용 조건: 회원 정지·해제의 기본 범위는 사용자 확인을 받음. 실제 역할 배정·조치 절차를 정하고 이 단계 구현을 요청했을 때.

```text
승인된 회원 정지·해제와 운영 이력만 구현하세요. 실제 회원에게 실행하지 마세요.

요구사항:
- 정상→정지, 정지→정상만 허용. 탈퇴 복구·영구 삭제·관리자 부여·강제 협업 완료는 제외.
- 사유 필수, 대상·변경 상태·영향을 표시하는 확인창, 내부 메모와 사용자 안내 분리.
- 관리자 계정 조치·본인 정지·마지막 전체 관리자 상실은 첫 단계에서 차단.
- 서버 권한/입력/현재 상태 검사, 동시 변경 충돌 보호.
- 상태 변경과 성공한 조치 이력은 같은 트랜잭션에서 함께 성공하거나 함께 실패.
- 중복 요청과 응답 유실에 대한 처리 계약을 정하고 결과 재조회 우선.
- 회원 정지가 프로젝트 취소·멤버 삭제로 번지지 않게 할 것.
- 운영 담당자는 계정·공개 대상 조치, 콘텐츠 담당자는 원고 운영만 가능하도록 분리.
- 운영 이력은 일반 UI에서 수정·삭제할 수 없고 민감정보·원문·키를 기록하지 않을 것.
- 기존 인사이트 review_events는 보존하고 중복 기록하지 않을 것.

가상 DB에서 권한 우회, 상태 충돌, 중복, 응답 유실, 이력 저장 실패 롤백,
정지 후 기존 쿠키 접근 차단, 정상 해제를 검증하세요.
원격 migration 적용과 실제 계정 조치는 따로 요청하지 않는 한 실행하지 마세요.
```

공개 대상 숨김·복구는 대상 모듈·노출 경로와 권한 정책을 확정한 별도 프롬프트로 분리한다.
이 문구만으로 연구 등록의 상태 필드를 숨김 용도로 바꾸면 안 된다.

## 6. 3단계 — 방문·인사이트 조회 측정

사용 조건: 자체 방식은 확정. 세션·비회원 식별·보관·거부 정책과 이 단계의 실행 계약을 확인했을 때.

## 8. 협업 프로젝트와 후속 관리

팀의 요청·신청·확정·마일스톤·완료 모듈을 실제로 확인하고
그 계약에 맞춘 별도 프롬프트를 만든다. 현재 연구 등록 관리자에 가짜 상태를 추가하지 않는다.
신고·문의·평가·분류·관리자 역할 편집·내보내기·일괄 처리는 각 목적과 승인을 따로 다룬다.

## 9. 문서의 검증 경계

기획과 로컬 파일의 정합성 검토용이다. 위 구현 프롬프트를 실제 실행하거나,
관리자 코드·DB·회원·권한·추적 설정·배포를 변경하지 않았다.
관리 범위·인사이트 본인 전담·자체 분석·장기 제외 사항은 사용자 답변을 반영했다.
실제 계정 식별과 수집 정책 등 기술 계약을 확인하고, 실행 요청을 받은 단계만 진행한다.
