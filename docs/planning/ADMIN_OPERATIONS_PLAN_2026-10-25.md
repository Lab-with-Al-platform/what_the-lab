- 작성일: 2026-10-25
- 상태: **v1.0 — 제품 범위·자체 분석 개발 확정, Cursor 인계용**
- 목적: 기존 인사이트 관리자를 보존하면서 회원·연구/프로젝트 운영과 이용 통계를 확장한다.
- 이번 작업: 로컬 소스 확인과 기획 문서 작성만 수행했다. 서비스 코드·DB·계정 권한·배포는 변경하지 않았다.
- 구현 인계: [Cursor 전달용 단계별 프롬프트](ADMIN_OPERATIONS_CURSOR_PROMPTS_2026-10-25.md)
- 후속 결정·상세 설계: [작성 중단 분석·운영 권한·무료 분석 도구 비교](ADMIN_OPERATIONS_DECISIONS_AND_ANALYTICS_2026-10-25.md)

## 1. 이 문서를 읽는 기준

사용자는 연구 등록과 협업 프로젝트를 구분한 관리, 제안한 운영 조치 범위, 운영자 2명의 권한 구분, 실제 운영 가능한 수준의 목표를 확인했다.
후속 답변으로 방문·콘텐츠·등록 과정의 제한된 분석을 자체 개발하기로 확정했다. 화면 녹화·히트맵·개인별 전체 이동 이력·실시간 접속 지도·범용 분석기는 현재와 후속 로드맵에서 제외한다.
이에 따라 해당 제품 방향은 확정하고, 세부 화면·API·데이터 구조와 아직 선택하지 않은 정책은 **구현 전 검토안**으로 구분한다.
사용자가 관리자 기획을 요청한 것을 실제 회원 정지, 원격 DB 변경, 운영 추적 도구 설치의 승인으로 해석하지 않는다.
최종 구현 범위는 `docs/product/MVP_SCOPE.md`와 최신 `docs/product/03_DECISION_LOG.md`에 따른다.

사용자가 말한 회원·프로젝트 대시보드는 일반 회원의 마이페이지가 아니라 **운영자가 보는 전체 현황**으로 해석했다.
역할별 개인 대시보드 개편은 이번 기획에 포함하지 않는다.

### 1.1 확인된 현재 상태

아래는 2026-10-25 로컬 파일을 읽어 확인한 사실이다. 실제 서버·DB를 조회하거나 동작시킨 결과는 아니다.

| 확인 사실 | 로컬 근거 | 기획에 미치는 영향 |
|---|---|---|
| 기존 관리자에 전체 목록·수집후보·게시글·자동수집 설정이 있다 | `frontend/src/components/admin/insight-workspace.tsx` | 기존 기능을 새 관리자 메뉴 안에서 보존한다 |
| 인사이트 권한은 `users.is_admin` 또는 인사이트 전용 허용 목록으로 검사한다 | `backend/app/insights/auth.py` | 인사이트 전용 담당자를 전체 관리자로 승격하지 않는다 |
| 회원에 `user_role`, `signup_step`, `status`, `is_admin`, 생성·수정 시각이 있다 | `database/init/001_create_tables.sql` | 현재 상태의 회원 집계와 계정 생성 추이는 설계 가능하다 |
| 정지·탈퇴 계정은 공통 인증 검사에서 차단한다 | `backend/app/security.py` | 정지 기능을 추가할 때 기존 쿠키가 남은 경우도 회귀 검사한다 |
| 연구 등록의 상태는 `draft`와 `registered`다 | `database/init/006_create_research_tables.sql` | 등록 연구를 모집·진행·완료 프로젝트로 바꿔 집계하지 않는다 |
| 연구자와 전문가 가입 완료 경로가 각각 존재한다 | `backend/app/routers/researcher.py`, `expert.py` | 완료 이벤트를 추가하면 두 경로 모두 다뤄야 한다 |
| 가입 완료 시각, 연구 최초 등록 시각, 방문·조회 전용 기록은 확인 범위에서 찾지 못했다 | 가입·연구 API 및 관련 스키마 검색 | 기간 내 가입 완료·등록·방문 수는 별도 기록 계약이 필요하다 |
| 현재 작업 트리에 여러 팀 작업과 미추적 파일이 있다 | `git status --short` | 기존 변경을 초기화·정리·일괄 커밋하지 않는다 |

기존 기획의 관리자 항목에는 전문가·기관·신고·평가·블랙리스트·분류 관리도 있다.
이 목록은 장기 아이디어이지 전부 이번에 구현하라는 뜻이 아니다.
특히 기관/B2B, 결제·정산, 외부 경력 인증, DM, 개인화 추천은 기존 범위 밖으로 유지한다.

### 1.2 사용자 답변 반영 및 남은 선택

| ID | 항목 | 사용자 답변·현재 결정 | 남은 선택·제한 |
|---|---|---|---|
| D1 | 연구와 프로젝트 | 구분 관리. 작성하다 만 글도 원인을 파악할 수 있게 설계 | 임시저장과 저장 전 작성 중단을 분리. 실제 협업 모듈과의 연결은 별도 확인 |
| D2 | 관리자 조치 | 이전 제안대로 회원 정지·해제, 실제 공개 대상 숨김·복구 | 강제 삭제·프로젝트 강제 완료 제외. 실제 계정 조치·DB 적용은 별도 실행 승인 |
| D3 | 운영자·역할 | 사용자 포함 2명. 인사이트는 당분간 사용자 본인만 관리. 다른 운영자는 인사이트 변경 권한 제외 | 실제 계정 식별·배정은 별도 확인. 다른 운영자에게 `is_admin=true`를 넣어 인사이트 권한까지 열지 않음 |
| D4 | 구현 목표 | 발표용 시안이 아닌 실제 운영 가능한 수준 | 가상 데이터·권한·동시성·회귀 검증 후 지정 DB 연결·배포를 확인 |
| D5 | 분석 방식 | 방문·글 조회·등록 과정 분석을 필요한 범위만 자체 개발하기로 확정 | 방문 식별·보관·거부·운영 활성화 정책은 구현 전 계약으로 확정. 실제 추적은 아직 비활성 |
| D6 | 분석 제외 범위 | 화면 녹화·히트맵·개인별 전체 이동 이력·실시간 접속 지도·범용 분석기는 장기 범위에서도 제외 | '다음 버전 예정'으로 예약하거나 숨겨진 수집기를 만들지 않음. 필요하면 새 요구로 별도 검토 |

제품 방향과 자체 개발 선택을 다시 질문하지 않는다. 개인 계정 지정과 식별·보관 등 운영 계약, 실제 DB 적용·추적 활성화·배포는 구현 단계의 확인 사항으로 구분한다.

## 2. 운영자가 답을 얻어야 하는 질문

1. 회원은 늘고 있는가? 가입 중 어느 단계에서 멈추는가?
2. 연구 등록이 실제 협업 요청·참여 신청·프로젝트 확정으로 이어지는가?
3. 누가, 어떤 페이지를 통해 방문하며 무엇을 읽는가?
4. 인사이트가 전문가 탐색과 협업의 다음 행동에 도움이 되는가?
5. 지금 처리할 일이 무엇이며, 이전에는 누가 어떻게 처리했는가?

단순 누적 방문자 수만으로 서비스 성공을 판단하지 않는다.
반대로 클릭 한 번을 협업 성사로 표시하지 않는다.

## 3. 관리자 정보 구조

| 최상위 메뉴 | 하위 화면 | 제안 경로 | 역할 |
|---|---|---|---|
| 운영 요약 | 전체 현황·처리할 일 | `/admin` | 매일 확인할 요약 |
| 회원 관리 | 현황 / 목록 / 상세 | `/admin/members`, `/admin/members/[id]` | 계정 운영 |
| 연구·프로젝트 관리 | 현황 / 연구 등록 목록 / 상세 | `/admin/projects`, `/admin/projects/researches/[id]` | 현재 연구와 향후 협업 프로젝트 구분 |
| 인사이트 관리 | 기존 전체·후보·게시글·수집 설정 | 기존 `/admin/insights` 유지 | 원고 운영 |
| 이용 통계 | 방문 통계 / 인사이트 성과 / 글별 상세 | `/admin/analytics`, `/admin/analytics/insights/[id]` | 이용 분석 |
| 운영 이력 | 필터 목록 / 기록 상세 | `/admin/audit-logs` | 책임과 원인 추적 |

새 경로는 제안이며 기존 라우트와 충돌하면 기존 관례에 맞춰 조정한다.
회원·프로젝트 대시보드를 별도 최상위 메뉴로 중복 생성하지 않고 각 관리 메뉴의 현황 탭으로 둔다.
기존 인사이트 하위 사이드바와 전체 관리자 사이드바가 동시에 두 개 생기지 않게 한다.
공통 프레임으로 옮기더라도 기존 주소·필터·편집·승인·판본·미저장 변경 보호를 보존한다.

## 4. 화면 명세

### A-01. 운영 요약

목적: 숫자를 전부 복제하는 것이 아니라 오늘 확인할 상황과 처리할 일을 보여준다.

- 상단: 페이지 제목, 기간, 시간대, 마지막 집계 시각, 새로고침.
- 핵심 카드 최대 4개: 현재 가입 완료 회원 / 기간 계정 생성 / 현재 등록 연구 / 검토 대기 원고.
- 방문 수집 시작 후 기간 방문·조회 카드로 교체할 수 있지만 미연동 숫자는 꾸며 넣지 않는다.
- 추이 최대 2개: 계정 생성 추이, 측정 가능한 연구 관련 추이. 각 차트 단위와 집계 기준을 표시한다.
- 처리할 일: 검토 대기 원고 등 실제 판정 규칙과 데이터가 있는 항목만 표시한다.
- 최근 운영 이력: 관리자 작업, 대상, 시각, 상세 링크.
- 카드·차트 클릭: 해당 기간·상태가 적용된 목록으로 이동한다.

업무상 대기와 서비스 오류를 섞지 않는다. 아직 접수 기능이 없는 신고를 임의로 대기 목록에 넣지 않는다.

### A-02. 회원 현황

- 현재 가입 완료 회원: 정상·정지 중 가입 완료 계정을 구분해 보여준다.
- 현재 정상 회원, 정지 회원, 가입 진행 중 계정 수.
- 역할 구성: 현재 저장된 연구자·AI 전문가·미선택. 한 계정을 이중 합산하지 않는다.
- 기간 계정 생성 추이: `users.created_at` 기준이며 가입 완료 추이라고 부르지 않는다.
- 가입 단계 분포: 현재 어느 단계인지의 분포다. 시간 순서의 전환율과 다르다.
- 활동 회원 수는 활동 정의·이벤트를 만든 이후에만 노출한다.

장기 미완료 계정 알림은 기준 일수와 제외 대상을 합의한 뒤 추가한다.
소속 정보를 확인하는 운영 작업과 기관·학위·전문성을 공식 인증하는 기능은 구분한다.

### A-03. 회원 목록·상세

목록:

- 검색: 내부 회원 번호·닉네임. 검색 길이 제한과 서버 페이지네이션을 적용한다.
- 필터: 역할, 상태, 가입 단계, 계정 생성일. 소속 필터는 실제 데이터 표현을 확인한 뒤 추가한다.
- 열: 회원 번호 / 닉네임 / 역할 / 소속 / 가입 단계 / 계정 상태 / 생성일 / 상세.
- 기본 정렬: 최근 계정 생성순. CSV·연락처 내보내기·일괄 정지는 첫 단계에서 제외한다.

상세:

- 요약: 내부 회원 번호, 닉네임, 계정 상태, 역할, 생성일.
- 프로필: 필요한 공개 정보와 가입 확인 메타정보만 표시한다.
- 연구·프로젝트: 접근이 허용된 요약과 관련 화면 링크. 원자료·연락처는 추가하지 않는다.
- 조치 이력: 회원을 대상으로 수행한 관리자 작업과 사유.
- 승인 후 가능한 버튼: 정상 → 정지, 정지 → 정상. 탈퇴 계정의 복구·물리 삭제는 제외한다.

정지·해제의 조건:

1. 운영자가 대상과 현재 상태를 재확인한다.
2. 사유를 입력한다. 공개될 사용자 안내 문구와 내부 메모를 구분한다.
3. 확인창에 대상·변경 상태·영향을 표시한다.
4. 서버가 권한·현재 상태를 다시 검사하고 상태와 운영 이력을 같은 트랜잭션으로 기록한다.
5. 동시 변경은 덮어쓰지 않고 충돌을 알린다. 응답 유실 시 상태부터 재조회한다.
6. 실패하면 기존 화면 상태를 유지한다. DB 작업 실패를 성공 토스트로 표시하지 않는다.

관리자 계정 자체의 정지, 본인 정지, 마지막 전체 관리자의 상실은 첫 단계에서 차단한다.
회원 정지를 프로젝트 취소·완료·멤버 삭제로 연결하지 않는다.
정지 사실의 사용자 안내·팀에 미치는 영향은 정책 확정 대상이며 대량 알림을 자동 발송하지 않는다.

### A-04. 연구·프로젝트 현황

화면 안에서 다음 두 대상을 명확히 나눈다.

| 대상 | 현재 확인한 상태 | 화면 원칙 |
|---|---|---|
| 내 연구 등록 | 임시저장 / 등록 | 현재 상태의 건수·필요한 메타정보를 집계 |
| 협업 프로젝트 | 제품 기획의 확정·진행·완료 흐름 | 실제 모듈·상태 계약을 확인한 뒤 연결 |

- 지금 가능한 카드: 현재 등록 연구 수, 전체 연구 레코드 수 등 실제 원천에 근거한 집계.
- 분야·원하는 AI 과업 분포: 여러 항목을 선택할 수 있으므로 합계가 연구 수보다 커질 수 있음을 표시한다.
- 기간 연구 생성: 임시저장도 포함될 수 있으므로 '신규 등록 연구'와 구분한다.
- 추후: 협업 요청·참여 신청·프로젝트 확정·진행·완료를 분리한 현황.
- 미구현 협업 단계는 '연동 예정'으로 표시하거나 숨긴다. 0건 또는 가짜 그래프로 표현하지 않는다.

협업 요청과 참여 신청의 전환율은 서로 다른 모수로 계산한다.
같은 기간의 요청 수와 확정 수를 단순 나눈 숫자는 이전 기간 요청의 결과를 섞을 수 있다.
요청 생성 집단을 기준으로 결과를 추적하는 방식과 관찰 기간을 합의하기 전에는 '매칭 성공률'을 표시하지 않는다.

### A-05. 연구 등록 목록·상세 / 향후 프로젝트 상세

- 목록: 연구 번호 / 제목 / 등록자 / 분야 / 작성 상태 / 생성일 / 최근 수정일 / 상세.
- 필터: 등록자, 분야, 과업, 작성 상태, 생성 기간.
- `registered`는 작성·등록 상태이지 공개 모집 중이라는 뜻이 아니다.
- `share_policy`는 데이터 공유 조건이지 연구 게시글의 공개 여부가 아니다.
- 임시저장·비공개 내용의 관리자 열람 범위를 먼저 합의한다. 초안 본문을 관리자라는 이유만으로 기본 공개하지 않는다.
- 첫 단계는 필요한 등록 메타정보 조회 중심으로 설계한다. 원자료와 연락처는 다루지 않는다.
- 현재 연구 등록 화면에는 등록한 연구를 본인만 볼 수 있다는 안내가 있다. 운영자 권한을 추가하면서 이 약속을 조용히 바꾸지 않는다.
- 작성 중단 분석 탭을 추가한다. 4단계의 도달·중단 관찰·재개·저장/검증 오류와 선택형 사유를 구분하며 입력 본문을 수집하지 않는다.
- 임시저장 글과 저장 없이 닫힌 작성 시도를 별도로 집계한다. 구체적인 사건·기준·화면은 후속 상세 문서에 따른다.

운영상 숨김을 추가하려면 공개 대상과 실제 노출 경로가 먼저 있어야 한다.
숨김 상태를 등록 상태·프로젝트 진행 상태·데이터 공유 조건 필드에 덮어쓰지 않는다.
목록만 숨기고 직접 주소·검색·API에 내용이 남는 동작도 금지한다.
공개 소비 경로가 없거나 팀의 데이터 계약이 미정이면 숨김 기능은 별도 단계로 남긴다.

실제 협업 프로젝트 상세를 연결할 때에는 공개 정보, 참여 요약, 요청·신청 이력, 마일스톤 요약, 종료 상태와 운영 이력을 구분한다.
이 관리자 개발만을 위해 요청·신청·협업 엔진을 별도로 다시 구현하지 않는다.
강제 멤버 추가, 강제 수락·확정·완료, 연구 원문 대리 수정, 자동 취소는 제외한다.

### A-06. 기존 인사이트 관리

- 현재 원고 운영 화면을 보존한다. 관리자 통합을 이유로 편집기·승인·판본 보존을 교체하지 않는다.
- 기존 주소와 미리보기의 접근 정책도 유지한다.
- 원고 목록의 '성과 보기' 링크를 이용 통계의 글별 상세로 연결하는 확장만 검토한다.
- 수집 설정 저장을 실제 자동수집·예약 실행 완료로 표현하지 않는다.
- 공개 화면의 정적 원고와 DB 원고가 다를 수 있으므로 통계 연결용 콘텐츠 식별 매핑을 먼저 확인한다.

### A-07. 방문 통계

- 기간 카드: 방문자 식별자 수 / 방문 세션 수 / 페이지 조회수.
- 추이: 일·주·월 단위 선택. 기간 선택과 차트 집계 단위는 별개다.
- 표: 방문 페이지 상위, 유입 경로, 기기 유형.
- 상세 링크: 페이지·일자별 숫자의 근거를 확인할 수 있다. 개인의 전체 이동 경로를 기본 제공하지 않는다.
- 제외: 실시간 접속 지도, 개인별 감시, 브라우저 지문, IP 기반 개인 식별.

비회원 방문자 수는 실제 사람의 정확한 수가 아니라 합의한 식별 방식에 따른 추정치다.
한 사람이 기기·브라우저를 바꾸면 분리될 수 있고 수집 거부·차단으로 누락될 수 있다.
사업 지표의 확정 건수와 분석 도구의 추정 방문 지표를 동일한 정확도로 표현하지 않는다.

### A-08. 인사이트 성과 목록·상세

- 필터: 기간, 사례/트렌드, 실제 게시 분류, 공개일 범위.
- 목록: 글 식별자 / 제목 / 유형 / 공개일 / 기간 조회수 / 측정 이후 누적 조회수 / 읽은 세션 수 / 전문가 탐색 클릭.
- 기본 정렬: 기간 조회수. 기간을 바꾸면 정렬의 기준 기간도 함께 바뀐다.
- 상세: 조회 추이, 읽은 세션 추이, 주요 유입, 기기 유형, 전문가 탐색·관련 글 이동 클릭.
- 원고 편집 화면과 통계 상세를 서로 연결한다.
- 제목 변경·주소 변경·정정 판본 게시에도 같은 콘텐츠 단위로 집계한다.
- 협업사례라는 편집 분류를 실제 플랫폼에서 성사된 프로젝트 건수에 더하지 않는다.

체류시간·완독률·회원가입 기여·프로젝트 확정 기여는 이번 범위에 넣지 않으며 자동 후속 개발 일정도 잡지 않는다. 필요하면 별도 요구로 재검토한다.
숨겨진 탭에서 열린 시간이나 스크롤 도달만으로 실제 독서·완독을 단정하지 않는다.

### A-09. 운영 이력

- 필터: 처리 기간, 관리자, 대상 종류, 작업 종류, 결과.
- 열: 시각 / 관리자 / 대상 / 작업 / 변경 전후 상태 / 사유 요약 / 상세.
- 성공한 변경 기록은 대상의 상태 변경과 함께 원자적으로 남긴다.
- 실패한 변경·권한 거절 등 보안 로그는 성공 조치 기록과 별도로 다루며 필요 이상 수집하지 않는다.
- 기존 인사이트 `review_events`는 보존한다. 같은 기록을 새 로그로 무조건 복사해 이중 집계하지 않는다.
- 이전에 로그가 없던 운영 작업을 과거까지 있었던 것처럼 만들어 넣지 않는다.
- 관리자도 이력을 일반 화면에서 수정·삭제할 수 없도록 한다.

## 5. 공통 화면·디자인 계약

- 시각 기준은 기존 P0 이미지와 현재 토큰·공통 컴포넌트다. 관리자 전용 P0 시안이 있다고 가정하지 않는다.
- 화이트·연한 쿨그레이·네이비 중심, 보라는 선택과 주요 행동에 제한한다.
- 랜딩의 장식 이미지·대형 히어로를 운영 화면에 반복하지 않는다.
- 상단: 제목·설명·현재 기간·필요한 행동. 본문: 요약 → 필터 → 결과 순서.
- PC: 공통 메뉴 + 본문. 태블릿·모바일: 현재 인사이트 관리자의 상단 메뉴 전환 관례를 우선 검토한다.
- 회원·연구·운영 이력 표의 긴 열은 표 내부 스크롤로 처리할 수 있지만 페이지 전체는 넘치지 않는다.
- 기간·검색·필터·페이지는 URL로 복원한다. 상세에서 돌아왔을 때 목록 위치와 조건을 보존한다.
- 상세는 별도 경로를 기본으로 검토한다. 단순 확인은 기존 dialog, 다단계 검토는 상세 화면을 사용한다.
- 로딩·정상·빈 결과·수집 전·집계 지연·부분 수집·권한 거절·오류를 구분한다.
- 그래프에는 단위·기준·집계 시각을 표시하고 표로도 값을 확인할 수 있게 한다.
- 키보드·확인창 포커스·Escape 취소·모바일 44px 조작 공간을 확인한다.
- 1440/768/390px 실제 캡처와 미검증 항목을 남긴다.

## 6. 지표 정의와 데이터 부족분

### 6.1 회원·연구 지표

| 지표 | 제안 정의 | 현재 데이터로 가능한가 |
|---|---|---|
| 현재 가입 완료 회원 | 현재 `signup_step=done`, `status!=deleted` 계정의 고유 회원 수. 정지 포함 여부를 문구로 명시 | 현재 상태 조회로 가능, 새 관리자 API 필요 |
| 현재 정상 가입 완료 회원 | 위 조건 중 `status=active` | 현재 상태 조회로 가능 |
| 기간 계정 생성 수 | 기간 내 `users.created_at` 계정 수. 가입 시작의 대리 지표이며 완료 수가 아님 | 생성 시각 기준 조회 가능 |
| 현재 가입 진행 중 | 탈퇴 제외, `signup_step!=done` | 현재 상태 조회로 가능 |
| 기간 가입 완료 수 | 기간에 최초로 가입을 완료한 고유 계정 수 | 최초 완료 시각 또는 상태 전이 이벤트 필요 |
| 기간 활동 회원 | 합의한 활동을 기간에 1회 이상 수행한 고유 내부 회원 수 | 활동 정의·기록 필요 |
| 현재 등록 연구 수 | 현재 `research.status=registered`인 연구 수 | 현재 상태 조회로 가능 |
| 기간 연구 생성 수 | 기간 내 생성된 연구 레코드 수. 임시저장 포함 | 생성 시각 기준 조회 가능 |
| 기간 최초 연구 등록 수 | 기간 내 처음으로 등록 상태에 도달한 연구 수 | 최초 등록 시각 또는 전이 이벤트 필요 |
| 요청·신청·프로젝트 확정·완료 | 각 도메인의 서버 확정 사실 | 실제 모듈과 이벤트 확인 후 연결 |

`updated_at`은 수정할 때마다 바뀐다. 가입 완료·연구 최초 등록·최근 접속 시각의 대용으로 쓰지 않는다.
기존 완료 회원의 정확한 완료 시각을 모르면 `unknown`으로 두고 측정 시작 이후를 구분한다.
현재 상태의 가입 단계 분포로 과거 가입 완료율이나 당시 회원 수를 역산하지 않는다.
탈퇴 발생 추이·기준일 회원 수의 역사도 해당 이벤트나 스냅샷이 있어야 한다.

### 6.2 방문·콘텐츠 지표

아래는 자체 집계 시의 제안 정의다. 외부 도구를 선택하면 실제 공급자의 정의와 차이를 문서화한다.

| 지표 | 정의·주의 |
|---|---|
| 페이지 조회수(PV) | 지원하는 페이지의 실제 표시 이벤트. 같은 이벤트 재전송은 제거하고 정상 재방문·새로고침은 포함 |
| 인사이트 조회수 | 실제 공개 글 상세가 표시된 이벤트. 카드 노출·서버 프리패치·미리보기·404·관리자 편집은 제외 |
| 읽은 세션 수 | 선택 기간에서 `(session_id, content_id)`의 고유 조합 수. 완독 인원이라는 뜻이 아님 |
| 방문 횟수 | 기간에 시작한 고유 세션 수. 자체 세션의 비활동 30분 후 새 세션을 제안하며 구현 계약에서 확정 |
| 방문자 수 | 기간 내 고유 방문 식별자 수. 사람 수가 아닌 측정 방식에 따른 추정치 |
| 전문가 탐색 클릭 | 실제 콘텐츠의 전문가 탐색 행동 이벤트 수. 클릭과 도착 완료는 구분 |
| 탐색 클릭 세션 비율 | 같은 기간·콘텐츠의 탐색 클릭 세션 / 해당 글을 조회한 세션. 분모 0이면 계산 불가 |

세션 단위 읽은 글 수, 방문자 수는 일별 값을 더해 주간·월간 고유 수로 만들면 안 된다.
기간 전체의 원본 식별 관계나 공급자의 적절한 집계를 사용한다. PV처럼 더할 수 있는 지표와 구분한다.
필요한 기간의 고유 집계가 불가능하면 제공 범위를 제한하고 정확한 수치처럼 표시하지 않는다.

### 6.3 기간·비교·상태

- 시간대: `Asia/Seoul`. 저장 시간은 기존 UTC 관례를 확인하고 화면 날짜 경계만 변환한다.
- 빠른 기간: 오늘 / 최근 7일 / 최근 30일 / 이번 달 / 직접 선택.
- 오늘은 진행 중인 날이라는 라벨을 표시한다. 최근 7·30일에 오늘을 포함할지 API 계약에서 고정한다.
- 주 집계는 월요일 시작, 월 집계는 달력 월을 권장한다. 필터 바깥 날짜를 그래프에 섞지 않는다.
- API는 시작 포함·끝 제외 범위를 사용해 자정의 이중 집계를 막는 방식을 제안한다.
- 비교는 직전 동일 길이·동일 경과 시간 범위로 맞춘다. 불완전한 이번 달을 지난달 전체와 무조건 비교하지 않는다.
- 이전 값이 0이면 증감률을 무한대나 100%로 만들지 않고 절대 증감만 보여준다.
- 측정 시작일 이전은 '미수집', 수집 후 실제 사건 없음은 `0`, 장애는 '오류', 집계 중은 '갱신 중'이다.
- 데이터가 없는 그래프 구간을 임의의 0선으로 연결하지 않는다.

## 7. 데이터·API 방향 — 구현 전 계약 검토용

### 7.1 운영 데이터

- 회원·연구·프로젝트의 사실은 기존 서비스 DB에서 읽는다.
- 최초 가입 완료·최초 연구 등록 기록을 추가한다면 실제 서버의 상태 전이와 같은 트랜잭션에서 남긴다.
- 최초 이벤트는 중복 클릭·재시도에 여러 번 기록되지 않게 한다.
- 별도 조치 로그에는 내부 관리자 ID, 대상 ID·종류, 작업, 변경 전후 상태, 사유, 시각, 요청 식별자를 둔다.
- 로그에 JWT·쿠키·API 키·연락처·연구 원문·전체 요청 본문을 저장하지 않는다.
- 이미 적용된 초기 SQL을 수정해 새 변경이 반영됐다고 착각하지 않는다. 승인된 migration 흐름을 따른다.

### 7.2 자체 분석 데이터 — 확정 방향

- 확정: 기존 FastAPI·PostgreSQL 구조를 검토해 제한된 자체 수집·중복 방지·보관·집계를 만든다.
- 관리자 통계는 자체 API에서 읽는다. PostHog·GA4·Clarity 계정 생성, SDK·스크립트 설치, 외부 분석 API 연동은 하지 않는다.
- 회원·프로젝트 확정 사실과 분석상의 행동 관찰은 원천·정의·신뢰도를 구분한다.
- 식별·보관·수집 거부 정책을 구현 계약에서 확정하고 실제 추적 활성화를 확인한다. 정책 검토 전에는 수집을 켜지 않아도 운영 화면을 개발할 수 있다.
- 기존 서버·DB 용량과 조회 부하를 측정한다. 자체 개발이 추가 비용 0원이라는 보장은 아니다.
- 제외한 분석 기능의 데이터·예약 작업·비활성 코드도 선제적으로 추가하지 않는다.

자체 이벤트 계약에서 검토할 최소 필드:

- `event_id`: 중복 전송을 구분하는 값.
- `event_name`: 허용된 종류만 수신.
- `content_id` 또는 검증된 경로 키: 글·페이지 식별.
- `session_id`: 승인된 정책에 따른 임시 분석 식별자.
- `occurred_at`, `received_at`: 발생 시각과 서버 수신 시각. 허용 시간 범위를 확인.
- 유입은 검색어·개인정보가 섞인 전체 URL 대신 제한한 출처·캠페인 값으로 수집.

방문자 지표가 필요하면 별도 방문 식별 정책이 필요하다. 세션 ID만으로 사람 수를 계산하지 않는다.
Discord ID·이메일·JWT를 분석 식별자로 사용하거나 외부 도구에 보내지 않는다.
회원과 분석 식별자의 연결을 당연한 기본값으로 만들지 않는다.
동의·거부 처리, 보관 기간, 삭제·집계 정책은 도구와 운영 정책을 선택한 뒤 확정한다.

수집기는 입력 크기 제한, 이벤트·콘텐츠 허용 목록, 속도 제한, 중복 방지, 관리자·미리보기·개발 트래픽 분리를 검토한다.
클라이언트가 보낸 이벤트를 프로젝트 확정·회원 가입 완료 등의 업무상 사실로 신뢰하지 않는다.
수집 실패 때문에 공개 글의 표시나 탐색이 실패해서는 안 된다.

### 7.3 제안 API 책임

구체 주소·요청 타입은 구현자가 기존 관례와 함께 확정한다.

- 관리자 접근 가능 영역 조회: 권한별 메뉴의 유일한 기준, 실제 엔드포인트에서도 재검사.
- 운영 요약: 각 지표의 값뿐 아니라 측정 상태·기준·마지막 집계 시각 반환.
- 회원·연구 목록: 서버 필터·페이지네이션·안정적인 정렬. 상세도 대상별 권한 검사.
- 계정 조치: 기대 현재 상태·작업 사유·요청 식별자를 받아 검증.
- 방문·글별 성과: 시간 범위·집계 단위·지표 정의·수집 시작일·완전성 포함.
- 운영 이력 조회: 총괄 또는 승인된 운영 담당의 업무 범위로 제한. 인사이트 담당자에게 회원·연구 조치 기록을 노출하지 않음.

`value=0`만으로 미수집과 실제 0건을 함께 표현하지 않는다.
상태 예시는 `ready / not_configured / collecting / error`이며 실제 계약은 한 곳에서 정의한다.
집계가 오래 걸리면 갱신 주기와 마지막 성공 시각을 표시한다. 대형 캐시·분석 인프라는 먼저 만들지 않는다.

## 8. 권한·안전 경계

| 대상 | 권장 접근 |
|---|---|
| 비로그인·일반 회원 | 관리자 페이지·API 접근 거절 |
| 지정 인사이트 담당자(현재 사용자 본인) | 인사이트 운영. 기존 허용 목록의 타 계정은 자동으로 승인된 담당자로 간주하지 않음 |
| 공통 전체 관리자 | 승인된 운영 조회·통계. 상태 변경은 해당 기능 승인 이후 |
| 정지·탈퇴 계정 | 기존 인증 정책으로 관리자 접근도 차단 |

- `is_admin` 자동 변경, 허용 목록의 전체 관리자 전환, 테스트 편의를 위한 권한 우회는 금지한다.
- 전체 관리자 필드만으로 인사이트 변경 권한까지 자동 부여하지 않는다. 기존 로그인·보호 동작을 유지하면서 본인 전담 정책에 맞게 기능별 권한을 분리한다.
- 관리자 권한 부여·회수 UI와 세밀한 역할 편집은 후속으로 남긴다.
- 운영자 2명에게 총괄·운영·콘텐츠·통계 조회의 고정 권한 묶음을 제안한다. 실제 배정은 사용자가 선택한다. 초기 배정은 안전한 서버 설정/승인 절차로 처리하고 범용 권한 편집기를 먼저 만들지 않는다.
- 쿠키 인증 쓰기에는 현재 서버의 Origin·CSRF 보호 방식을 확인해 같은 수준으로 적용한다.
- 관리자 화면 전체의 인증을 인사이트 기능 활성화 플래그에 묶지 않는다.
- 관리자 검색 결과나 응답을 공개 페이지의 캐시로 공유하지 않는다.
- 실제 비공개 연구 열람·연락처 접근 권한을 이 기획만으로 확대하지 않는다.

## 9. 구현 우선순위와 승인 지점

| 단계 | 결과 | 시작 조건 |
|---|---|---|
| 0 | 현재 기능·데이터·권한·변경 파일 조사와 최종 범위표 | 읽기 전용 조사 가능 |
| 1 | 공통 관리자 진입·회원/연구 조회·현재 상태 집계 | 사용자 구현 범위 승인, 기존 변경과의 충돌 확인 |
| 2 | 회원 정지·해제와 해당 운영 이력 | D2 조치 정책 승인, 가상 DB 테스트 |
| 3 | 자체 방문·글별 조회·등록 단계 수집 | 자체 방식 확정. 식별·보관·제외 기준 계약 검토 후 단계 실행 |
| 4 | 방문·글별 성과·운영 요약 연결 | 수집 데이터와 조회 집계 검증 |
| 5 | 실제 협업 프로젝트 관리·단계 전환 통계 | 팀의 기존 협업 모듈·상태 계약과 연결 승인 |

공개 대상 숨김은 해당 공개 데이터 계약을 확인한 뒤 별도 목적의 단계로 편성한다.
운영 이력 데이터 계약은 1단계에 설계하고, 실제 상태 변경과 함께 2단계에서 원자적으로 검증한다.
회원·연구 조회도 새 관리자 권한 경계이므로 0단계 조사만으로 자동 구현하지 않는다.
기능 구현 승인과 원격 migration·실제 회원 변경·배포 승인은 구분한다.
문서 변경은 합의된 부분만 제품 범위·결정 로그에 최소 반영하며 기존 설명을 대규모 재작성하지 않는다.

## 10. 수용 기준

### 권한·조치

- 비로그인·일반 회원·총괄 겸 인사이트 담당자·콘텐츠 권한 없는 운영 담당·정지 계정으로 각각 허용/거절 확인.
- 다른 운영자의 인사이트 작성·수정·승인·게시·수집 설정 변경은 주소 직접 호출도 거절.
- 다른 대상 ID를 직접 입력한 API 호출, 임의 필드 주입도 거절.
- 정지 후 기존 쿠키 접근 차단, 해제 후 정상 인증 재확인.
- 조치 사유 누락·상태 충돌·중복 요청·응답 유실·로그 저장 실패를 검사.
- 상태 변경만 성공하고 이력이 빠지거나 이력만 성공하는 경우가 없어야 함.
- 공개 대상 숨김을 구현하면 직접 주소·검색·API·노출 캐시까지 검사.

### 통계

- 한국 시간 자정·주 경계·월 경계·선택 구간을 넘는 데이터를 검사.
- 계정 생성과 가입 완료, 연구 생성과 최초 등록의 날짜가 다른 예제로 확인.
- 이전 기간 0, 분모 0, 수집 시작 전, 지연·장애·부분 수집 상태를 확인.
- 같은 이벤트 재전송은 1회, 별도 정상 조회는 정의대로 집계.
- 프리패치·404·관리자·미리보기·개발 이벤트는 일반 조회수에서 제외.
- 같은 세션이 다른 날에도 같은 글을 읽는 예제로 기간별 고유 집계 검사.
- 글 제목·주소·판본 변경 후에도 콘텐츠 단위 연속성을 확인.
- 측정 전 과거 수치를 추정값으로 채워 넣지 않음.

### UI·회귀

- 검색·필터·페이지·정렬·뒤로가기 복원, 빈 화면·실패·재시도 검사.
- 1440/768/390px에서 가로 넘침·표 내부 스크롤·키보드 조작·확인창 검사.
- 기존 인사이트 메뉴·필터·편집·미리보기·승인·공개본 보존·미저장 변경 보호 검사.
- 공개 사이트·회원 가입·내 연구 기능을 불필요하게 변경하지 않았는지 확인.
- 테스트·정적 검사·빌드와 실제 수행 범위를 기록. 가상 데이터 테스트를 실제 운영 검증이라고 쓰지 않음.

## 11. 추가 의견과 후속 후보

권장:

- '더 많은 지표'보다 원인이 되는 목록으로 이동하는 연결을 우선한다.
- 회원은 가입 단계의 병목, 연구는 협업으로 이어지는 단계, 인사이트는 다음 탐색 행동을 중요하게 본다.
- 로그와 안전한 복구 경계를 통계 차트보다 먼저 설계한다.
- 동작하지 않는 알림 배지·가짜 실시간 접속 수·장식용 성공률을 넣지 않는다.

후속 후보:

- 신고·문의: 실제 접수 경로·담당자·처리 상태를 합의할 때 추가.
- 분류·기관 정보 정정: 현재 승인 체계와 데이터 소유자 확인 후 별도 기획. 관리자 개발을 이유로 재승인·일괄 상태 변경하지 않음.
- CSV 내보내기·일괄 처리·세부 관리자 권한 UI: 개인정보·복구·책임 경계 검토 후 추가.
- 추가 분석: 이번 필요 지표를 먼저 검증하고 별도 요구가 생길 때만 검토. 자동 후속 일정 없음.

장기 범위에서도 제외:

- 화면 녹화·세션 재현, 히트맵, 개인별 전체 이동 이력, 실시간 접속 지도, 범용 분석기.
- 이를 위해 필요한 자동 DOM·입력값·포인터 이동 수집, 숨겨진 준비 코드나 예약 작업.
- 등록 과정에 필요한 최소 단계·오류·저장 결과 기록과 단순 합계·추이는 위 제외 기능과 구분해 구현한다.

## 12. 이번 문서의 검증 범위

- 현재 작업 경로·브랜치·기존 변경 목록과 관련 로컬 코드·범위 문서를 읽었다.
- v0.1에서는 새 Markdown 두 파일을 작성했다. v0.2에서는 사용자 답변으로 두 파일을 갱신하고 후속 상세 문서 한 개를 추가했다. 기존 제품 범위·디자인 문서는 변경하지 않았다.
- 실제 DB·회원·방문 데이터는 조회하거나 변경하지 않았다.
- 관리자 화면·분석 수집기·API를 구현하지 않았으므로 실행 테스트·브라우저 검증·배포는 하지 않았다.
- 기본 관리 방향·인사이트 본인 전담·자체 분석·장기 제외 범위를 사용자 답변으로 확정했다. 계정 식별·수집 정책 등 기술 계약은 실행 시 확인하며, 문서 자체는 구현 완료나 원격 운영 변경의 승인 증거가 아니다.
