# Research × AI Collaboration Platform 기획 정리

> 연구자와 AI 전문가를 연결하고, 프로젝트 발견부터 협업 종료 및 평가까지
> 관리하는 연구 협업 플랫폼

## 1. 서비스 방향

이 서비스는 단순한 **AI 전문가 소개/구인 사이트**가 아니라 다음 전체
흐름을 지원하는 **Research Collaboration Platform**을 목표로 한다.

**발견 → 매칭 → 요청/지원 → 선택 → 협업 → 연구 수행 → 종료 → 평가 → 이력
축적 → 다음 협업**

핵심은 회원 수 자체보다 **좋은 연구자--AI 전문가 매칭이 실제 협업으로
이어지는 것**이다.

------------------------------------------------------------------------

## 2. 핵심 매칭 구조

플랫폼에서는 두 가지 매칭 방식을 모두 지원한다.

### 2.1 공개 모집형

연구자가 프로젝트를 등록하고 AI 전문가가 지원하는 방식.

``` text
연구자
↓
프로젝트 등록
↓
AI 전문가가 프로젝트 탐색
↓
참여 신청
↓
연구자가 전문가 선택
↓
협업 시작
```

### 2.2 직접 매칭형

연구자가 적합한 AI 전문가를 찾아 직접 협업을 요청하는 방식.

``` text
연구자
↓
AI 전문가 탐색
↓
전문가에게 협업 요청
↓
전문가 검토/수락
↓
협업 시작
```

따라서 서비스의 핵심 모델은 다음과 같다.

**Open Recruitment + Direct Matching**

## 4. `내 프로젝트`보다 `내 협업 공간`

사용자가 관리해야 하는 것은 프로젝트만이 아니다.

-   받은 요청
-   보낸 요청
-   참여 신청
-   받은 신청
-   진행 프로젝트
-   일정
-   저장한 프로젝트/전문가
-   평가
-   알림

따라서 상위 메뉴를 **내 프로젝트**보다 **내 협업 공간**으로 설계하는
것이 적합하다.

예시:

``` text
내 협업 공간

Dashboard

요청 관리
 ├─ 받은 요청
 └─ 보낸 요청

프로젝트
 ├─ 진행 중
 ├─ 예정
 └─ 완료

일정

저장

평가

내 계정
```

## 5. 홈 화면

현재 연구 콘텐츠/연구 포털 느낌보다 **연구자 ↔ AI 전문가 협업 연결
서비스**라는 정체성을 상단에서 명확히 보여줄 필요가 있다.

### Hero 예시

**연구에 필요한 AI 전문가를 찾아보세요**

AI 경험이 필요한 연구자와\
연구 프로젝트에 참여하고 싶은 AI 전문가를 연결합니다.

CTA:

-   프로젝트 등록하기
-   AI 전문가 찾기

그 아래에는 다음 콘텐츠를 배치할 수 있다.

1.  연구 블로그 / 인사이트
2.  AI 협업 성공 사례
3.  함께할 사람을 찾는 연구 과제
4.  지금 함께할 수 있는 AI 전문가

## 6. 프로젝트 찾기

프로젝트 카드 및 검색 화면에서 기본적으로 필요한 정보:

-   연구 분야
-   모집 상태
-   연구 내용
-   필요한 기술
-   프로젝트 기간
-   지원 인원

추가로 실제 참여 판단에 중요한 정보를 제공한다.

### 6.1 참여 방식

-   온라인
-   오프라인
-   하이브리드

### 6.2 예상 투입량

예:

-   주 2시간
-   주 5시간
-   단기 자문
-   정기 참여

단순히 `6개월 프로젝트`라고 표시하는 것보다 `6개월 / 주 2시간`처럼
보여주는 것이 실질적인 판단에 도움이 된다.

### 6.3 협업 형태

-   단기 자문
-   PoC 개발
-   데이터 분석
-   모델 개발
-   연구 설계
-   논문 공동연구
-   장기 프로젝트

### 6.4 보상 형태

플랫폼이 결제나 계약을 직접 중개하지 않더라도 보상 형태는 프로젝트
정보로 제공하는 것을 검토한다.

-   무급 연구협업
-   연구비 지급 가능
-   협의
-   공동연구 / 논문 참여
-   인턴십 / 프로젝트 경험
-   기업 산학 프로젝트

## 7. 연구 데이터 상태(Data Readiness)

일반 프리랜서 플랫폼과 차별화할 수 있는 연구 협업 특화 요소다.

예:

-   데이터 없음
-   데이터 수집 중
-   데이터 보유
-   전처리 완료
-   분석 가능
-   민감 데이터

프로젝트 등록 시 고려할 필드:

``` text
데이터 보유 여부
데이터 형태
  - 텍스트
  - 이미지
  - 정형
  - 영상
  - 기타

대략적인 데이터 규모
민감정보 포함 여부
외부 공유 가능 여부
```

연구자가 AI 개발을 요청하더라도 데이터 상태에 따라 실제 수행 가능성이
크게 달라질 수 있으므로 중요한 정보다.

## 8. AI 전문가 찾기

전문가 목록에서는 다음 정보를 중심으로 제공한다.

-   연구 분야
-   AI 전문 영역
-   기술
-   참여 가능 상태
-   과거 프로젝트 참여 경험
-   협업 요청 CTA

### 8.1 활동/신뢰 지표

단순한 `받은 요청 수`보다 다음 지표가 유용하다.

-   응답률
-   평균 응답 시간
-   완료 프로젝트 수
-   재협업 의향

예:

``` text
응답률 92%
평균 응답 1.4일
완료 프로젝트 4건
재협업 의향 94%
```

### 8.2 정렬

추천 후보:

-   추천순
-   바로 참여 가능
-   최근 활동순
-   평가 높은순
-   프로젝트 경험순

향후 추천 시스템을 적용할 경우 `추천순`을 기본 정렬로 활용할 수 있다.

## 9. AI 기반 매칭

AI 기능을 적용할 우선순위는 콘텐츠 자동 생성보다 **연구자--전문가
매칭**에 둔다.

### 9.1 프로젝트 → 전문가 추천

예:

``` text
김서윤
92% Match

왜 추천되었나요?

✓ 의료 영상 프로젝트 경험
✓ PyTorch 사용 경험
✓ 현재 바로 참여 가능
✓ 유사 프로젝트 3건 완료
```

추천 요소 예시:

-   연구 분야 일치도
-   요구 기술 일치도
-   가용 일정
-   과거 프로젝트 경험
-   협업 형태
-   데이터 유형 경험

### 9.2 전문가 → 프로젝트 추천

예:

``` text
의료영상 병변 검출 프로젝트
Match 94%

왜 추천됐나요?

✓ PyTorch
✓ 의료영상 경험
✓ 객체 탐지 경험
✓ 요구 일정과 가용기간 일치
```

즉, **양방향 추천 구조**를 지향한다.

``` text
Research Project
       ↕
   Matching
       ↕
   AI Expert
```

장기적으로 이 Matching Data가 플랫폼의 중요한 데이터 자산이 될 수 있다.

## 11. 전문가 평가

단순한 별점 하나보다 평가의 맥락을 제공한다.

예:

``` text
전문성       4.8
의사소통     4.7
일정준수     4.9
협업만족도   4.8
```

표본 수도 함께 표시한다.

``` text
4.8 / 5.0
완료 프로젝트 12건 기준
```

평가 건수가 적은데 높은 평점만 크게 표시하는 방식은 피한다.

## 12. 프로젝트 상세에서 AI 전문가가 알고 싶은 정보

프로젝트 상세 화면에서는 다음 질문에 답할 수 있어야 한다.

-   무엇을 만들어야 하는가?
-   데이터는 있는가?
-   얼마나 참여해야 하는가?
-   언제까지 해야 하는가?
-   몇 명과 일하는가?
-   내 역할은 정확히 무엇인가?
-   연구 결과는 어디에 사용되는가?
-   논문 저자 참여가 가능한가?
-   보상은 있는가?
-   데이터 반출이 가능한가?

연구 목적뿐 아니라 **실제 작업 조건**을 충분히 제공해야 한다.

## 15. 요청 관리

두 가지 요청 방향을 관리한다.

### ProjectApplication

**AI 전문가 → 공개 프로젝트 신청**

**연구자 → 특정 AI 전문가 협업 요청**

두 흐름은 방향과 의미가 다르므로 백엔드에서도 별도 개념으로 관리하는

## 16. `협의 중` 단계

현실적인 협업은 보통 즉시 수락으로 이어지지 않는다.

``` text
요청
↓
관심 있음
↓
질문
↓
미팅
↓
협의
↓
최종 수락
```

따라서 `협의 중`과 같은 중간 상태 또는 문의 기능이 필요할 수 있다.

## 17. 문의와 실시간 채팅

MVP에서는 실시간 채팅을 우선 구현하지 않는다.

실시간 채팅은 다음 기능까지 요구할 수 있어 복잡도가 커진다.

-   WebSocket
-   읽음 상태
-   차단
-   신고
-   이미지/파일
-   Push Notification
-   메시지 보관
-   개인정보 관리

초기에는 다음 정도로 충분하다.

``` text
문의 남기기
↓
이메일/사이트 알림
↓
사이트 내 답변
```

## 18. 저장 기능

### AI 전문가

프로젝트를 바로 신청하지 않고 나중에 검토할 수 있도록:

-   관심 프로젝트 저장

### 연구자

전문가를 나중에 검토할 수 있도록:

-   관심 전문가 저장

내 협업 공간에 다음 메뉴를 둘 수 있다.

``` text
저장한 프로젝트
저장한 전문가
```

구현 난이도 대비 활용도가 높은 기능이다.

``` text
 ├─ AI 연구실
 └─ 의과대학 OO연구실

연세대학교
 └─ OO 연구센터
```

사용자 프로필은 기관/연구실과 연결할 수 있다.

``` text
홍길동
OO대학교
OO연구실
Researcher
```

향후 기관 전용 기능을 고려한다면 초기 DB 설계부터 Organization/Lab
구조를 고려하는 것이 좋다.

## 24. 연구 성과, IP, 저자권

플랫폼이 직접 판단하거나 계약을 중개하지 않더라도 연구 협업에서는 다음
요소에 대한 안내가 필요하다.

-   연구 성과 귀속
-   논문 저자권
-   코드 소유권
-   지식재산권(IP)
-   결과물 사용 범위

예:

> 공동연구 결과물의 IP, 논문 저자권, 코드 소유권 등은 프로젝트 참여자 간
> 별도 협의가 필요합니다.

## 30. 다음으로 설계할 핵심 화면

현재 UI 이후 우선 설계할 화면:

### 1) 프로젝트 등록

연구자가 프로젝트의 목적, 필요 기술, 데이터 상태, 참여 조건 등을
입력한다.

### 2) 협업 요청 작성

연구자가 특정 AI 전문가에게 직접 협업을 요청한다.

### 3) 프로젝트 참여 신청

AI 전문가가 공개 프로젝트에 참여 신청한다.

### 4) 내 협업 대시보드

예:

``` text
받은 요청 2
검토할 지원자 3
진행 프로젝트 2
평가 대기 1
```

### 5) 프로젝트 진행 화면

``` text
프로젝트 정보
참여자
일정
상태
파일 / 외부 링크
프로젝트 종료
```

### 6) 온보딩

연구자와 AI 전문가의 초기 프로필 등록 흐름을 각각 설계한다.

이 6개 화면까지 설계하면 핵심 서비스 Flow가 대부분 연결된다.

## 32. 핵심 KPI

초기에는 단순 회원 수보다 실제 매칭과 협업 전환을 측정한다.

## 33. 핵심 의사결정 요약

### 1. `프로젝트 찾기 + AI 전문가 찾기`를 `협업 찾기`로 묶는다.

두 가지 매칭 방식은 모두 유지한다.

### 2. `내 프로젝트`를 `내 협업 공간`으로 확장한다.

요청, 프로젝트, 일정, 저장, 평가 등을 한곳에서 관리한다.

### 3. `블로그`의 우선순위를 낮추고 `인사이트`로 재정의한다.

서비스의 핵심은 콘텐츠가 아니라 **매칭과 협업**이다.

### 4. 다음 핵심 Flow를 먼저 완성한다.

``` text
프로젝트 등록
↓
지원 / 직접 요청
↓
요청 관리
↓
검토 / 협의
↓
프로젝트 진행
↓
종료
↓
평가
```

### 5. AI 기능의 우선순위는 매칭이다.

AI 블로그 자동 생성보다 다음 기능을 우선 고려한다.

-   프로젝트에 맞는 전문가 추천
-   전문가에게 맞는 프로젝트 추천
-   추천 이유 설명
