- 작성일·자료 확인일: 2026-10-25
- 상태: v1.0. 인사이트 본인 전담·제한된 자체 분석·장기 제외 범위 확정. 실제 계정 지정·수집 정책은 구현 시 확인한다.
- 연결 문서: [기본 기획](ADMIN_OPERATIONS_PLAN_2026-10-25.md), [Cursor 프롬프트](ADMIN_OPERATIONS_CURSOR_PROMPTS_2026-10-25.md)
- 이번 변경: 기획 문서만 갱신했다. 계정 지정, 관리자 권한 변경, 도구 가입·설치, 추적·녹화, 실제 DB 적용·배포는 실행하지 않았다.

## 1. 사용자 답변으로 정해진 방향

| 질문 | 확정 방향 | 실행 경계 |
|---|---|---|
| 연구·프로젝트 | 구분 관리하며 등록을 끝내지 못한 경우의 원인도 살핀다 | 관찰 신호로 이유를 단정하거나 초안 본문을 운영자에게 공개하지 않음 |
| 관리자 조치 | 회원 정지·해제, 실제 공개 대상 숨김·복구의 기존 제안을 수용 | 강제 삭제·프로젝트 강제 완료는 제외. 실제 대상 조치는 별도 요청 때 실행 |
| 운영자 | 사용자 포함 2명. 인사이트 운영은 당분간 사용자 본인만 담당 | 다른 운영자에게 콘텐츠 작성·편집·승인·게시·수집 설정 변경 권한을 주지 않음. 실제 계정 지정은 별도 |
| 개발 목표 | 발표용 시안이 아니라 실제 운영 가능한 수준 | 권한·데이터 무결성·회귀 검증을 포함. 즉시 원격 변경·배포하라는 뜻은 아님 |
| 분석 방식 | 무료 외부 도구 비교 후 제한된 자체 개발로 확정 | 외부 분석 도구 도입은 하지 않음. 계정 지정·수집 정책·실제 활성화는 별도 확인 |
| 장기 제외 | 화면 녹화·히트맵·개인별 전체 이동 이력·실시간 접속 지도·범용 분석기는 앞으로도 필요성이 크지 않다고 확인 | 현 로드맵에서 제외. 새로운 요구가 없으면 관련 기능·기반 코드도 만들지 않음 |

## 2. 등록 미완료는 하나의 상태가 아니다

로컬 `frontend/src/components/my-research-modal.tsx`의 현재 단계는 다음 네 가지다.

1. 연구
2. 데이터
3. 협업
4. 확인

현재는 제목을 입력해야 임시저장 버튼을 사용할 수 있다.
따라서 DB의 임시저장 건수만 보면 창을 열고 제목 입력 전 닫은 경우를 놓친다.
기존 등록 연구의 수정 중단은 신규 등록 실패가 아니다.
창에는 등록 연구를 본인만 보고 협업 요청 때 선택해 함께 보낸다는 안내도 있다.
이 약속을 유지하며 내용이 아닌 **과정 메타정보**로 분석한다.

### 2.1 구분할 관찰 집단

| 집단 | 의미 | 기본 데이터 |
|---|---|---|
| 작성 시작, 저장 없음 | 새 등록 창은 열었으나 저장·등록 확인이 없음 | 신규 작성 시도 식별자·시작·단계 기록 |
| 임시저장 연구 | 저장은 했지만 등록 상태에 도달하지 않음 | 연구 ID·현재 상태·최초 저장 시각·허용된 과정 기록 |
| 다시 작성함 | 임시저장 연구를 재개하거나 같은 흐름을 이어감 | 재개 모드·연결된 연구 ID·단계 기록 |
| 등록 완료 | 서버가 최초 등록을 성공시킴 | 서버의 최초 등록 사실·시각 |
| 기존 연구 수정 | 이미 등록된 연구를 편집함 | 수정 모드, 신규 등록 모수에서 제외 |

작성 창을 한 번 열었다는 사실만으로 작성 의사가 확정되었다고 보지는 않는다.
첫 단계 탐색·내용 확인과 본격적인 작성을 완벽하게 구별할 수 없으므로 지표의 한계로 남긴다.
회원 목록의 생성 시각·최근 수정 시각으로 이 과정을 추정하지 않는다.

### 2.2 필요한 최소 사건

아래 이름은 계약 제안이며 기존 프로젝트의 명명 관례를 확인한 뒤 확정한다.

| 사건 | 기록 시점 | 허용 정보 예시 |
|---|---|---|
| 작성 창 열기 | 등록 창이 실제로 표시됨 | create / resume / edit 모드, 작성 시도 식별자 |
| 단계 표시 | 단계 화면이 실제로 표시됨 | research / data / collaboration / review |
| 다음 단계 진행 | 유효성 검사를 통과해 이동함 | 이전·다음 단계 |
| 입력 검증 실패 | 진행·저장을 시도했으나 검사에서 막힘 | 단계, 미리 정한 오류 코드 |
| 임시저장 성공·실패 | 서버 응답으로 확인 | 단계, 저장 결과, 안전한 오류 분류 |
| 명시적 나가기 | 닫기·나중에 작성 버튼으로 종료 | 마지막 단계, 선택형 사유 유무 |
| 등록 성공 | 서버 트랜잭션으로 최초 등록 확정 | 최초 등록 시각, 내부 연구 연결 |

입력값, 연구 제목·설명, 실험 내용, 연락처, 전체 URL, 오류 원문·요청 본문은 분석 도구로 보내지 않는다.
저장·등록의 확정 사실은 클라이언트 버튼 클릭과 구분한다.
외부 도구의 사용자 ID를 내부 회원 ID·Discord ID로 맞추는 기능은 기본 제외다.
내부 업무 집계와 외부 익명·가명 분석의 식별 관계를 무조건 결합하지 않는다.

신규 창·다시 열린 초안·여러 탭·재시도에서 중복이 나지 않도록 작성 시도와 연구 단위의 집계 기준을 먼저 확정한다.
새 시도 횟수와 임시저장 글 수는 서로 다른 모수다.
같은 초안을 여러 번 재개해도 초안 수·최초 등록 수가 늘지 않아야 한다.
기존 등록 연구의 수정은 신규 등록 전환율에서 제외한다.

### 2.3 중단 판정과 지표

사용자 탈퇴나 프로젝트 취소 상태를 새로 만드는 것이 아니라 분석용 관찰 상태다.

- 즉시 관찰: 명시적으로 나갔으나 등록 성공은 없는 시도.
- 24시간 미완료: 작성 시작 집단 중 정해진 관찰 기간 안에 등록이 확인되지 않은 경우.
- 7일 미완료: 임시저장 연구 중 해당 관찰 기간 안에 최초 등록이 확인되지 않은 경우.
- 다시 작성한 비율: 같은 정의의 초안 집단에서 재개 기록이 있는 고유 연구의 비율.
- 단계별 검증 실패: 진행을 시도한 횟수와 실패한 횟수·고유 시도를 구분.
- 저장 실패: 서버 오류·네트워크·권한/충돌 등을 구분하되 민감한 오류 원문은 남기지 않음.

24시간·7일은 조정 가능한 분석 제안값이다. 자동 삭제·정지·독촉의 기준이 아니다.
분모를 정한 집단의 관찰 기간이 아직 끝나지 않았으면 '관찰 중'으로 표시하고 최종 이탈률에 넣지 않는다.
창·브라우저 종료 이벤트는 누락될 수 있다. 닫기 기록이 없다는 이유로 사용자가 계속 작성 중이라고 단정하지 않는다.
수집 거부·차단·장애로 미측정된 경우가 있으므로 확정된 서비스 상태와 분석상의 추정·누락을 구별한다.

단계별 비교는 같은 기간에 발생한 사건 수를 단순히 나누지 않는다.
신규 시도 단위의 흐름과 저장된 연구 단위의 재개·완료를 별도 표로 보여주고,
두 단위를 연결한 전환율은 식별·집계 계약을 검증한 뒤 제공한다.

### 2.4 왜 중단했는지는 별도 확인

세 가지를 구별해 화면에 표시한다.

| 분류 | 예시 | 표현 |
|---|---|---|
| 관찰 신호 | 데이터 단계에서 마지막 기록, 검증 실패, 저장 오류 | 관찰된 현상 |
| 사용자 응답 | 아직 준비 중, 설명이 어려움, 보안이 걱정됨 | 사용자가 선택한 사유 |
| 운영 가설 | 데이터 항목의 설명이 어려울 수 있음 | 추가 확인이 필요한 가설 |

선택형 사유는 명시적으로 나갈 때 또는 임시저장 후 자연스러운 위치에서 한 번만 제안한다.
응답하지 않고도 나갈 수 있고, 브라우저를 닫는 사람에게 응답을 강요하지 않는다.
초기에는 자유 입력을 받지 않는다.

권장 선택지:

- 나중에 이어서 작성하려고요
- 연구 내용을 어떻게 설명할지 모르겠어요
- 데이터가 아직 준비되지 않았어요
- 공유·보안 조건이 걱정돼요
- 입력이 많거나 어려워요
- 오류가 났어요
- 기타 / 답하지 않기

이 응답을 보냈다고 상담·이메일·Discord 메시지를 자동 발송하지 않는다.
원인을 판단할 때 응답자 편향과 표본 수를 표시한다. 답하지 않은 사람의 사유를 채워 넣지 않는다.

### 2.5 관리자 화면 추가

`연구·프로젝트 관리 → 등록 과정 분석` 탭을 제안한다.

- 상단: 기간, 관찰 기간, 집계 시각, 측정 시작일, 데이터 누락 상태.
- 카드: 신규 작성 시도 / 저장 없이 미완료 관찰 / 현재 임시저장 연구 / 재개 후 최초 등록.
- 본문 왼쪽: 4단계 도달·검증 실패·미완료 관찰. 작은 표본은 건수를 먼저 표시.
- 본문 오른쪽: 선택형 사유 분포, 응답 수·응답률, 오류 분류.
- 하단: 최근 오류·중단 관찰 메타정보 목록. 초안 내용·입력값·연락처는 제외.
- 각 항목에 '관찰 신호 / 사용자 응답 / 운영 가설' 라벨을 구분.

먼저 분석하고 이후 입력 항목·도움말·임시저장 흐름을 개선한다.
이 기획을 이유로 필수 입력 기준이나 자동저장을 즉시 바꾸지는 않는다.

## 3. 운영자 2명을 위한 권한 구성

두 명에게 같은 최고 권한을 무조건 부여하기보다 고정된 권한 묶음을 제안한다.
권한 종류와 실제 담당자 배정을 분리하며 배정은 사용자가 선택한다.
초기에는 역할 묶음을 서버에서 관리하고, 범용 권한 편집기는 만들지 않는다.

| 기능 | 총괄 관리자 | 운영 담당 | 콘텐츠 담당 | 통계 조회 |
|---|---|---|---|---|
| 회원 목록·허용 상세 | 가능 | 가능 | 불가 | 불가 |
| 회원 정지·해제 | 가능 | 가능 | 불가 | 불가 |
| 연구·프로젝트 운영 메타정보 | 가능 | 가능 | 불가 | 불가 |
| 실제 공개 대상 숨김·복구 | 가능 | 가능 | 불가 | 불가 |
| 인사이트 작성·검토·승인·게시 | 가능 | 불가 | 가능 | 불가 |
| 집계된 이용 통계 | 가능 | 가능 | 콘텐츠 성과만 | 가능 |
| 조치 이력 | 전체 허용 범위 | 운영 업무 범위 | 기존 콘텐츠 이력 | 불가 |
| 역할 배정·회수 절차 | 담당 | 불가 | 불가 | 불가 |
| 초안 본문·연구 원자료 | 기본 제공 안 함 | 기본 제공 안 함 | 불가 | 불가 |

총괄 관리자도 비공개 연구 원문 열람을 자동 허용받는다는 뜻이 아니다.
총괄의 역할 배정은 안전한 초기 설정·확인 절차를 뜻하며, 이번에 원격 계정 변경이나 역할 편집 UI를 실행하지 않는다.
외부 도구 계정의 관리자 권한은 이 표와 별개다. 서비스 안의 역할을 바꿔도 외부 도구 권한은 자동 회수되지 않는다.
최소 인원으로 초대하고 계정 공유 대신 각자 계정을 사용한다.

배정 제안:

- 사용자: 총괄 관리자.
- 다른 운영자: 운영 담당. 사용자 답변에 따라 당분간 콘텐츠 담당 묶음을 배정하지 않는다.
- 단순 현황 확인 인원에게는 통계 조회만 부여할 수 있다.

운영 담당의 콘텐츠 승인 권한을 암묵적으로 열지 않는다.
단계 0에서 역할 묶음을 복수 배정할지와 기존 인증 구조에 맞는 최소 데이터 구조를 검토한다.
두 명에게 맞추는 목적이지 복잡한 조직/기관 계층이나 임의 권한 정책 엔진을 만드는 목적이 아니다.
회원 정지와 공개 글 숨김에는 사유·확인·운영 이력을 남긴다.
관리자 본인·다른 관리자 계정 정지와 마지막 총괄 관리자 상실은 초기 기능에서 차단한다.
강제 삭제·탈퇴 복구·프로젝트 강제 확정/완료는 제공하지 않는다.

현재 `is_admin`과 인사이트 전용 허용 목록의 동작을 먼저 확인하고 호환성을 유지한다.
인사이트 허용 목록에 있다는 이유만으로 운영 담당이 되지 않게 한다.
기존 전체 관리자 재매핑이나 개인별 권한 추가는 사용자의 계정 지정 확인 이후에만 한다.

## 4. 분석 방식 검토 기록과 자체 개발 확정

### 4.1 과거 외부 대안 — 현재 선택하지 않음: PostHog 무료 플랜 + 서비스 DB

이는 공급자의 필수 구조가 아니라 이번 요구에 맞춘 설계 제안이다.

- 서비스 DB: 실제 회원 상태, 가입·등록 완료, 프로젝트 확정·완료, 관리자 조치의 기준.
- 분석 도구: 공개 방문·글 조회, 승인한 과정 메타정보, 단계별 도달·이동과 누락 가능한 행동 신호.
- 관리자 화면: DB 집계와 분석 API의 결과를 가져와 표시. 같은 이름이라도 원천·정의·갱신 시각을 함께 표시.
- 서버: 분석 조회 API 자격증명을 보관하고 권한 검사 후 제한된 결과만 전달.
- 브라우저: 개인 API 키나 분석 도구의 관리 자격증명을 받지 않음.

PostHog 공식 API 문서는 모든 사용자에게 API를 제공하며 앱에서 조회 결과를 가져올 수 있다고 설명한다.
비공개 조회 API는 개인 API 키를 요구하므로 서버에서만 사용하고 필요한 최소 범위로 제한한다.
호출 한도·캐시·조회 비용 정책을 실제 선택일에 검증하고, 별도 유료 기능이 필요한 경로는 사용하지 않는다.
공개 공유 대시보드나 인증 없는 iframe으로 내부 운영 지표를 우회 공개하지 않는다.

근거: [PostHog API 공식 문서](https://posthog.com/docs/api)

도구 선택이 다르면 지표 계약은 유지하고 공급자 조회·수집 계층만 교체한다.
공급자 코드를 모든 페이지에 흩뿌리는 구조나 큰 범용 분석 엔진은 만들지 않는다.

### 4.2 과거 외부 도구 검토 시의 비용 관리 원칙 — 현재 도입하지 않음

1. 처음에는 카드 등록 없는 무료 플랜을 사용한다. 자동 유료 전환·유료 부가기능을 선택하지 않는다.
2. 실제 무료 한도·프로젝트 수·보존·조회 API 정책을 가입 시 다시 확인한다.
3. 향후 카드를 넣으면 제품별 한도를 다시 검토해야 한다. 그 전까지 무료 설정이 유지된다고 가정하지 않는다.
4. 화면 녹화·세션 재현·자동 DOM 수집·필요 없는 오류/성능 수집은 기본 끈다.
5. 페이지·단계·저장 결과 등 필요한 사건만 명시적으로 보낸다. 타이핑할 때마다 보내지 않는다.
6. 사용량과 수집 상태를 운영자가 확인한다. 경고 기준은 예를 들어 한도의 70%·90%로 제안한다.
7. 한도에 닿으면 누락될 수 있으므로 해당 기간을 불완전한 데이터로 표시한다. 결측을 실제 이용 감소로 해석하지 않는다.
8. 외부 도구 제한이 있더라도 가입·등록·읽기·회원 관리 같은 본래 서비스는 계속 동작해야 한다.
9. 기존 호스팅·DB의 무료 한도도 별도로 점검한다. 자체 이벤트를 전부 DB에 중복 저장해 비용을 키우지 않는다.

1회 방문이 1개 사건은 아니다. 예를 들어 10,000회 방문에 평균 12개 사건을 보낸다면 120,000개 사건이라는 식으로 예산을 계산한다.
이는 설명용 산수이며 실제 이용량 예측이 아니다. 도구의 자동 추가 사건과 과금 단위는 설치 검증에서 확인한다.

### 4.3 개인정보·연구 정보·운영 주의점

- 무료 도구를 쓴다고 자동으로 개인정보 요건을 충족하는 것은 아니다.
- 수집 항목·목적·공급자·처리 지역·보관·삭제·외부 제공/국외 처리와 고지·동의·거부 방식을 실제 설정에 맞춰 검토한다.
- 법적 적용 요건은 취급 정보·이용자·공급자 조건에 따라 별도 확인한다. 이 기획은 적법성 검토를 대체하지 않는다.
- 연구 제목·설명·데이터 파일·협업 메시지·개인 연락처는 외부 분석 도구에 보내지 않는다.
- 원문이 포함된 DOM·전체 주소·검색어·오류 메시지로 간접 유출되지 않는지도 검사한다.
- 화면 녹화는 단순 영상만이 아니라 화면 구성과 행동을 수집할 수 있다. 마스킹 기본값만 믿고 비공개 화면에 넣지 않는다.
- 해시한 회원 ID도 연결 가능한 식별자라면 무조건 익명 데이터라고 부르지 않는다.
- 동의 거부·차단을 지문 수집이나 다른 식별자로 우회하지 않는다.
- 개발·관리자·미리보기·테스트 트래픽을 실제 이용에서 제외한다.
- 도구 설치만으로 전용 관리자 통계 화면이 완성되지는 않는다. 사건 정의·API·권한·갱신·품질 검증이 별도로 필요하다.
- 방문 수는 차단·거부·한도·시차로 불완전할 수 있다. 정지·탈퇴·실제 협업 같은 조치의 단독 근거로 쓰지 않는다.

### 4.4 자체 개발한다면 — PostHog 전체가 아닌 제한된 운영 분석

직전 단계에서는 사용자의 질문에 따라 자체 개발의 장단점을 비교했다. 이후 사용자가 자체 개발을 선택했으므로 현재는 4.5절의 확정 범위를 적용한다. 실제 추적 활성화까지 실행한 것은 아니다.
이전 PostHog 추천은 빠르게 분석 도구를 도입하는 관점이었다.
현재 필요한 지표로 범위를 고정하고 구현·운영 책임을 감수한다면 자체 개발도 합리적인 선택이다.

우선 분리할 것:

- 회원 상태·연구/프로젝트 상태·정지/숨김·운영 이력: 외부 도구를 쓰더라도 서비스에서 직접 구현해야 한다.
- 방문·글 조회·작성 단계별 행동 집계: 외부 도구를 쓰거나 직접 개발할 수 있는 부분이다.
- PostHog 선택이 관리자 전체를 외부 서비스에 맡긴다는 뜻은 아니다.

#### 장점

1. 연구 등록의 4단계·임시저장·재개와 연결한 정확한 업무 용어로 화면을 만들 수 있다.
2. 필요 없는 화면 녹화·자동 DOM 수집 없이 승인한 최소 메타정보만 남길 수 있다.
3. 외부 분석 공급자의 요금·API·화면 변화와 분리할 수 있다.
4. 실제 서버가 확인한 가입·등록·프로젝트 사건과 일관된 내부 지표를 만들기 쉽다.
5. 학습과 인계 관점에서 요청 → 검증 → 저장 → SQL 집계 → 관리자 표시의 흐름을 설명할 수 있다.

단, 분석 데이터를 Supabase에 저장하면 여전히 해당 인프라 공급자가 데이터를 처리한다.
'자체 개발=내 PC에만 보관' 또는 '외부 처리·개인정보 검토가 사라짐'이라고 설명하지 않는다.

#### 단점·숨은 작업

1. 글 표시와 서버 GET 호출은 다르다. GET마다 조회수를 올리면 프리패치·봇·재시도 등이 섞일 수 있다.
2. 신규 사건과 재전송을 구분하고, 같은 시간대의 동시 집계에서 중복·유실을 막아야 한다.
3. 방문자·세션·PV의 정의와 날짜 경계, 일/주/월 고유 수를 검증해야 한다.
4. 위조 사건·과다 요청·봇을 완벽히 제거할 수는 없다. 제외 기준과 지표의 한계를 표시한다.
5. 원본·집계·보관·삭제·정정·장애·지연을 운영자가 관리해야 한다.
6. 매번 전체 원본을 읽는 대시보드는 커질수록 느려질 수 있다. 필요한 인덱스·집계·조회 범위를 검증해야 한다.
7. 두 운영자 외에 분석 기능을 유지보수할 개발 책임도 남는다. 도구 요금 절감만으로 이 시간을 무시하면 안 된다.
8. 입력 과정을 기록해도 실제 중단 이유가 자동으로 밝혀지지 않는다. 선택형 응답과 관찰 신호를 계속 구분한다.

#### 비용에 대한 판단

자체 개발에는 분석 SaaS 구독료가 없지만 기존 호스팅·DB의 저장 공간·트래픽·계산·백업 부담이 늘 수 있다.
현재 실제 프로젝트의 요금제·사용량은 조회하지 않았으므로 추가 비용 0원을 보장하지 않는다.
공식 Supabase Free 안내의 DB 용량은 500MB이며, 이것은 분석용으로 따로 주어지는 공간이 아니라 해당 DB의 한도다.
작은 사건을 많이 저장해도 행·인덱스·집계 데이터가 함께 커질 수 있다.

#### 자체 개발을 택할 경우의 작은 시작 범위

첫 단계 권장:

- 페이지·인사이트 상세의 정상 조회와 관리자·개발·미리보기 제외.
- 일/주/월 PV, 인기 글, 익명 세션 기준의 방문 추이. 방문자 수는 별도 식별 계약 후 제공.
- 신규 등록의 4단계 도달, 검증/저장 오류 코드, 임시저장·재개·최초 등록 확인.
- 선택형 중단 사유. 입력 본문·자유 텍스트·원자료·화면 녹화는 제외.
- 최소 운영용 집계와 지표 정의·측정 상태를 보여주는 관리자 화면.

현재·후속 로드맵에서 제외할 것:

- 세션 녹화·히트맵·실시간 접속 지도·개인별 전체 이동 이력.
- 임의로 분석 단계를 조합하는 범용 분석기, 복잡한 장기 세그먼트·기여도 분석.
- 모든 행동·모든 필드를 수집하는 자동 추적과 대형 메시지/분석 인프라.

구조 검토안:

1. 화면에서 승인된 표시·단계 사건만 보내는 작은 수집 함수를 둔다.
2. FastAPI에서 허용 종류·크기·시각·콘텐츠 ID를 검증하고 속도를 제한한다.
3. 제한된 분석 기록을 저장한다. 브라우저에서 분석 테이블에 직접 임의 쓰기하도록 열지 않는다.
4. 동일 사건의 재전송을 제거하고, 업무상 확정 사실은 기존 서버 트랜잭션과 연결한다.
5. 조회량에 맞춰 필요한 집계를 만들고, 권한 검사한 관리자 API에서 제한된 결과만 반환한다.
6. 원본·집계의 보관 및 정정 기준을 따로 정한다. 원본을 지웠는데 과거 고유 방문자 수를 새로 계산할 수 있다고 가정하지 않는다.

일별 고유 방문자·고유 세션 수를 단순 합해 월별 고유 수로 만들지 않는다.
날짜·조회수는 더할 수 있어도 고유 식별 수는 별도의 집계 근거가 필요하다.
트래픽 원본 보관 정책을 회원 조치 이력·업무 기록에 적용해 함께 삭제하지 않는다.
위 구조는 확정된 자체 개발 방향의 기술 검토안이며 새 테이블·수집기를 이미 만들었다는 뜻은 아니다.

#### 비교 단계의 판단 근거

- 출시 속도·적은 유지보수가 우선이면 외부 무료 도구가 유리하다.
- 필요한 지표만 맞춤 제공하고 데이터 통제·학습을 중요하게 보면 제한된 자체 개발이 유리할 수 있다.
- LabBridge의 현재 요구는 범위가 정해져 있어 작은 자체 분석을 검토할 만하다. 범용 PostHog 복제는 권하지 않는다.
- 자체 방식 선택 전 지표·보관·식별·운영 책임과 실제 DB 여유를 확인하고 최종 Cursor 프롬프트를 확정한다.

### 4.5 자체 개발 확정 범위 — 현재 구현 기준

사용자 후속 답변: 자체 개발로 진행하며 이전 제외 기능은 이후에도 필요성이 크지 않음.
이 결정은 제품 범위 확정이며 이 대화에서 서비스 코드를 직접 구현하라는 요청으로 확대하지 않는다.

포함:

1. 회원·연구·프로젝트의 현재 상태와 확정된 서버 사건에 근거한 운영 집계.
2. 일·주·월 PV 및 세션 기준 방문 추이. 별도 방문자 지표는 식별 정책을 확정한 뒤 제공.
3. 인사이트별 기간·측정 이후 누적 조회수, 읽은 세션, 인기 글과 필요한 탐색 클릭.
4. 연구 등록 4단계 도달, 검증·저장 오류 분류, 저장 전 미완료·임시저장·재개·최초 등록 관찰.
5. 선택형 중단 사유. 실제 응답·관찰 신호·운영 가설의 구분.
6. 필요한 집계·기간 비교·관리자 표시와 수집 상태·권한·보관·집계 품질 관리.

포함하지 않음:

- 화면 녹화·세션 재현, 히트맵, 개인별 전체 이동 이력, 실시간 접속 지도, 범용 분석기.
- DOM·키 입력·포인터 이동의 자동 수집, 원문·연락처 수집, 위 기능의 숨겨진 기반 코드.
- PostHog·GA4·Clarity SDK·외부 분석 API·새 분석 공급자 계정.

이 제외는 '다음 단계에 구현'이라는 뜻이 아니다. 필요성이 새로 확인되면 별도 기획·승인한다.
필요한 단계 이동 기록은 등록 흐름 분석에만 제한하며 개인별 전체 사이트 탐색을 재구성하는 화면으로 확대하지 않는다.

구현 시 확정할 계약:

- 익명 세션·방문 식별의 수명·저장 방식·수집 거부, 원본과 집계의 보관·삭제 기준.
- 고유 수의 집계 근거, 과다·위조·재전송 대응, 데이터 누락·지연 표시.
- 실제 DB 여유·인덱스·조회 및 집계 부하, 격리 테스트와 변경 이력·백업.
- 계정별 권한 배정, 실제 DB 적용·운영 추적 활성화·배포 절차.

업무·운영 이력과 분석 원본은 보관 정책을 분리한다. 원본을 정리해 과거 고유 집계가 불가능해지면 제공 기간을 제한하거나 적절한 집계 근거를 먼저 확보한다.
비용·유지보수 부담은 자체 개발에서도 남으며 무료 사용을 보장하지 않는다.

## 5. 실제 운영 수준의 완료 조건

- 두 운영자의 실제 배정과 서버 권한 계약을 확인한다. 테스트용 가상 계정으로 거절·허용을 검증한다.
- 상태 변경과 운영 이력이 함께 성공/실패하는지, 기존 쿠키로 정지를 우회할 수 없는지 확인한다.
- 정지·숨김의 사용자 안내·내부 사유·조치 복구 경계가 정해져 있어야 한다.
- 연구 초안 내용은 기본 비공개, 분석 사건은 허용된 단계·오류 코드만 포함해야 한다.
- 분석 전송 실제 페이로드를 가상 데이터로 검사하고 금지 정보가 없는지 확인한다.
- 정상 재조회·이벤트 재전송·프리패치·SPA 이동·관찰 기간 미완료를 테스트한다.
- 자체 저장 용량·집계 부하·수집 API 실패·차단·거부·집계 지연 상태에서도 서비스와 관리자 화면이 안전하게 동작해야 한다.
- 실제 DB 적용 전 대상·백업·migration·접근 권한을 확인한다. 운영 배포와 추적 활성화는 사용자 선택 후 진행한다.
- 운영 절차에 담당자, 지표 정의, DB·트래픽 사용량 확인, 자체 관리자 권한 회수, 장애 시 대응을 기록한다.

## 6. 확정 사항과 구현 전 확인

1. 역할: 인사이트는 당분간 사용자 본인 전담으로 확정. 다른 1명에게 콘텐츠 변경 권한은 부여하지 않음. 실제 계정 지정은 별도 확인.
2. 분석 방식: 제한된 자체 개발로 확정. 외부 분석 도구 도입과 장기 제외 기능의 자동 후속 개발 없음.
3. 수집 정책: 자체 방식의 식별·보관·거부·페이지 제외 범위를 정하고 실제 활성화를 확인.

인사이트 권한과 자체 분석 방향은 Cursor 인계에 고정한다. 이미 정해진 제품 방향을 다시 질문하지 않고, 남은 기술·운영 계약만 실행 전에 확인한다.
서비스 구현은 Cursor에 전달할 계획이므로 이번 대화에서는 문서·기획만 정리하고 실행하지 않는다.
