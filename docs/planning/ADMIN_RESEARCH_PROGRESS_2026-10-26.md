# 관리자 연구 목록 — 진행 상태 표시

2026-10-26 사용자의 요청으로 작성 상태 옆에 진행 상태 열과 검색 필터를 추가합니다.
이번 범위는 관리자 조회 화면·응답 보완과 디자인 데모이며, 실제 프로젝트의 생성·상태 전환 기능을 새로 만드는 작업은 아닙니다.

## 1. 근거와 현재 소스

- `docs/product/MVP_SCOPE.md` 4절: 요청 관계와 확정 프로젝트 진행 상태를 구분합니다.
- `docs/product/02_SCREEN_GUIDE.md` PRJ-01: 시작 전·진행 중·일시 중지·종료 대기·완료·중단을 정의합니다.
- `docs/planning/ADMIN_OPERATIONS_PLAN_2026-10-25.md` A-04/05: 등록 연구와 협업 프로젝트를 구분하며 실제 모듈·상태 계약 확인 후 연결합니다.
- 현재 `research.status`는 `draft`/`registered`입니다. 운영 조회에 모집 기한·프로젝트 확정·시작·종료 정보가 없습니다.
- 직접 협업 요청의 `pending/accepted/started/expired`는 개별 요청의 상태입니다. 요청 하나가 만료되었다고 연구 전체를 미매칭 종료로 판정하지 않습니다.

## 2. 화면 용어 추천과 반영

| 화면 표시 | 조회용 코드 | 의미와 판정에 필요한 사실 |
|---|---|---|
| 모집 중 | `recruiting` | 공개 모집이 열려 있고 아직 최종 프로젝트 확정 전 |
| 모집 종료·미매칭 | `unmatched_closed` | 모집 기한이 지나 모집이 닫혔으며 확정된 협업이 없음 |
| 모집 취소 | `recruitment_canceled` | 프로젝트 확정 전에 연구자가 모집을 철회함. 기한 만료와 구분 |
| 진행 예정 | `scheduled` | 매칭·프로젝트 확정은 마쳤지만 실제 시작 전 |
| 진행 중 | `in_progress` | 프로젝트 시작이 확인됨 |
| 일시 중지 | `paused` | 참여자 합의로 작업을 잠시 멈추고 재개할 예정. 협업 관계는 유지 |
| 종료 확인 중 | `completion_pending` | 종료 요청 후 참여자 확인을 기다림. 아직 완료는 아님 |
| 완료 | `completed` | 종료 확인을 마침. 예정 종료일 도달만으로 판정하지 않음 |
| 중단 | `discontinued` | 시작한 협업을 목표를 마치지 못한 채 종료하기로 확정 |
| 해당 없음 | `not_applicable` | 임시저장 연구. 아직 모집·진행 상태 대상이 아님 |
| 연동 전 | `not_linked` | 모집·협업 상태를 조회할 원천이 아직 연결되지 않음 |

‘모집 중’은 공개 모집에 쓰는 명칭입니다. 직접 협업 요청만 보낸 연구까지 모집 중으로 묶지 않습니다.
공개 모집 전이거나 직접 요청으로 협의 중인 등록 연구는 실제 연동 시 **매칭 대기** 같은 별도 표시가 필요합니다.
‘연동 전’은 사용자 업무 상태가 아니라 데이터 연결 상태입니다. 연결 후 이를 매칭 대기로 일괄 변환해서는 안 됩니다.

‘비매칭 만료’보다 ‘모집 종료·미매칭’을 추천합니다. 기한이 끝난 대상과 매칭 결과를 함께 알려주고,
개별 요청의 응답 만료와 구분하기 쉽습니다. ‘진행 예정’을 추가해 매칭 완료와 실제 시작도 구분합니다.

## 3. 모집 기한과 예정 시작일

사용자 조건은 **모집 기한 = 연구 예정 시작일**입니다. 이를 적용하는 실제 업무 로직은 아직 연결하지 않습니다.
날짜만 저장한다면 시작일 00:00(한국 시간)에 모집 종료, 즉 전날 23:59까지 모집하는 방식을 제안합니다.
시작일 당일까지 모집하려는 의도라면 별도 마감 시각을 정해야 합니다. 정확한 시각 경계는 실제 모집 기능 연결 시 확인합니다.

- 마감 전에 프로젝트가 확정되었다면 진행 예정/진행 중이 우선입니다. 기한 도달로 미매칭 종료에 덮어쓰지 않습니다.
- 예정 시작일만 지났다고 프로젝트를 진행 중으로, 예정 종료일만 지났다고 완료로 바꾸지 않습니다.
- 마감 연장·재모집은 동일 연구의 새로운 모집 회차로 기록하는 방식을 제안합니다.
- 실제 모집이 여러 역할/회차로 나뉘면 일부 역할의 마감과 연구 전체의 종료를 구분해야 합니다.
- 원천 데이터는 작성·모집·협업 상태를 분리해 유지합니다. 이 열은 관리자에게 보여주는 요약이며 단일 DB 상태를 강제하는 계약이 아닙니다.

## 4. 후속 요청으로 추가한 네 상태

사용자가 추가 제안 상태도 우선 넣어 달라고 요청하여, 아래 네 상태를 목록 필터·상세 표시·가상 예시에 반영합니다.
일시 중지는 앞서 초기 제외를 추천했지만 이번 요청에 따라 포함합니다. 실제 업무 상태 전환 기능은 만들지 않습니다.

| 후보 | 필요한 이유 |
|---|---|
| 모집 취소 | 기한이 끝난 경우와 연구자가 모집을 철회한 경우를 구분 |
| 일시 중지 | 재개할 협업을 중단/완료와 구분. 기존 PRJ-01에도 있음 |
| 종료 확인 중 | 종료 요청은 했지만 상대 확인 전인 단계. 기존 ‘종료 대기’보다 행동이 분명함 |
| 중단 | 시작한 프로젝트가 목표를 마치지 못하고 끝난 경우를 정상 완료와 구분 |

모집 취소와 협업 중단은 발생 단계가 다릅니다. 회원 정지와도 자동 연동하지 않습니다.
일시 중지는 단순 지연과 구분합니다. 실제 기능 연결 시 참여자 합의·중지 사유·재개 예정일을 근거로 삼으며,
시작 전 데이터 준비 대기는 진행 예정으로 다룹니다. 이 정보의 저장·변경·이력 API는 이번 범위가 아닙니다.

## 5. 이번 구현의 동작

- 목록의 작성 상태 바로 다음에 진행 상태 배지를 표시하고 상세에서도 같은 표시 함수를 사용합니다.
- 작성 상태·진행 상태·검색어·기간을 함께 필터링할 수 있습니다. 초기화하면 진행 상태 조건도 제거합니다.
- 실데이터: 등록 연구는 연동 전, 임시저장은 해당 없음. 날짜나 개별 요청으로 상태를 추측하지 않습니다.
- 데모: 등록된 가상 연구에 아홉 진행 상태를 배정합니다. 임시저장에는 진행 상태 예시를 붙이지 않습니다.
- 구형 API에 `progress`가 없어도 모집 중으로 채우지 않고 동일하게 연동 전/해당 없음을 표시합니다.
- 서버 목록/상세 응답에 `progress: {code, note}`와 `progress_status` 조회 조건을 추가합니다.
- DB 스키마 변경·실제 회원/연구 상태 변경·원격 데이터 쓰기·자동 만료 작업은 없습니다.

학습 포인트: ‘글을 등록했다’와 ‘협업이 시작됐다’는 다른 사실입니다. 두 상태를 별도 필드로 두면
임시저장을 진행 중으로 세거나, 모집 마감을 프로젝트 완료로 착각하는 오류를 막을 수 있습니다.
