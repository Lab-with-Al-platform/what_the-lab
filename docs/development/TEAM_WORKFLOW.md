# 팀 Git/GitHub 작업 방식

## 1. `dev 폴더`를 만들지 않는 이유

`develop`은 여러 기능을 합쳐 확인하는 **Git 브랜치**입니다. 개발 환경은 각 팀원의 컴퓨터에서 앱을 실행하는 **환경**입니다. 파일을 모으는 `dev/` 폴더와는 역할이 다릅니다.

```text
main       안정적이고 시연 가능한 코드
  ↑
develop    팀 기능을 합쳐 통합 확인하는 코드
  ↑
feature/*  한 사람이 한 가지 기능을 작업하는 코드
```

## 2. 브랜치 규칙

### `main`

- 시연·배포 가능한 안정 상태만 둡니다.
- 직접 작업하지 않습니다.
- `develop`에서 충분히 검증한 변경만 PR로 합칩니다.
- 강제 push하지 않습니다.

### `develop`

- 기능 PR이 모이는 통합 브랜치입니다.
- 팀의 기본 작업 시작점입니다.
- 테스트가 깨진 상태를 오래 유지하지 않습니다.

### `feature/*`

- 한 가지 작은 목적만 작업합니다.
- 예: `feature/expert-list`, `feature/auth-login`, `feature/common-button`
- 작업이 끝나면 `develop`을 대상으로 PR을 만듭니다.

## 3. 역할과 1차 책임

| 담당 | 1차 책임 | 리뷰에서 확인할 내용 |
|---|---|---|
| 프로젝트 리드(사용자) | 통합, 메인, 인증, 브랜치 관리 | MVP 범위, API 계약, 충돌, 최종 통합 |
| 프론트엔드 경험자 | 공통 UI, 레이아웃, 디자인 시스템 | 재사용성, 반응형, 접근성, 화면 일관성 |
| 초보 팀원 | 전문가 목록·상세, 관련 샘플 데이터 | 작은 컴포넌트, 타입, 상태별 화면, 데이터 구조 |

인사이트는 프론트엔드 경험자의 미래 담당 후보이지만 현재 `MVP+`입니다. 팀이 범위를 바꾸기 전에는 MVP 기능보다 먼저 구현하지 않습니다.

> 2026-10-16 추가 기록: 사용자가 인사이트 정기 게시를 맡아 비활성 기본값의 첫 백엔드 개발을 진행합니다. 위 표는 최초 역할 배분 기록이며, 현재 인사이트의 허용 범위는 [D-23](../product/03_DECISION_LOG.md#d-23-인사이트-첫-백엔드와-공통-db)을 따릅니다. 다른 담당자의 역할은 이 변경에서 임의로 수정하지 않습니다.

## 4. 매일 작업 순서

### 4.1 최신 코드 받기

```powershell
git switch develop
git pull origin develop
```

### 4.2 기능 브랜치 만들기

```powershell
git switch -c feature/expert-list
```

브랜치 이름은 자신의 이름보다 기능을 설명하도록 만듭니다.

### 4.3 작은 단위로 저장하기

```powershell
git status
git add frontend
git commit -m "feat: 전문가 목록 카드 추가"
```

`git add .`를 습관적으로 사용하기 전에 `.env`, 생성 파일, 관계없는 변경이 포함되지 않았는지 `git status`로 확인합니다.

### 4.4 원격에 올리고 PR 만들기

```powershell
git push -u origin feature/expert-list
```

GitHub에서 `feature/expert-list` → `develop` Pull Request를 만듭니다. PR 템플릿의 테스트와 범위 항목을 채웁니다.

## 5. 리뷰와 병합

- 작성자는 먼저 자신의 변경을 다시 읽는 셀프 리뷰를 합니다.
- UI 변경은 데스크톱·모바일 캡처를 첨부합니다.
- API 변경은 요청·응답 예시와 권한 조건을 적습니다.
- DB 변경은 마이그레이션과 영향 범위를 설명합니다.
- 큰 PR 하나보다 검토 가능한 작은 PR 여러 개를 선호합니다.
- 리뷰 의견은 사람을 평가하는 말이 아니라 코드와 동작을 설명합니다.

## 6. `main` 반영

1. `develop`에서 MVP 흐름을 통합 검증합니다.
2. 프로젝트 리드가 `develop` → `main` PR을 만듭니다.
3. 변경 요약, 테스트 결과, 알려진 제한을 확인합니다.
4. 팀 합의 후 일반 병합합니다.
5. 충돌을 피하려고 원격 `main`을 강제로 덮어쓰지 않습니다.

## 7. 충돌이 생겼을 때

충돌은 두 사람이 같은 부분을 다르게 수정했다는 알림입니다. 오류나 잘못이 아닙니다.

1. 작업 중인 변경을 커밋합니다.
2. 원격 변경을 가져옵니다.
3. 충돌 표시의 양쪽 의도를 읽습니다.
4. 담당자와 필요한 결과를 합의합니다.
5. 앱과 테스트를 다시 확인한 뒤 해결 커밋을 만듭니다.

이해하지 못한 파일을 통째로 한쪽 버전으로 선택하지 않습니다.

## 8. 환경 파일

- `.env.example`: 필요한 변수 이름과 안전한 예시. Git에 포함
- `.env`: 각자의 실제 로컬 값. Git에서 제외
- 운영 비밀값: GitHub 또는 배포 서비스의 Secret 기능으로 관리

키가 노출되었다면 파일만 삭제하는 것으로 끝나지 않습니다. 해당 키를 즉시 폐기·재발급하고 Git 이력을 점검해야 합니다.
