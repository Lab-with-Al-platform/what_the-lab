# Cursor 화면 개선 수정 지시서

> 대상 프로젝트: SKN36 Research × AI Collaboration Platform\

> **기존 기획과 사용자 흐름을 유지하면서 UX/UI 완성도를 높이기 위한
> Cursor 실행 지시서**\

# 0. Cursor가 먼저 이해해야 할 제품 구조

이 서비스는 단순한 AI 전문가 목록이나 구인 사이트가 아니다.

핵심 흐름은 다음과 같다.

``` text
발견
  ↓
협업 요청 / 참여 신청
  ↓
검토·협의
  ↓
최종 선택
  ↓
프로젝트 확정
  ↓
마일스톤 기반 협업
  ↓
프로젝트 종료
  ↓
양방향 평가
  ↓
협업 이력 / Portfolio
```

두 개의 매칭 경로가 존재한다.

### 직접 요청형

``` text
연구자
  ↓
AI 전문가 탐색
  ↓
전문가 상세
  ↓
협업 요청
  ↓
전문가 검토 / 협의
  ↓
수락
  ↓
최종 확정
```

### 공개 모집형

``` text
연구자
  ↓
모집 프로젝트 등록
  ↓
AI 전문가가 프로젝트 탐색
  ↓
참여 신청
  ↓
연구자가 신청자 검토 / 협의
  ↓
최종 선택
```

두 경로는 최종 선택 이후 동일한 프로젝트 흐름으로 합쳐진다.

``` text
프로젝트 확정
  ↓
프로젝트 개요
  ↓
마일스톤 진행
  ↓
산출물 검토
  ↓
종료
  ↓
평가
```

# 1. 이번 수정의 핵심 목표

현재 화면에는 필요한 정보가 대부분 들어가 있지만 다음 문제가 있다.

1.  정보가 거의 같은 시각적 중요도로 나열되어 있다.
2.  일부 화면에 같은 의미의 CTA 또는 정보가 중복된다.
3.  입력 데이터의 성격과 실제 Input UI가 맞지 않는다.
4.  긴 설명도 한 줄 Input처럼 보이는 경우가 있다.
5.  목록과 상세 화면의 정보 밀도 차이가 충분하지 않다.
6.  상태와 사용자가 해야 할 다음 행동의 시각적 우선순위가 약하다.
7.  프로젝트 진행 화면에서 이 서비스의 핵심인 Milestone 관리가 충분히
    드러나지 않는다.
8.  카드, Form, Badge, Button, Section의 디자인 규칙이 화면마다 조금씩
    달라 보인다.
9.  전체적으로 기능 명세를 그대로 화면에 배치한 느낌이 강하다.

이번 수정 목표는 다음과 같다.

> 기능을 늘리는 것이 아니라 사용자가\
> **현재 상태 → 필요한 정보 → 다음 행동**을 빠르게 이해할 수 있도록
> 화면을 재정렬한다.

# 2. 절대 변경하지 말아야 할 사항

## 2.1 홈의 인사이트/블로그 위치

현재 팀 결정에 따라 홈 화면에서 **인사이트/블로그 콘텐츠가 상단에
위치하는 구조를 유지한다.**

Cursor는 다음을 하지 않는다.

-   인사이트를 홈 하단으로 이동
-   인사이트 영역 삭제
-   프로젝트 목록을 인사이트보다 위로 임의 이동
-   홈 전체 IA를 임의 변경

홈에서는 CTA 위계, 정렬, 간격, 카드 디자인 등 **디테일만 개선한다.**

------------------------------------------------------------------------

## 2.2 용어

반드시 다음 용어를 구분한다.

``` text
연구자 → AI 전문가 = 협업 요청
AI 전문가 → 공개 프로젝트 = 참여 신청
매칭 이후 = 프로젝트 확정
협업 진행 단위 = 마일스톤
완료 이후 = 양방향 평가
```

`협업 요청`과 `참여 신청`을 같은 객체나 같은 행동처럼 표현하지 않는다.

------------------------------------------------------------------------

## 2.3 상태 구분

다음 세 상태를 섞지 않는다.

### Availability

전문가가 새로운 협업을 받을 수 있는가?

예:

-   참여 가능
-   제한적 참여 가능
-   현재 어려움
-   날짜 협의

### Relationship

현재 사용자와 상대 사이의 관계 상태.

예:

-   요청 보냄
-   확인함
-   협의 중
-   수락
-   거절
-   참여 신청 검토 중
-   최종 선택
-   미선정

### Project Status

확정된 프로젝트의 진행 상태.

예:

-   시작 전
-   진행 중
-   일시 중지
-   종료 대기
-   완료

------------------------------------------------------------------------

# 3. 전체 UI 시스템 정리

화면별 수정 전에 공통 컴포넌트를 먼저 정리한다.

## 3.1 Page Container

모든 Desktop 화면에서 동일한 Content Width와 좌우 여백을 사용한다.

권장:

``` text
max-width: 1200~1280px
margin: 0 auto
```

Form 중심 화면은 너무 넓게 펼치지 않는다.

권장:

``` text
Form content: 720~840px
```

필요하면 우측 Summary Panel을 추가해 전체 1200px 정도로 구성한다.

------------------------------------------------------------------------

## 3.2 Vertical Spacing

임의의 간격을 반복하지 말고 일정한 spacing scale을 사용한다.

예:

``` text
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64
```

권장 사용:

-   Label ↔ Input: 8px
-   관련 Input 사이: 16px
-   Field Group 사이: 24px
-   Section 사이: 40\~48px
-   Page title ↔ 첫 Section: 32px

------------------------------------------------------------------------

## 3.3 정보 계층

한 화면에서 최소 다음 단계가 구분되어야 한다.

``` text
Page Title
  ↓
Page Description / Context
  ↓
Primary Action or Current Status
  ↓
Section Title
  ↓
Main Information
  ↓
Supporting Information
  ↓
Metadata
```

모든 텍스트를 비슷한 크기와 굵기로 표시하지 않는다.

------------------------------------------------------------------------

## 3.4 Button Hierarchy

한 화면에서 **Primary Button을 남발하지 않는다.**

### Primary

현재 화면에서 가장 중요한 다음 행동.

예:

-   모집 시작
-   협업 요청 보내기
-   참여 신청하기
-   최종 선택
-   검토 요청
-   평가 제출

### Secondary

보조 행동.

예:

-   미리보기
-   임시 저장
-   상세 보기

### Tertiary / Text

낮은 우선순위.

예:

-   취소
-   뒤로
-   저장 해제

Danger Action은 일반 Primary와 분리한다.

예:

-   프로젝트 종료
-   신청 취소
-   요청 철회

------------------------------------------------------------------------

## 3.5 Card

카드 안에 모든 정보를 넣지 않는다.

목록 카드는 다음 질문에 답하는 정보만 보여준다.

> 이 대상을 더 자세히 볼 가치가 있는가?

상세 화면은 다음 질문에 답한다.

> 실제로 협업 요청 또는 참여 신청을 할 것인가?

------------------------------------------------------------------------

## 3.6 Badge

Badge는 짧은 상태와 분류에만 사용한다.

예:

``` text
의료·바이오
모집 중
D-12
참여 가능
NDA 필요
외부 반출 불가
```

긴 설명을 Badge 안에 넣지 않는다.

색만으로 상태를 표현하지 말고 텍스트를 함께 표시한다.

------------------------------------------------------------------------

# 4. 입력 컴포넌트 규칙

현재 Form에서 모든 정보를 비슷한 Input으로 표현하지 않는다.

## Text Input

사용:

-   프로젝트명
-   짧은 한 줄 제목
-   URL
-   기관명

사용하지 않음:

-   연구 목적
-   요청 내용
-   기대 결과
-   관련 경험
-   지원 메시지

------------------------------------------------------------------------

## Textarea

사용:

-   연구 목적 / 배경
-   기대 결과
-   요청 내용
-   요청 이유
-   관련 경험
-   지원 메시지
-   역할 설명
-   검토 의견

최소 3\~5줄 높이를 제공한다.

------------------------------------------------------------------------

## Select

사용:

-   연구 분야
-   과업 유형
-   대표 협업 형태

옵션이 많으면 Searchable Select 사용.

------------------------------------------------------------------------

## Multi Select / Tag Input

사용:

-   필요한 AI 영역
-   기술 스택
-   필요 기술
-   연구 분야 경험
-   역할

선택 결과는 Chip 형태로 표시한다.

------------------------------------------------------------------------

## Date Picker / Date Range

사용:

-   시작일
-   종료일
-   희망 기간
-   참여 가능 시작일
-   응답 기한

날짜를 일반 Text Input으로 받지 않는다.

------------------------------------------------------------------------

## Number Input / Stepper

사용:

-   모집 인원
-   주당 예상 투입 시간

단위를 Input 안 또는 옆에 명확히 표시한다.

예:

``` text
[ 8 ] 시간 / 주
```

------------------------------------------------------------------------

## Radio / Segmented Control

하나만 선택하는 값.

예:

``` text
원격 / 오프라인 / 혼합
전체 공개 / 회원 공개 / 일부 공개 / 초대 전용 / 비공개
```

------------------------------------------------------------------------

## Checkbox

복수 조건.

예:

``` text
NDA 필요
IRB 관련
기관 승인 필요
외부 반출 불가
```

------------------------------------------------------------------------

# 6. P-03 과업 템플릿 선택 --- 추가/분리

현재 프로젝트 등록 화면 앞에 별도 Step으로 구성한다.

## 목적

AI 용어에 익숙하지 않은 연구자가 빈 Form에서 시작하지 않게 한다.

## Layout

``` text
프로젝트 등록
AI 협업에서 어떤 도움이 필요한가요?

[ 데이터 전처리·QC ]
데이터 정리, 결측치, 품질 검토가 필요한 경우

[ 데이터 분석 ]
보유 데이터를 분석하고 인사이트를 얻고 싶은 경우

[ 논문 구현·재현 ]
기존 논문이나 모델을 재현하고 싶은 경우

[ Baseline 구축 ]
연구 아이디어의 초기 모델을 만들고 싶은 경우

[ 모델 개발·튜닝 ]
모델 성능 개선이 필요한 경우

[ PoC ]
아이디어의 기술적 가능성을 검증하고 싶은 경우

[ 단기 자문 ]
AI 적용 방향에 대한 전문가 의견이 필요한 경우

[ 직접 작성 ]
```

카드는 2\~3열 Grid로 구성한다.

선택 시:

-   선택 상태 명확히 표시
-   해당 템플릿 설명
-   준비하면 좋은 정보
-   예상 결과물

을 짧게 보여준다.

Primary CTA:

``` text
이 템플릿으로 시작
```

# 7. P-04 프로젝트 등록 --- 전면 Form 개선

현재 긴 단일 Form을 Step Form으로 변경한다.

## Step Navigation

``` text
1 연구 정보
2 AI 협업
3 데이터·보안
4 확인
```

현재 Step을 시각적으로 명확히 표시한다.

------------------------------------------------------------------------

## Step 1. 연구 정보

### 프로젝트명

`Text Input`

### 연구 분야

`Searchable Select`

### 연구 목적 / 배경

`Textarea`

최소 4\~5줄.

### 기대 결과

`Textarea`

예시 Helper Text 제공:

``` text
예: 모델 성능 검증, 분석 보고서, 논문 실험 결과 등
```

------------------------------------------------------------------------

## Step 2. AI 협업

### 필요한 AI 영역

`Multi Select`

### 필요 기술

`Tag Input`

### 기대 역할

`Multi Select + 기타 입력`

### 협업 형태

`Radio Card`

예:

``` text
공동 연구
기술 자문
구현 지원
분석 지원
```

### 참여 방식

`Segmented`

``` text
원격 / 오프라인 / 혼합
```

### 모집 인원

`Number Stepper`

### 협업 기간

`Date Range Picker`

### 예상 투입량

``` text
[ 8 ] 시간 / 주
```

### 보상/성과 형태

선택 가능한 구조로 표현.

예:

``` text
□ 금전 보상
□ 공동저자 협의
□ 공동 연구
□ 프로젝트 경험/포트폴리오 공개 협의
□ 기타
```

플랫폼이 결제나 계약을 중개한다는 인상을 주지 않는다.

------------------------------------------------------------------------

## Step 3. 데이터·보안

별도 Section/Card로 묶는다.

### Data Readiness

Radio Card 또는 Step Selector:

``` text
데이터 없음
수집 예정
일부 확보
분석 가능 상태
```

### 데이터 유형

Select/Multi Select.

### 데이터 규모

Text 또는 Number + Unit.

### 접근 방식

Radio:

``` text
즉시 제공 가능
승인 후 제공
기관 환경에서만 접근
제공 불가 / 협의 필요
```

### 보안 조건

Checkbox:

``` text
□ 외부 반출 불가
□ NDA 필요
□ IRB 관련
□ 기관 승인 필요
□ 민감정보 포함
```

### 공개 범위

Radio Card:

``` text
전체 공개
회원 공개
일부 정보 공개
초대 전용
비공개
```

각 옵션 아래 한 줄 설명 제공.

------------------------------------------------------------------------

## Step 4. 확인

Form을 다시 Input으로 보여주지 말고 **읽기 좋은 Summary**로 보여준다.

섹션:

``` text
연구 정보
AI 협업 조건
기간 및 투입
데이터 및 보안
공개 범위
```

각 Section에 `수정` 버튼 제공.

하단:

Secondary:

``` text
임시 저장
미리보기
```

Primary:

``` text
모집 시작
```

# 8. P-01 프로젝트 찾기

## 목표

카드끼리 빠르게 비교할 수 있어야 한다.

## Filter

상단 또는 좌측 Filter 영역:

``` text
연구 분야
과업 유형
필요 기술
기간
참여 방식
보상 형태
Data Readiness
```

모바일에서는 Filter Drawer.

## Project Card

권장 구조:


# 23. H-01 홈

## 중요

**인사이트 / 블로그가 현재 상단에 있는 구조는 유지한다.**

Section 순서를 임의로 바꾸지 않는다.

현재 구조를 유지하면서 다음만 개선한다.

### CTA Hierarchy

현재:

``` text
프로젝트 등록하기
AI 전문가 찾기
프로젝트 찾기
```

세 버튼이 모두 같은 중요도로 보이지 않게 한다.

로그인 역할에 따라 Primary를 변경할 수 있다.

연구자:

``` text
Primary: 프로젝트 등록하기
Secondary: AI 전문가 찾기
Tertiary: 프로젝트 찾기
```

AI 전문가:

``` text
Primary: 프로젝트 찾기
Secondary: 내 협업
```

Guest:

서비스 이해를 방해하지 않는 수준에서 CTA를 제공한다.

### 관심 분야

Chip/Filter의 선택 상태를 명확히 한다.

선택 시 아래 콘텐츠가 변경된다는 관계가 시각적으로 이해되어야 한다.

### Blog / Insight Card

제목, 분야, 날짜, 작성자, 요약의 Typography hierarchy를 정리한다.

### 프로젝트 / 전문가 Section

홈에서는 전체 정보를 보여주지 않는다.

목록 화면으로 이동하게 만드는 Preview 역할만 한다.

# 29. 각 화면 완료 조건

화면을 수정한 뒤 다음을 스스로 확인한다.

### Layout

-   좌우 정렬이 일관적인가?
-   Section 간 간격이 일정한가?
-   같은 역할의 Card 높이와 구조가 일관적인가?
-   Form이 불필요하게 전체 폭으로 늘어나지 않았는가?

### CTA

-   Primary CTA가 한눈에 보이는가?
-   같은 기능의 버튼이 두 번 반복되지 않는가?
-   Secondary Action이 Primary보다 강하게 보이지 않는가?
-   현재 상태에서 불가능한 Action의 이유가 설명되는가?

### Form

-   긴 내용이 Textarea인가?
-   날짜가 Date Picker인가?
-   복수 선택은 Multi Select인가?
-   숫자는 Number Input인가?
-   단위가 명확한가?
-   관련 Field가 Section으로 묶였는가?

### Flow

-   사용자가 이 화면에 왜 들어왔는지 알 수 있는가?
-   현재 상태가 무엇인지 알 수 있는가?
-   다음 행동이 무엇인지 알 수 있는가?
-   다음 화면으로 자연스럽게 이어지는가?

### Status

-   Availability / Relationship / Project Status가 섞이지 않는가?
-   색만으로 상태를 표현하지 않는가?

### Content

-   목록과 상세에 같은 양의 정보를 반복하지 않는가?
-   동일 정보가 한 화면에 중복되지 않는가?
-   프로젝트 모집 정보와 확정 프로젝트 정보가 구분되는가?

# 30. 최종 UX 검수 시나리오

수정 완료 후 개별 화면만 확인하지 말고 아래 시나리오를 처음부터 끝까지
실행한다.

## Scenario A --- 공개 모집

``` text
연구자 로그인
→ 프로젝트 등록
→ 과업 템플릿 선택
→ 모집 프로젝트 공개

AI 전문가 로그인
→ 프로젝트 찾기
→ 프로젝트 상세
→ 참여 신청

연구자
→ 신청 도착 알림
→ 신청자 검토
→ 협의
→ 최종 선택
→ 프로젝트 확정

양쪽 사용자
→ 프로젝트 개요
→ 마일스톤 진행
→ 산출물 검토
→ 프로젝트 종료
→ 양방향 평가
```

## Scenario B --- 직접 요청

``` text
연구자 로그인
→ 프로젝트 준비
→ AI 전문가 찾기
→ 전문가 상세
→ 협업 요청

AI 전문가
→ 요청 알림
→ 요청 검토
→ 협의
→ 수락

연구자
→ 최종 확정
→ 프로젝트 생성

양쪽 사용자
→ 마일스톤
→ 종료
→ 평가
```

두 시나리오가 `프로젝트 확정` 이후 동일한 프로젝트 UX로 합쳐져야 한다.

# 31. Cursor에게 최종 요청

현재 화면의 색상이나 스타일을 전부 새로 만드는 것이 목적이 아니다.

이번 수정의 우선순위는 다음과 같다.

``` text
1. 사용자 흐름
2. 기능 중복 제거
3. 입력 방식 개선
4. CTA 위계
5. 정보 구조
6. 정렬 / 간격
7. 시각적 완성도
```

기존 디자인 언어는 최대한 유지하되, 정보가 단순히 나열된 느낌을 줄이고
**사용자가 현재 상태와 다음 행동을 즉시 이해할 수 있는 제품 UI**로
개선한다.

특히 다음 세 영역은 반드시 개선한다.

``` text
프로젝트 등록
→ 긴 Form 나열이 아닌 단계형 Form

협업 요청 / 참여 신청
→ 데이터 성격에 맞는 Input Component

프로젝트 진행
→ 일정 목록이 아닌 Milestone 중심 Dashboard
```

홈의 인사이트/블로그 상단 배치는 현재 팀 결정이므로 유지한다.

작업 중 기존 요구사항과 충돌하거나 화면 삭제/통합이 필요하다고 판단되는
경우 **임의로 변경하지 말고 변경 이유와 대안을 먼저 제시한다.**
