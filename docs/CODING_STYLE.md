# LabBridge — 팀 공통 코딩 스타일

> 버전: 1.0 (팀 검토용)  
> 기준 문서: `peter_coding_style_v1.md` (강사님 코드 관찰을 바탕으로 작성된 개인 스타일)  
> 적용 범위: `frontend/`(Next.js·React·TypeScript), `backend/`(Python·FastAPI), `data/`, `ai/`, 테스트 코드  
> 문서 소유: 개발팀 전체. 변경은 PR에서 검토한다.

## 1. 한 문장 원칙

**짧은 코드보다 흐름이 보이는 코드, 복잡한 설계보다 지금 필요한 구조, AI가 만든 코드라도 담당자가 설명할 수 있는 코드.**

이 문서는 특정 팀원의 취향을 강제하기 위한 것이 아니라, 개발 경험이 서로 다른 3명이 GPT·Codex를 활용해 **읽고 수정하고 검증할 수 있는 코드**를 만들기 위한 공통 기준이다.

## 2. 우선순위

규칙이 충돌할 경우 다음 순서를 따른다.

1. **보안·데이터 무결성·인증/인가** 등 필수 안전성
2. 사용자 요구사항과 확정된 MVP 범위 (`docs/MVP_SCOPE.md`)
3. 프로젝트의 기존 구조·공통 인터페이스·공통 UI (`docs/STYLE_GUIDE.md`, API 계약)
4. 가독성·단순성·일관성 (이 문서)
5. 개인 취향이나 코드 길이

단순하게 만든다는 이유로 권한 검증, 입력 검증, 오류 처리, 테스트를 제거하지 않는다.

## 3. 기본 원칙 (모든 언어 공통)

- **위에서 아래로 읽히는 흐름:** 입력 → 처리 → 결과가 보이도록 작성한다.
- **하나의 명확한 책임:** 함수·컴포넌트·모듈의 이름과 책임이 일치한다.
- **필요한 만큼만 분리:** 반복, 독립된 책임, 재사용, 테스트 용이성, 팀 간 변경 충돌 감소가 이유일 때 분리한다.
- **의미 있는 변수:** 한 줄 표현보다 이해가 쉬우면 중간 변수를 둔다.
- **과도한 추상화 금지:** 아직 필요 없는 wrapper, factory, repository, 범용 설정 계층을 선제적으로 만들지 않는다.
- **주석은 이유를 설명:** 코드가 *무엇을* 하는지 이름으로 알 수 있다면 주석을 중복하지 않는다. *왜* 이렇게 했는지, 비즈니스 제약이나 예외적인 판단을 기록한다.
- **기존 구조 재사용:** 동일 기능의 컴포넌트·유틸·타입을 새로 만들기 전에 기존 것을 확인한다.
- **현재 범위에 집중:** 계약, 정산, 프로젝트 관리 등 확정되지 않은 기능을 미래 대비용으로 만들지 않는다.
- **설명 가능한 코드:** PR 작성자는 주요 데이터 흐름과 변경 이유를 설명할 수 있어야 한다.

### 함수 분리의 실무 기준

'반복되기 전에는 함수를 만들지 않는다'를 기계적으로 적용하지 않는다. 재사용되지 않더라도 인증 검증, 외부 API 호출, DB 접근, UI 렌더링처럼 **책임과 실패 양상이 다른 부분**은 분리할 수 있다. 반대로 단 한 줄을 감싸는 의미 없는 함수는 만들지 않는다.

### 파일 분리의 실무 기준

파일이 커졌다는 이유만이 아니라 **담당 역할, 변경 빈도, 테스트 경계, 프론트/백엔드 책임**을 고려한다. 무조건 파일을 많이 만들거나 하나로 합치지 않는다.

## 4. TypeScript / React / Next.js

### 4.1 화면 구현

- 페이지(`app/`)는 **라우팅과 페이지 조립**, 재사용 UI는 `components/`, API 호출은 `lib/` 또는 합의된 서비스 계층에서 처리한다.
- Figma 및 `STYLE_GUIDE.md`의 공통 디자인 토큰과 컴포넌트를 우선 사용한다.
- 같은 버튼·카드·배지를 화면마다 복사하지 않는다.
- 컴포넌트는 **표시 책임과 데이터 로딩/비즈니스 처리**가 혼잡해질 때 분리한다. 모든 작은 JSX 조각을 컴포넌트로 만들 필요는 없다.
- 필요한 상태만 유지한다. 계산 가능한 값은 중복 상태로 저장하지 않는다.
- `useEffect`를 무분별하게 사용하지 않고, 데이터 흐름을 명확히 한다.
- 클라이언트 컴포넌트(`'use client'`)는 실제 상호작용이 필요한 범위에만 사용한다.
- 링크는 탐색에, 버튼은 동작에 사용한다.

### 4.2 타입과 데이터

- `any` 사용을 기본적으로 피한다. 불가피할 때는 이유를 주석이나 PR에 기록한다.
- 화면 데이터 타입과 API 응답 타입을 일관되게 관리한다.
- API·폼 등 외부에서 들어오는 데이터는 타입 선언만 믿지 말고 런타임 검증이 필요한 경계에서 확인한다.
- 로딩·빈 결과·오류 상태를 정상 화면과 함께 설계한다.
- Mock Data와 실제 API 응답의 필드 구조를 맞추고, 임시 데이터임을 명시한다.

### 4.3 간단한 예시

```tsx
// 이해하기 쉬운 중간 변수와 명확한 UI 상태를 사용한다.
type Expert = { id: string; name: string; skills: string[] };

function ExpertList({ experts }: { experts: Expert[] }) {
  const hasExperts = experts.length > 0;

  if (!hasExperts) {
    return <p>조건에 맞는 전문가가 없습니다.</p>;
  }

  return (
    <ul>
      {experts.map((expert) => (
        <li key={expert.id}>{expert.name}</li>
      ))}
    </ul>
  );
}
```

## 5. Python / FastAPI

- 함수명은 `get_expert()`, `list_cases()`처럼 역할을 나타낸다.
- 라우터는 HTTP 요청·응답과 인증 경계를, 서비스는 핵심 비즈니스 로직을 담당한다. **단순 CRUD까지 무조건 여러 계층으로 쪼개지는 않는다.**
- 입력·출력 스키마는 Pydantic 등 합의된 방식으로 명확하게 관리한다.
- DB 접근, 외부 호출, 파일 처리의 오류는 예상 가능한 실패 유형을 구분해 처리한다.
- 광범위한 `except Exception: pass`로 오류를 숨기지 않는다.
- 비밀키·비밀번호·토큰·개인정보를 로그에 남기지 않는다.
- 학습/실험 코드는 `ai/`, 실제 서비스 추론 코드는 `backend/`의 합의된 위치에 둔다. **MVP에 추론 기능이 필요하지 않으면 구현하지 않는다.**

```python
# 입력 → 조회 → 결과 변환의 흐름이 보이도록 작성한다.
def list_expert_names(experts: list[dict]) -> list[str]:
    names = []

    for expert in experts:
        if not expert.get("is_public", False):
            continue

        names.append(expert["name"])

    return names
```

> 예시는 스타일 설명용이다. 실제 서비스에서는 dict 구조·권한·DB 접근 방식을 API 계약에 맞게 결정한다.

## 6. 반드시 지킬 안전장치

- **인증과 인가를 구분:** 로그인 여부뿐 아니라 해당 데이터에 접근·수정할 권한을 서버에서 확인한다.
- **입력 검증:** 프론트엔드 편의 검증과 별개로 서버에서 유효성을 검사한다.
- **비밀정보:** `.env` 및 비밀 저장소를 사용하고 `.env` 실파일·키·토큰을 커밋하지 않는다. `.env.example`만 공유한다.
- **DB 변경:** 스키마 변경은 합의된 마이그레이션 절차로 관리하고 기존 데이터를 임의 삭제하지 않는다.
- **예외처리:** 네트워크 실패, 인증 만료, 잘못된 입력, DB 오류처럼 예측 가능한 실패를 처리한다. 불필요한 try/except 남발은 피한다.
- **외부 콘텐츠:** 논문·연구사례의 출처를 보존하고, HTML 렌더링 시 XSS 등 입력 위험을 고려한다.
- **테스트:** 주요 사용자 흐름, 데이터 변환, 권한 검증 등 실패 비용이 큰 부분을 우선 검증한다.

## 7. Git / PR 작업 원칙

- 작업 전 최신 `develop` 및 관련 문서를 확인한다.
- `feature/...` 브랜치에서 작게 작업하고 PR로 `develop`에 병합한다. `main`에 직접 푸시하지 않는다.
- 다른 담당자의 파일과 공통 컴포넌트를 바꿀 때는 PR에 영향을 명시한다.
- 의존성을 추가할 때는 필요성과 대안을 PR에 적는다.
- 포맷팅·리네이밍만으로 대규모 변경을 만들지 않는다.
- PR에는 **무엇을 바꿨는지 / 왜 바꿨는지 / 어떻게 테스트했는지 / 스크린샷(화면 작업 시)**를 남긴다.

## 8. GPT / Codex에 적용할 규칙

AI 코딩 도구에는 다음 순서로 작업하도록 요청한다.

1. 관련 파일과 `AGENTS.md`, `docs/MVP_SCOPE.md`, `docs/STYLE_GUIDE.md`, 이 문서를 먼저 읽는다.
2. 기존 구현·컴포넌트·타입을 조사한다.
3. 변경 범위를 짧게 설명하고 **필요한 파일만** 수정한다.
4. 먼저 동작하는 단순한 구현을 만든다.
5. 인증·보안·검증·오류 처리 등 필수 안전장치를 포함한다.
6. 린트·타입 검사·테스트·빌드를 가능한 범위에서 실행한다.
7. 변경 파일, 핵심 동작, 테스트 결과, 남은 위험을 요약한다.
8. 불확실한 요구사항은 임의로 확정하지 않고 질문하거나 TODO/결정 대기 사항으로 기록한다.

### Codex용 짧은 지시문

```text
이 저장소의 AGENTS.md와 docs/CODING_STYLE.md를 따르세요.
현재 요구사항에 필요한 가장 단순한 구현을 우선하고, 기존 구조와 공통 UI를 재사용하세요.
과도한 추상화·미래 기능 선구현은 피하되, 인증/인가·입력 검증·오류 처리·보안은 생략하지 마세요.
변경 전에 관련 파일을 확인하고, 변경 후 테스트 결과와 주요 코드 흐름을 설명하세요.
확정되지 않은 디자인이나 요구사항은 임의로 결정하지 마세요.
```

## 9. 코드 리뷰 체크리스트

- [ ] 담당자가 핵심 처리 흐름을 설명할 수 있다.
- [ ] 함수·컴포넌트의 책임이 명확하다.
- [ ] 불필요한 파일·추상화·미사용 코드가 없다.
- [ ] 기존 공통 컴포넌트와 API 계약을 재사용한다.
- [ ] 외부 입력과 권한을 필요한 경계에서 검증한다.
- [ ] 비밀정보·민감정보가 커밋/로그에 노출되지 않는다.
- [ ] 로딩·빈 상태·오류 등 사용자 상태를 고려했다.
- [ ] 관련 테스트/타입 검사/빌드 결과를 PR에 기록했다.
- [ ] MVP 범위 밖 기능을 임의로 추가하지 않았다.

## 10. 문서 변경 원칙

- 원본 `peter_coding_style_v1.md`는 **개인 학습·강사님 스타일 참고 원본**으로 보존한다.
- 이 문서는 팀 웹 개발에 맞게 보완한 **공통 규칙**이다.
- 팀원이 더 좋은 구현 근거를 제시하면 PR로 변경할 수 있다. 스타일 준수 자체가 목표가 아니라 이해 가능한 안정적 제품 개발이 목표다.
