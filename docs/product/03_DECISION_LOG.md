### 해석 규칙

1. S1과 충돌하는 S3·S4 제안은 현재 제품 결정으로 채택하지 않는다.
2. 좋은 문제 제기와 제안된 해결책을 분리해서 본다. 예를 들어 “매칭 후 이탈” 문제는 채택하지만 “계약·정산으로 Lock-in”은 Later로 둔다.
3. 외부 시장 수치와 우선 도메인은 업로드 자료의 주장으로만 기록하고, 원문 재검증 전에는 확정 근거로 사용하지 않는다.
4. 결정은 고정된 진리가 아니다. 각 항목의 재검토 조건이 충족되면 다시 논의한다.

## D-01. 비대칭 양방향 매칭

| 항목 | 내용 |
|---|---|
| 검토안 A | 연구자만 AI 전문가에게 협업 요청 |
| 검토안 B | 양쪽이 서로에게 동일한 형식으로 요청 |
| 검토안 C | 연구자는 전문가에게 `협업 요청`, 전문가는 공개 프로젝트에 `참여 신청` |
| 출처·피드백 | S4의 초기 단방향 제안, S2의 공개 모집형+직접 매칭형, S1의 최신 합의 |
| 최종 결정 | **검토안 C: 비대칭 양방향 매칭** |
| 이유 | AI를 잘 아는 연구자는 직접 전문가를 고를 수 있다. AI를 잘 모르는 연구자는 프로젝트를 공개하고 지원자를 비교하는 편이 쉽다. 전문가는 요청만 기다리지 않고 자신의 조건에 맞는 프로젝트를 찾을 수 있다. 두 방향의 의도와 상태가 다르므로 같은 객체로 합치지 않는다. |
| 현재 단계 | MVP |
| 재검토 조건 | 한쪽 경로의 사용률이 지나치게 낮거나, 운영 비용이 높거나, 사용자 인터뷰에서 두 용어가 지속적으로 혼동될 때 |
| 화면·데이터 영향 | `CollaborationRequest`와 `ProjectApplication`을 분리. M-01, M-02, W-02에서 상태와 CTA를 다르게 설계 |

## D-02. 제품의 중심 단위

| 항목 | 내용 |
|---|---|
| 검토안 A | 연구실 중심 커뮤니티 |
| 검토안 B | AI 전문가 주소록·구인 목록 |
| 검토안 C | 연구 프로젝트 중심 협업 플랫폼 |
| 출처·피드백 | S4의 초기 연구실 타깃, S2의 Collaboration Lifecycle, S1의 프로젝트 중심 합의 |
| 최종 결정 | **제품 구조는 연구 프로젝트 중심** |
| 이유 | 같은 연구실에서도 과제마다 필요한 기술·기간·데이터·보안이 다르다. 매칭, 역할, 마일스톤, 평가, Portfolio를 프로젝트에 묶어야 이력이 검증 가능하다. 초기 마케팅 타깃은 연구실일 수 있지만 데이터 구조를 연구실에 고정하지 않는다. |
| 현재 단계 | MVP |
| 재검토 조건 | 초기 사용자에게 프로젝트 생성 비용이 너무 크거나, 자문처럼 프로젝트 정의가 어려운 사례가 다수를 차지할 때 |
| 화면·데이터 영향 | 모든 요청·신청은 프로젝트를 참조. 간단 자문용 최소 프로젝트 템플릿 제공 |
| 상태 | 확정 |

| 최종 결정 | **초기 획득은 AI 도입이 필요한 대학 연구자·연구팀에 집중하고, 제품 구조는 연구기관·기업 프로젝트도 수용 가능하게 설계** |
| 이유 | 팀 프로젝트 범위를 좁히면서도 향후 확장을 막지 않는다. 기업 연구소의 수요와 행정은 별도 검증이 필요하므로 현재 사용자 요구에 섞지 않는다. |
| 현재 단계 | 초기 타깃은 MVP, 기업 확장은 Later |
| 재검토 조건 | 10~15건 이상의 인터뷰에서 특정 연구 도메인 또는 기업 연구소 수요가 반복되고, 파일럿 파트너가 확보될 때 |

## D-07. 평가 온도와 양방향 평가

| 항목 | 내용 |
|---|---|
| 검토안 A | 전문가만 온도 형태로 누적 평가 |
| 검토안 B | 전문가만 별점 평가 |
| 검토안 C | 완료 프로젝트에 묶인 양방향 다항목 평가 |
| 출처·피드백 | S4의 평가 온도 아이디어와 개선 의견, S2의 평가 맥락·표본 수 원칙, S1의 양방향 평가 합의 |
| 최종 결정 | **평가 온도는 사용하지 않고, 연구자와 전문가가 서로 평가** |
| 이유 | 온도는 의미가 모호하고 연구 협업 서비스의 신뢰감이 약하다. 전문가도 요구사항 명확성, 소통, 약속 준수 등을 기준으로 연구자를 판단해야 한다. 평가 점수만 표시하지 않고 표본 수와 완료 프로젝트 수를 함께 보여준다. |
| 현재 단계 | MVP |
| 재검토 조건 | 평가 회수율이 낮거나 보복 평가가 발생하거나, 공개 평가가 참여를 위축시킬 때 |
| 화면·데이터 영향 | 프로젝트 완료 사용자만 평가 가능. 상호 제출 후 또는 기한 종료 후 공개. 신고·비공개 정책 필요 |

| 검토안 B | 보상 형태는 표시하되 결제·계약은 당사자 협의 |
| 검토안 C | 플랫폼이 결제·에스크로·계약까지 중개 |
| 출처·피드백 | S4의 계약·대금 중개 제외 결정, S2의 보상 형태 표시, S3의 연구비 집행 제안 |
| 최종 결정 | **프로젝트에서 보상 형태를 명확히 표시하지만 MVP에서 거래를 중개하지 않음** |
