# SKN36 Research × AI Collaboration Platform 화면 가이드

> 문서 목적: 화면 담당자가 바로 Figma의 정보 구조, 사용자 흐름, 화면 상태를 설계할 수 있도록 현재 팀 합의를 화면 단위로 풀어쓴다.  
> 기준일: 2026-10-01  
> 적용 원칙: 최신 팀 합의가 최우선이며, 강사·시니어 개발자 의견과 시장조사는 참고 근거로 사용한다.

---

## 1. 제품을 한 문장으로 이해하기

연구 프로젝트와 AI 전문가가 서로를 발견하고, 두 가지 경로로 매칭된 뒤, 실제 연구 협업을 끝내고 평가와 이력을 남길 때까지 관리하는 플랫폼이다.

```text
발견 → 요청 또는 신청 → 검토·협의 → 최종 선택 → 프로젝트 확정
     → 마일스톤 협업 → 종료 → 양방향 평가 → 포트폴리오 → 다음 협업
```

화면 설계의 기준은 “사람 목록을 보여주는가?”가 아니라 “사용자가 다음 협업 행동을 분명히 알 수 있는가?”이다.

---

## 2. 범위 표시 규칙

| 표시 | 의미 | 화면 설계 방식 |
|---|---|---|
| `MVP` | 핵심 가설 검증에 반드시 필요 | 실제 사용자 흐름과 상태를 모두 설계 |
| `MVP+` | 매칭 품질·신뢰·재사용을 높임 | MVP 화면에서 확장 가능한 자리와 진입점 확보 |
| `Later` | 충분한 데이터·법률 검토·운영 역량 이후 | 메뉴를 미리 노출하지 않고 개념만 보존 |
| `Hypothesis` | 인터뷰와 사용 데이터로 검증 전 | 확정 기능처럼 표현하지 않음 |

### MVP의 검증 질문

> 연구자와 AI 전문가가 플랫폼에서 서로를 발견하고, 실제 프로젝트를 시작하여, 협업을 끝낼 수 있는가?

따라서 MVP의 범위는 검색에서 끝나지 않는다. `요청/신청 → 선택 → 프로젝트 → 마일스톤 → 종료 → 평가`가 한 번에 이어져야 한다.

## 3. 사용자와 권한

| 역할 | 핵심 목적 | 대표 행동 |
|---|---|---|
| Guest | 서비스와 공개 프로젝트를 이해 | 둘러보기, 로그인/가입 |
| Researcher | 연구에 필요한 AI 협업자를 확보 | 프로젝트 등록, 전문가 요청, 신청자 선택, 프로젝트 관리 |
| AI Expert | 자신의 역량에 맞는 연구 프로젝트 참여 | 프로젝트 탐색, 참여 신청, 요청 검토, 마일스톤 수행, 포트폴리오 축적 |
| Platform Admin | 안전하고 일관된 운영 | 사용자·프로젝트·신고·태그·평가 관리 |
| Organization Admin | 기관 단위 운영 | `Later`에서 구성원·기관 프로젝트 관리 |

한 계정이 연구자와 AI 전문가 역할을 함께 가질 수 있도록 화면에서는 현재 역할을 분명히 표시한다. 역할 전환은 계정 자체를 바꾸는 것이 아니라 같은 사용자의 보기와 행동 권한을 바꾸는 개념이다.

## 4. 전역 정보 구조

### 4.1 비로그인

```text
홈
협업 찾기
 ├─ 프로젝트 찾기
 └─ AI 전문가 찾기
인사이트
서비스 소개
로그인 / 회원가입
```

### 4.2 로그인

```text
홈
협업 찾기
 ├─ 프로젝트 찾기
 └─ AI 전문가 찾기
내 협업 공간
 ├─ 대시보드
 ├─ 요청·신청 관리
 ├─ 프로젝트
 ├─ 일정
 ├─ 저장
 └─ 평가
인사이트
알림
프로필
```

상위 메뉴는 `내 프로젝트`보다 `내 협업 공간`을 사용한다. 사용자는 프로젝트 외에도 요청, 신청, 일정, 저장, 평가를 관리하기 때문이다.

## 5. 공통 UI 원칙

### 5.1 목록과 상세의 역할 분리

- 목록 카드는 비교와 선택에 필요한 최소 정보만 보여준다.
- 상세 화면은 최종 판단에 필요한 맥락과 조건을 보여준다.
- 카드에 긴 설명, 전체 기술 스택, 모든 보안 조건을 한꺼번에 넣지 않는다.

### 5.2 서로 다른 세 상태를 섞지 않기

| 상태 | 답하는 질문 | 예시 |
|---|---|---|
| Availability | 전문가가 새 협업을 받을 수 있는가? | 바로 가능, 날짜 협의, 현재 어려움 |
| Relationship | 나와 이 대상 사이에 어떤 요청이 있는가? | 요청 보냄, 신청 검토 중, 수락 |
| Project Status | 확정된 프로젝트가 어디까지 왔는가? | 예정, 진행 중, 종료 대기, 완료 |

`프로젝트 1건 진행 중`이라는 이유만으로 `요청 불가`로 처리하지 않는다. 실제 가용 시간과 참여 가능일을 별도로 본다.

### 5.3 상태는 색만으로 전달하지 않기

색상과 함께 상태명, 아이콘 또는 짧은 설명을 사용한다. 예: 주황색 점만 표시하지 말고 `협의 중`을 함께 쓴다.

### 5.4 다음 행동이 하나 이상 보여야 함

모든 상세·관리 화면은 다음 단계의 CTA를 분명히 보여준다. 권한이나 상태 때문에 행동할 수 없다면 버튼을 숨기기보다 비활성 이유를 설명한다.

### 5.5 연구 보안은 공개 정보와 상세 정보를 분리

프로젝트 제목까지 숨겨야 하는 경우를 고려한다. `일부 정보 공개`에서는 목록 카드에 요약 정보만 표시하고, 상세 연구 내용·데이터 설명·기관명은 승인 또는 초대 이후 공개할 수 있다.

### 5.6 용어 통일

- 연구자에서 전문가로: `협업 요청`
- 전문가에서 공개 프로젝트로: `참여 신청`
- 두 경로가 합쳐지는 지점: `프로젝트 확정`
- 협업 중 관리 단위: `마일스톤`
- 완료 후 상호 피드백: `양방향 평가`

## 7. 화면 상세 정의

## H-01 홈

| 항목 | 정의 |
|---|---|
| 목적 | 플랫폼이 연구 콘텐츠 포털이 아니라 연구 프로젝트와 AI 전문가를 연결하는 서비스임을 첫 화면에서 이해시킨다. |
| 사용자 | Guest, Researcher, AI Expert |
| 진입점 | 서비스 URL, 검색 결과, 공유 링크 |
| 주요 CTA | `프로젝트 등록하기`, `AI 전문가 찾기`, `프로젝트 찾기` |
| 필수 정보 | 한 문장 가치 제안, 두 사용자별 시작점, 모집 중 프로젝트 일부, 협업 가능한 전문가 일부, 작동 방식 |
| 상태 | 비로그인, 연구자 로그인, 전문가 로그인에 따라 1순위 CTA 변경 |
| 예외 | 공개 가능한 프로젝트·전문가가 없으면 빈 목록 대신 작동 방식과 가입 CTA 표시 |
| 다음 화면 | P-01, P-03, E-01, AUTH-01 |
| 단계 | MVP |

홈에서 블로그를 주인공으로 만들지 않는다. 인사이트는 하단 또는 별도 메뉴에서 보조 역할을 맡는다.

## 10. 빈 화면·오류·권한 예외 공통 규칙

- 검색 결과가 없으면 필터 초기화와 조건 완화 예시를 함께 제공한다.
- 신규 사용자의 빈 대시보드는 기능 목록보다 첫 행동 하나를 안내한다.
- 비공개 정보에 접근하면 단순 404 대신 공개 범위와 요청 가능한 행동을 설명한다.
- 마감·만료·상태 변경이 동시에 일어나면 서버의 최종 상태를 기준으로 하고, 사용자가 입력한 초안은 보존한다.
- 네트워크 오류 뒤 재시도할 때 요청이나 신청이 중복 생성되지 않게 한다.
- 탈퇴·정지 사용자가 포함된 완료 프로젝트의 이력은 운영 정책에 따라 보존하되 공개 개인정보는 최소화한다.
- 평가가 한 건도 없으면 `평가 없음`을 표시하며 임의의 기본 점수를 만들지 않는다.

## 12. 화면 검수 체크리스트

- 연구자와 AI 전문가의 1순위 CTA가 서로 다른가?
- `협업 요청`과 `참여 신청`이 같은 객체처럼 보이지 않는가?
- 두 경로가 프로젝트 확정 뒤 같은 협업 화면으로 합쳐지는가?
- Availability, Relationship, Project Status가 분리되어 있는가?
- 프로젝트 카드만 보고 투입량·기간·협업 방식의 1차 판단이 가능한가?
- 상세에서 Data Readiness, 데이터 접근, 보안 조건을 판단할 수 있는가?
- 공개 범위에 따라 민감 정보가 실제로 달라지는가?
- 알림에서 현재 처리 가능한 화면으로 바로 이동하는가?
- 마일스톤마다 담당자·기한·완료 조건·검토 상태가 보이는가?
- 완료 뒤 양방향 평가와 Portfolio 초안으로 이어지는가?
- 평가 표본 수와 완료 프로젝트 수를 함께 보여주는가?
- 빈 상태, 마감, 만료, 권한 부족, 네트워크 오류 화면이 있는가?

## 13. 근거와 해석 경계

- 현재 팀 합의: 프로젝트 중심, 비대칭 양방향 매칭, 협업 Lifecycle, Stay-in Value, Milestone, 과업 템플릿, Portfolio.

- 시니어 개발자 피드백: 주소록화, 매칭 후 이탈, Progress Tracking, Cold Start 문제를 제품 리스크로 제시.
