# WHAT THE LAB 인사이트 편집·정기 게시 운영 기준서

> 버전: 1.1 / 작성일: 2026-10-16 / 개정일: 2026-10-20 (Asia/Seoul)
>
> 목적: 연구사례 선정부터 검증, 편성, 관리자 승인, 게시, 사후 정정까지 사람이 일관되게 판단하고 AI가 같은 기준으로 보조하도록 한다.
>
> 상태: Peter와의 대화에서 확인된 원칙을 기록한 기준서. 게시 빈도·후보 수 등 운영값은 시범 운영 제안이며 팀 전체 승인이나 운영 검증이 완료된 값이 아니다.

## 1. 가장 중요한 편집 원칙

**근거가 충분하고, 연구자가 자신의 상황에 맞는 다음 판단을 내리는 데 도움이 되는가?**

인사이트의 목적은 연구자가 자신의 연구에 AI를 적용할지, 무엇부터 준비할지 판단하도록 돕는 것이다.

**주 1회는 기본 편성 주기의 제안이며, 품질 기준을 낮춰서라도 채워야 하는 할당량이 아니다.** 적합한 승인 글이 없으면 게시를 보류한다.

좋은 결과를 소개하는 것뿐 아니라 적용이 어려운 조건과 추가로 확인해야 할 사항을 설명하는 것도 유용한 콘텐츠다. 특정 연구에서의 성공이 다른 연구에서의 성공을 보장한다고 표현하지 않는다.

### 1.1 합의 수준

| 구분 | 내용 | 적용 방식 |
|---|---|---|
| 대화에서 확인한 원칙 | 게시 횟수보다 내용의 질과 연구자에게 주는 도움을 우선 | 모든 선정·작성·검토 판단에 적용 |
| 기존 실행 명세의 기본 원칙 | 수집·분석·초안 자동화, 관리자 승인 후 게시, 출처·키워드 검증 | 기존 개발 명세와 함께 적용 |
| 시범 운영 제안 | 주 1회, 8주 시험 운영, 다음 4주 편성 | 운영 담당자와 팀이 값 확정 후 적용 |
| 시범 운영 제안 | 후보 8~12건, 승인 글 4~6건, 2~3편의 짧은 주제 묶음 | 목표 참고값이며 강제 수량·하드코딩 금지 |
| 구현 전 확인 | 담당자, 게시 요일·시간, 예산, 승인 기한, 분류체계 운영 버전 | 실제 저장소·팀 합의·외부 정책 확인 후 기록 |

이 문서는 편집 기준을 구체화한다. 제품 전체의 MVP 범위를 변경하거나 자동화 기능의 구현·배포를 승인하는 문서는 아니다.

## 2. 독자가 답할 수 있어야 하는 질문

연구사례 글은 다음 질문에 답하도록 작성한다.

1. 내 연구와 어떤 점이 비슷하고 다른가?
2. 기존 연구 방식의 어떤 병목을 해결하려 했는가?
3. AI가 수행한 일과 연구자가 직접 수행·검증한 일은 무엇인가?
4. 어떤 데이터, 라벨, 장비, 인력, 준비가 필요한가?
5. 어떤 조건에서 결과를 검증했으며, 어디까지 적용 가능한가?
6. 어떤 한계가 있고, 내 연구에서는 무엇을 더 확인해야 하는가?
7. 다음에 살펴볼 사례·기술·전문가는 무엇인가?

모든 질문에 확정적인 답을 만들어 넣지 않는다. 원문에서 확인되지 않은 규모·기간·비용·역할은 미확인이라고 밝힌다. 적용 가능성에 중요한 정보가 빠졌다면 보류하거나 공개 문장을 근거 범위까지 좁힌다.

## 3. 콘텐츠 유형과 사실의 경계

| 유형 | 중심 내용 | 지켜야 할 구분 |
|---|---|---|
| 연구사례 | 비-AI 연구 문제에 실제 AI를 적용하고 검증한 내용 | AI 적용 사실과 실제 인적·조직 간 협업 사실을 구분 |
| 실용 사례 | 대학 연구실·현장과 연결해 살펴볼 실증 사례 | 소규모·저비용·짧은 기간이라는 주장도 별도 근거 필요 |
| 비교·해설 | 여러 사례의 차이, 준비 조건, 기술 선택을 설명 | 원문 결과와 편집자의 해석을 구분하고 새 실증 사례로 집계하지 않음 |
| AI 트렌드 | 연구자에게 의미 있는 최근 변화 | 사건 발생일·발표일·확인일을 구분하고 게시 전 최신성 확인 |

연구사례 기반을 먼저 구현하고 AI 트렌드는 기존 실행 명세의 후속 단계에서 확장한다. 가정 시나리오는 실제 연구사례로 게시하지 않는다. 새 콘텐츠 유형의 개발은 팀 범위 합의 후 진행한다.

### 3.1 2026-10-17 추가 대화: 두 관점의 글과 읽기 보조

- 같은 주제로 연구사례와 기술 해설을 각각 쓸 수 있다. 사례는 실제 연구 적용·검증, 트렌드의 해설 글은 AI 개념·변화·연구자에게 주는 의미에 답한다. 단순 복제나 게시 수량 확보 목적으로 나누지 않는다.
- 두 글은 서로 연결하고 같은 연구라는 점을 밝힌다. 서로 독립된 연구사례 두 건으로 집계하지 않으며 각각 검토·승인한다.
- AI 트렌드는 속보뿐 아니라 이해를 돕는 기술 해설을 포함할 수 있다. 과거 연구 해설을 최신 발표·최신 순위로 표현하지 않고 사건일·글 작성일·개편일을 구분한다.
- AI 배경지식을 가정하지 않는다. 문제 → 쉬운 설명 → 정확한 용어 → 활용 → 한계 순서로 쓰고, 전문용어는 첫 문맥에서 풀어 설명한다. 섹션별 접이식 용어 풀이를 보조로 제공할 수 있다.
- 원문 결과와 편집자의 해설·적용 제안·주의 판단은 문단 유형으로 분리하고 화면에서 라벨·배경·테두리로 구별한다. 색만으로 의미를 전달하지 않는다. 원문에 없는 인적 협업이나 비용·절감률은 생성하지 않는다.
- 챗봇은 기본 설명을 대신하지 않는다. 연결 기능·권한·글 판본 계약은 담당 팀원과 합의 후 별도로 구현한다. 현재 변경은 로컬 정적 글과 읽기 보조 UI이며 자동 수집·실제 DB 게시를 승인하지 않는다.

### 3.2 설명의 깊이와 짧은 글 보강

- 글자 수·목차 수·읽는 시간만으로 충분한 설명이라고 판단하지 않는다. 모든 글의 길이를 맞추거나 이번 보강 분량을 최소 할당량으로 삼지 않는다. 자동 테스트의 분량 문턱은 추가 문단이 사라지는 오류를 찾는 보조 장치이지 게시 자격 기준이 아니다.
- 사례는 실제 연구 질문 → 데이터·정답 준비 → AI 방법 → 평가 조건·결과 → 적용 한계를 연결한다. 트렌드 해설은 쉬운 원리·비유·구체적인 예시·오해하기 쉬운 점을 중심으로, 독자가 **입력 → AI가 만드는 출력 → 사람이 확인할 결과**를 설명할 수 있게 쓴다.
- 짧은 글은 먼저 어느 질문의 답이 부족한지 확인한다. 목차나 비슷한 주의 문장을 늘리기보다 부족한 기존 문맥에 데이터 연결 예, 작동 과정, 실패 조건, 작은 평가 방법을 보탠다. 이미 충분한 설명을 일괄 재작성하지 않는다.
- 비유는 이해를 돕는 도구이지 모델이 실제로 생각·이해·대화한다는 증거가 아니다. 비유 뒤에는 정확한 작업과 비유가 성립하지 않는 부분을 풀어 설명한다. 전문용어는 접이식 풀이만 제공하지 말고 본문 첫 문맥에서도 설명한다.
- 원문에 없는 예시·시험 설계는 ‘설명용 가정’ 또는 ‘적용 제안’으로 명시한다. 새 표본 수·정확도·비용 절감·기관·저자별 역할을 만들어 사례의 결과처럼 제시하지 않는다. 역할 제안과 실제 협업 사실을 구분한다.
- 작은 시험은 비교 기준, 평가 단위, 중요한 오류, 사람이 검토할 조건과 남길 산출물을 설명한다. 성능 점수 외에 라벨 수정·검토 시간 등 실제 작업 부담도 살피도록 돕되, 이를 측정하지 않았다면 개선 효과로 주장하지 않는다.
- 의료·식품 안전·구조 안전·연구 보안 등의 예시는 개별 진단·안전 판정·자료 전송 허가를 대신하지 않는다. 연구용 출력과 실제 사용에 필요한 별도 검토·승인을 구분한다.

## 4. 두 가지 판단을 분리한다

### 4.1 게시 자격: 이 글은 게시할 만한가?

기존 Case Sheet와 12점 평가를 유지한다.

| 평가 항목 | 범위 |
|---|---:|
| 비-AI 분야의 실제 연구 문제 | 0~2 |
| AI의 연구 병목 해결 기여 | 0~2 |
| 연구자·AI 역할 구분 | 0~2 |
| 실제 결과 또는 적절한 검증 | 0~2 |
| 다른 연구자가 적용점을 찾을 가능성 | 0~2 |
| 입력 데이터 형태 설명 | 0~1 |
| 한계·적용 조건 설명 | 0~1 |

9~12점은 우선 검토, 7~8점은 추가 조사, 0~6점은 우선 제외한다. 점수는 출처 확인이나 관리자 승인을 대신하지 않는다. 이 점수는 사례 적합성 평가이며, 연구 자체의 학문적 우수성이나 재현성을 인증하는 점수가 아니다.

다음 조건은 점수와 별개로 충족해야 한다.

- 핵심 기술·수치·성과 주장을 출처와 위치로 추적할 수 있다.
- DOI·서지 확인과 논문 내용 검증을 구분한다.
- 초록만으로 Methods나 실제 협업을 검증 완료 처리하지 않는다.
- 원문의 관찰·결과와 플랫폼의 해석을 구분한다.
- 출처 이용 조건, 이미지 권리, 필수 표시 항목을 확인한다.
- 공개할 본문 버전과 승인 기록이 고정되어 있다.
- 검색 연결에 사용하는 키워드 ID가 운영 승인된 값이다.
- 사용자가 자신의 준비 조건·적용 한계·다음 행동을 이해할 수 있다.

근거 없는 핵심 주장은 삭제·수정하거나 보완 전 게시를 보류한다. 중요 한계가 확인되지 않았다는 사실을 숨기거나 AI로 추정해 채우지 않는다.

### 4.2 편집 우선순위: 이 글을 지금 게시할 이유가 있는가?

게시 자격이 있는 후보 사이에서 다음을 비교한다.

| 기준 | 판단 질문 | 관리자에게 보여줄 근거 |
|---|---|---|
| 사용자 가치 | 실제 연구자의 문제·준비 판단에 도움이 되는가? | 대상 연구자, 해결하려는 질문 |
| 차별성 | 기존 글과 비교해 무엇을 새로 제공하는가? | 중복되는 글과 차이 |
| 분야 균형 | 최근 게시가 같은 분야·기술에 몰렸는가? | 최근 게시 이력 |
| 연결 흐름 | 이전 글 다음에 읽을 이유가 있는가? | 연결할 글, 이어지는 독자 질문 |
| 시의성 | 지금 다루어야 할 이유가 있는가? | 관련 발표일·변경 사항 |
| 검토 준비도 | 게시 전 남은 확인 사항이 무엇인가? | 미완료 항목과 담당자 |

검토 준비도가 낮은 후보를 고득점만으로 예약하지 않는다. AI가 만든 단일 점수만으로 순서를 확정하지 말고 추천 이유·보류 이유·대체 후보를 함께 표시한다. 정교한 가중치 최적화는 운영 데이터가 쌓인 후 검토한다.

### 4.3 원문 확인 범위와 수치 인용

검토 기록에는 출처 제목·URL/DOI·자료 버전·확인일과 **실제로 읽은 위치**를 남긴다. HTML 절·소절·표 번호, PDF 파일 페이지와 인쇄 쪽수처럼 다시 찾을 수 있는 정보를 사용한다. PDF 표·도판의 추출 텍스트가 불분명하거나 수치가 충돌하면 해당 페이지를 시각적으로 대조한다. 이것은 검토 기록의 원칙이며 새 DB 필드나 자동 검증 기능의 구현 승인은 아니다.

| 확인 범위 | 말할 수 있는 내용 | 말하면 안 되는 내용 |
|---|---|---|
| DOI·서지 정보 | 해당 논문의 식별 정보 확인 | 방법·성과·실제 협업 검증 완료 |
| 공개 초록·공식 연구 소개 | 해당 자료에 명시된 주장과 요약 | 미열람 Methods·보충자료의 표본·조건을 확인한 것처럼 설명 |
| 원문 일부 절·표·보충자료 | 직접 확인한 위치와 그 근거 범위 | 일부 확인을 원문 전체 검증·현장 일반화로 확대 |
| 직접 실행·재현 | 실제 수행한 환경·절차·비교 결과 | 논문을 읽거나 UI 테스트만 통과한 것을 실험 재현으로 표시 |

- **접근하지 못한 것과 원문에 없는 것은 다르다.** 접근 실패·구독 제한·부분 열람은 그 상태대로 기록한다. 확인되지 않은 조건을 추정해 채우지 않고, 중요하면 추가 확인 전 핵심 주장을 보류한다.
- 수치는 지표 이름·단위·대상·평가 단위·조건을 함께 읽는다. 이미지 수와 환자·개체 수, 후보 모델 최고값과 최종 선정 모델, 학습·선정 자료의 점수와 독립 평가 결과를 혼동하지 않는다. R²를 정답 비율로, IoU를 안전 판정 정확도로, 모델 FPS를 전체 현장 처리 속도로 바꾸어 설명하지 않는다.
- 초록·표·본문·결론 사이에 수치가 다르면 각 위치와 값을 기록하고 설명·정정 자료를 확인한다. 해결되지 않은 차이는 유리한 값 선택·평균·조용한 치환으로 처리하지 않는다. 단일 확정 수치의 인용을 보류하고 중요도에 따라 주장 범위를 축소하거나 게시를 보류한다.
- 정정·철회·버전 변경을 확인했을 때는 원래 주장과 달라진 근거를 연결한다. 자료 간 차이가 있다는 사실만으로 원 연구 전체를 오류로 단정하지 않는다. 확인 결과와 미해결 사항을 함께 남긴다.
- 지표나 한계를 고치면 본문뿐 아니라 제목·요약·하이라이트·카드·관련 글 소개에도 같은 주장이 남아 있는지 점검한다. 수정한 공개 버전은 다시 승인받는다.

## 5. 후보 확보와 글 비축

수집 주기, 검토·편성 주기, 게시 주기를 분리한다.

- 수집: 소스 변경량과 호출 예산에 맞춰 주기적으로 실행한다.
- 검토·편성: 다음 4주 계획을 정기 검토하는 방식을 초기안으로 삼는다.
- 게시: 주 1회 기본안을 시험하되 승인 글이 없으면 보류한다.

초기 비축 참고값은 조사·검토 후보 8~12건, 승인 글 4~6건이다. 후보가 많다는 이유로 모두 본문까지 생성하지 않는다. 규칙 필터·중복 검사·최소 근거 검사를 먼저 수행해 검토 부담과 AI 호출 비용을 줄인다.

후보 부족은 다음 원인으로 구분한다.

| 원인 | 대응 |
|---|---|
| 발견 부족 | 검색어·분야·허용 소스를 점검 |
| 근거 부족 | 허가된 원문·추가 출처 확보, 검증 방법 개선 |
| 기존 글과 중복 | 미충족 연구 문제 탐색, 기존 글 업데이트 검토 |
| 검토 지연 | 담당자·검토 시간 조정 |
| 작성 준비 부족 | 구조화 자료 보완 후 본문 작성 |

주제 범위를 무리하게 넓히거나 가정을 실증 사례로 바꾸어 수량을 채우지 않는다.

## 6. 게시 흐름과 순서

### 6.1 서비스 오픈 시점

오픈 시점에는 방문자가 서로 다른 문제와 접근법을 비교할 수 있는 검증된 기본 사례 묶음을 준비한다. 초기 공개 수량은 분야·문제의 범위와 검토 여력으로 결정한다. 기본 사례도 모두 같은 승인 절차를 거친다.

### 6.2 정기 편성

다음 4주는 구체적으로 편성하고, 더 먼 일정은 주제 수준으로 잠정 관리하는 방식을 초기안으로 삼는다.

연결 묶음은 2~3편 정도를 참고하되 긴 의무 연재로 만들지 않는다. 같은 분야뿐 아니라 연구자의 질문이 이어지는지를 확인한다.

예시: 사진에서 수치 측정 → 대상 영역 분할 → 추출한 특징으로 결과 예측. 실제 후보에서 각 기술의 사용 근거가 확인될 때만 해당 흐름을 구성한다.

- 각 글은 중간 편부터 읽어도 이해할 수 있도록 독립적으로 완결한다.
- 연결은 관련 글 링크와 짧은 설명으로 제공한다.
- 관련성이 있다는 이유만으로 논문 간 선후 관계·우열을 만들어내지 않는다.
- 주제 연속성과 분야 다양성을 함께 검토한다.
- 선행 글이 꼭 필요한 경우에만 순서 제약을 두고, 나머지는 추천 연결로 관리한다.
- 편성안 승인과 개별 본문 게시 승인은 구분한다.
- 예약 변경·취소는 변경자와 사유를 남기며 에이전트가 확정 일정을 조용히 바꾸지 않는다.

### 6.3 사례와 트렌드의 대기 방식

연구사례는 활용 조건이 유지되는지 확인하며 비축한다. 트렌드는 핵심 사실이 오래되지 않았는지 게시 직전에 재확인한다. 긴급한 트렌드 때문에 기존 순서를 바꾸는 경우에도 관리자 검토와 변경 이력을 유지한다. 트렌드로 사례 부족을 자동 대체하지 않는다.

## 7. 게시 직전 점검과 보류

예약된 글도 발행 직전에 다음을 확인한다.

- 승인받은 revision과 실제 게시 revision이 일치하는가?
- 핵심 출처 링크와 식별 정보가 유효한가?
- 사용 가능한 출처에서 정정·철회·핵심 변경 정보가 발견되는가?
- 주요 수치·버전 등 시간에 민감한 사실이 유효한가?
- 키워드 상태와 관련 글·전문가 검색 링크가 정상인가?
- 이미지·인용·라이선스 및 공개 범위에 문제가 없는가?

점검의 자동화 범위와 확인 불가능한 항목을 기록한다. 자동 조회에서 정정·철회가 발견되지 않았다는 사실만으로 부재를 보증하지 않는다.

핵심 점검 실패 시 해당 글을 보류하고 관리자에게 사유를 안내한다. 링크 일시 장애는 연구 내용이 틀렸다는 판정과 구분한다. 대체 글을 발행할 때도 그 글의 본문 승인·편성·게시 전 점검이 충족되어야 한다. 대체 글이 없으면 그 주 게시를 생략한다.

## 8. 기존 글 업데이트와 중복 관리

| 상황 | 기본 처리 |
|---|---|
| 같은 사례에 새로운 사실·정정 추가 | 기존 글 업데이트와 변경 이력 |
| 표현만 다른 동일 내용 | 새 글 발행하지 않음 |
| 여러 사례의 공통점·조건 차이 분석 | 별도 비교·해설 글로 분류, 출처 명시 |
| 후속 연구에서 독립적인 새 결과 확인 | 새 사례 또는 후속 글로 검토 |

같은 논문을 다루는 글은 연결 관계와 새로운 가치를 기록한다. 본문을 바꾼 경우 승인도 새 버전에 맞춰 다시 수행한다. 실질적 변경 없이 날짜만 갱신하지 않는다.

게시 후 오류나 권리 문제가 제기되면 영향 범위 확인 → 필요시 일시 비공개·후속 게시 중지 → 근거 검토 → 수정·재승인 → 정정 이력 표시 순으로 처리한다. 원본 이력과 감사 기록은 보존한다.

### 8.1 표지의 의미와 보강 후 검수

- 서로 다른 글이 같은 글로 오인되지 않도록 대표 이미지 재사용을 피한다. 중복 이미지 중에서는 핵심 대상·방법·독자 질문과 가장 직접적으로 맞는 글에 기존 이미지를 남기고, 연관성이 낮은 글의 표지를 교체한다. 같은 글의 목록·상세·관련 글에 같은 표지를 사용하는 것은 정상이다.
- 새 표지는 제목이나 태그의 단어만 보고 고르지 않고 본문 내용과 대조한다. 목록·상세·모바일 크롭에서도 핵심 대상이 보이는지 확인한다. 원본 에셋은 보존하고 교체 파일과 글의 연결을 기록한다.
- AI 생성 이미지는 설명용임을 alt·캡션과 에셋 기록에 남긴다. 실제 논문 도판·환자 영상·측정 결과로 오인시키거나 그림 안에 확인되지 않은 수치·성과를 넣지 않는다. 생성 이미지라는 사실만으로 권리·이용 조건 확인을 면제하지 않는다.
- 보강 전후 URL·분류·목차·관련 글·용어·표지 연결을 비교한다. 요청한 변경 외에 이미 검토된 본문이 바뀌지 않았는지 확인하고, 의도적으로 변경한 항목은 이유를 기록한다. 표지 중복은 경로뿐 아니라 실제 파일 내용도 확인해 파일명만 바꾼 복제를 놓치지 않는다.
- 긴 본문·편집자 노트·용어 펼침·목차 이동을 PC·태블릿·모바일에서 확인한다. 첫 화면만이 아니라 실제로 보강한 본문 위치를 캡처한다. 검사 조건·실행 결과·미검증 범위는 날짜별 QA 기록에 남기고 과거 기록을 덮어쓰지 않는다.
- 빌드·자동 테스트·화면 검수는 콘텐츠 전달과 기존 기능 보존의 검사다. 학술적 동료 심사·모델 성능 재현·운영 게시 완료로 표현하지 않는다. 로컬 정적 원고 반영, DB 본문 갱신, 관리자 승인, 실제 게시·배포의 완료 상태를 각각 구분한다.

## 9. 기술 키워드와 전문가 연결

- 연구자용 쉬운 태그, AM 기술 분야, 전문가 세부 기술·CAP를 같은 개념으로 취급하지 않는다.
- 사례에서 확인한 기술과 원문에 없는 적용 아이디어를 구분한다.
- 새 키워드는 후보로 두고 사람이 검토한다.
- 운영 미승인 분류체계를 확정 필터로 사용하지 않는다.
- 관련 전문가가 없으면 있다고 표현하거나 적합성을 보장하지 않는다.
- 정확한 연결이 없으면 관련 사례·기술 설명·일반 전문가 탐색으로 안내한다.
- 상담 전 확인할 질문을 제공할 수 있으나, 미구현 상담 기능이 동작하는 것처럼 표시하지 않는다.

## 10. 에이전트·서버·관리자의 역할

| 주체 | 맡는 일 | 최종 결정 경계 |
|---|---|---|

| 관리자 | 근거·유용성·본문·키워드 검토, 편성 승인, 게시·보류·정정 판단 | 결정과 사유를 기록 |

- 이번에 게시해야 할 이유
- 연결할 이전·다음 글과 이어지는 질문
- 중복·분야 편중 점검
- 근거 보완 사항과 게시 전 재확인 사항
- 대체 후보와 순서 변경 이유

초기 구현은 규칙 기반 필터와 AI 설명 제안을 조합한다. LangGraph는 분기·재검토·승인 대기를 관리하는 구현 선택지다. 프레임워크 사용 자체가 콘텐츠 품질을 보장하지는 않는다.

## 11. 측정과 운영 조정

### 11.1 공급과 처리 상태

- 승인된 미게시 글 중 현재 게시 가능한 글 수
- 남은 게시 가능 주수 = 게시 가능한 승인 미게시 글 수 ÷ 주당 계획 게시 수
- 새 후보의 검증 통과율과 제외 사유
- 글 한 건에 드는 검토 시간과 비용
- 근거 보완·관리자 검토 단계별 대기 시간

동일 글은 한 번만 세고, 이미 예약된 미게시 글도 승인 미게시 재고에 포함한다. 재확인 필요·게시 보류·시의성을 잃은 글은 게시 가능 재고에서 제외한다. 유형별 수량도 함께 본다. 주당 계획 게시 수가 0이면 주수 지표는 계산하지 않는다.

### 11.2 독자에게 준 도움

- 관련 사례 이동
- 기술 태그와 전문가 검색 클릭
- 구현된 경우 상담 요청 연결
- 이용자 피드백: 준비 조건 이해 여부, 적용 판단에 도움이 된 점, 추가로 필요한 정보

조회수는 보조 지표로 사용한다. 클릭을 연구의 실제 성공이나 전문가 적합성 검증으로 해석하지 않는다. 초기 소수 이용자의 결과만으로 특정 분야의 수요가 없다고 결론내리지 않는다.

8주 시범 운영 후 빈도, 재고 목표, 검토 여력, 유형 구성의 조정 여부를 검토하는 것을 제안한다. 실제 운영 전에는 담당자와 검토 시점을 확정한다. 목표 미달의 자동 대응으로 품질 기준을 낮추지 않는다.

- [ ] 미확인 정보와 편집자의 해석이 분리되어 있다.
- [ ] 입력·AI 출력·사람의 검증을 설명할 수 있으며 분량을 채우는 반복 대신 부족한 질문을 보완했다.
- [ ] 비유·가정·작은 시험·역할 제안이 원 연구의 실제 결과와 구분된다.
- [ ] 실제 열람 범위·버전·확인일·원문 위치를 기록하고 접근 불가를 정보 부재로 단정하지 않았다.
- [ ] 지표의 대상·단위·조건·후보/최종 모델을 구분하고 미해결 수치 차이를 숨기지 않았다.
- [ ] 기존 글과의 차이 또는 업데이트 이유가 있다.
- [ ] 키워드와 전문가 탐색 연결이 정확하고 과장되지 않았다.
- [ ] 이미지·인용·출처 이용 조건과 표시를 확인했다.
- [ ] 다른 글과 표지가 혼동되지 않고 AI 생성 설명 이미지의 표시·크롭·목록/상세 연결을 확인했다.
- [ ] 변경한 본문·요약·카드의 내용이 일치하며 보강 위치와 읽기 보조 동작의 검수 범위를 기록했다.
- [ ] 승인할 본문 버전이 저장되어 있다.
- [ ] 편성 이유·순서·대체 여부를 기록했다.
- [ ] 게시 직전 점검 결과를 기록했으며 실패 항목을 해결했다.

‘많이 읽힐 것 같다’거나 ‘이번 주 게시일이다’라는 이유만으로 위 기준을 면제하지 않는다.

## 13. 개발 반영 범위와 문서 관계

첫 구현에 반영할 항목:

1. 후보·근거 보완·검토·승인·예약·게시·보류 상태를 구분한다.
2. 편성 정보에는 후보 ID, 예정일, 추천 이유, 주제 묶음, 연결 글, 대체 후보를 기록한다.
3. 게시 자격 점수와 편집 우선순위는 별개로 저장한다.
4. 본문 revision 승인과 편성 결정을 각각 추적한다.
5. 게시 직전 점검 실패·적격 후보 없음의 보류 동작을 구현한다.
6. 승인 버전 일치와 동일 글 중복 게시 방지를 검증한다.
7. 재고·처리 대기·독자 행동의 최소 운영 지표를 남긴다.

추후 검토: 자동 가중치 최적화, 복잡한 연재 그래프, 개인화 편성. 이 기능들을 첫 구현의 필수 조건으로 추가하지 않는다.
