## 1. 목적과 적용 경계

컴퓨터를 꺼도 자료 조사와 후보 초안 생성을 이어갈 수 있도록 실행 환경을 분리하되, 외부 자료를 읽는 AI에 운영 DB 권한을 주지 않는다. 수집 결과는 PR로 전달하고 검증된 프로그램이 Supabase에 **미승인 후보로만** 반입하는 방식을 초기 권고안으로 삼는다.

**PR 머지 ≠ DB 반입 완료 ≠ 편집 승인 ≠ 공개 사이트 게시 완료.** 각 단계의 결과를 따로 확인한다.

이 기준서는 구현·배포 실행 지시가 아니다. 문서 작성만으로 AWS 자원 생성, 유료 모델 호출, 비밀키 등록, GitHub 권한 변경, DB 쓰기, PR 생성·머지, 자동 게시를 허용하지 않는다. 로그인·일반 관리자·챗봇 등 다른 담당 기능의 범위도 확대하지 않는다.

함께 적용할 기존 문서:

- [MVP 범위](../product/MVP_SCOPE.md), [의사결정 로그](../product/03_DECISION_LOG.md): 허용한 개발 범위와 단계.
- [편집·정기 게시 운영 기준서](INSIGHT_EDITORIAL_OPERATING_STANDARD.md): 연구자 유용성, 근거, 설명 깊이, 키워드, 이미지, 게시 승인.
- [통합 개발 지시서](WHAT_THE_LAB_AI_CASE_AND_TREND_AUTOMATION_CODEX_SPEC.md): 단계별 개발·검증과 기존 설계.
- [일괄 입력 QA](../qa/INSIGHT_CANDIDATE_IMPORT_2026-10-22.md), [수집 정책 QA](../qa/insight-discovery-policy-20261022/README.md): 실제 구현과 미구현의 경계.

문서가 충돌하면 최신 팀 합의와 명시적인 사용자 승인 범위를 확인한다. 이 문서의 제안을 과거 구현 사실이나 팀 전체의 확정 결정으로 해석하지 않는다.

기존 일괄 입력 코드를 재사용하되, 현재의 사람용 관리자 로그인·권한을 기계용 반입 계정으로 공유하지 않는다. 새 작업 계정 또는 전용 실행 경계는 별도 설계·검증이 필요하다.

### 2.2 이번 기준서에서 정리하는 필수 안전 원칙

1. 수집 AI와 DB 반입 프로그램의 권한을 분리한다.
2. 수집 결과는 신뢰하지 않는 외부 입력으로 검증한다.
3. 반입 결과는 미승인 후보이고, 최종 게시에는 별도 관리자 승인이 필요하다.
4. 기존 공개본·사람이 수정한 초안·검토 이력을 자동으로 덮어쓰지 않는다.
5. 비밀정보를 코드·PR·원고·로그·AI 대화에 넣지 않는다.
6. 품질이나 근거가 부족하면 수량을 채우지 않고 보류한다.

### 2.3 팀 검토가 필요한 초기 권고안

- 클라우드 AI가 데이터 전용 PR을 만들고, 초기에는 사람이 검토한 뒤 수동으로 반입한다.
- 검증이 안정화되면 보호된 브랜치에 머지된 데이터만 AWS 반입 프로그램이 처리한다.
- 공개되지 않은 초안은 비공개 저장소를 우선 검토한다. 현 서비스 저장소의 공개 여부는 재확인한다.
- 실행 환경은 AWS를 우선 검토하되 EC2·ECS/Fargate·Lambda 중 하나를 이 문서에서 확정하지 않는다.
- 게시 빈도와 수집 빈도는 분리한다. 주 1회 게시 시범안은 게시 의무가 아니다.

## 3. 기본 구조와 책임

| 주체 | 할 수 있는 일 | 주지 않을 권한 |
|---|---|---|
| 클라우드 수집 AI | 허용 출처 조사, 초안·근거 위치·쉬운 설명 작성, 데이터 PR 제안 | Supabase 접속, AWS 비밀정보 읽기, PR 자체 승인·머지, 게시 |
| 비밀키 없는 PR 검사 | 형식·크기·허용 경로·누락·민감정보·중복 단서 검사 | 운영 DB 읽기·쓰기, 미승인 코드 실행 |
| 사람 리뷰어 | 출처·권리·범위·변경 의도 확인, 반입용 PR 승인·머지 | 머지만으로 게시 승인 대체 |
| AWS 반입 프로그램 | 승인된 입력 재검사, 중복 확인, 미승인 후보 및 판본 저장, 결과 기록 | 회원·프로젝트 수정, 승인·예약·게시 상태 생성, 운영 Master 승인 |
| 인사이트 관리자 | 근거·원고·권리·키워드 검토, 판본별 최종 승인·게시 판단 | 근거 없이 사실·성과를 확정 |

한 사람이 PR 리뷰와 편집 검토를 겸할 수 있으나 두 결정의 기록과 의미는 구분한다. 소규모 팀에서 검토 부담이 커지면 중복 절차를 조정할 수 있지만 최종 게시 승인을 생략하지 않는다.

### 단계별 산출물

1. 수집: 출처 목록, 실제 접근 범위, 검색·선별 결과, 실패 사유.
2. 초안: 출처로 추적 가능한 주장 메모와 독자용 전체 원고를 구분한 파일.
3. PR: 새 후보·중복 가능성·미확인 사항·권리 주의사항·원고 차이.
4. 반입: 승인된 입력 식별값, 후보·판본 ID, 생성·중복·충돌·실패 결과.
5. 편집·게시: 승인자, 승인 판본, 게시 전 점검, 공개 결과.

AWS 배포는 실행 장소를 제공한다. 예약 실행기나 AI 모델을 자동으로 연결해 주지는 않는다. 구독 기반 클라우드 AI를 사용하든 모델 API를 사용하든 위 권한 경계는 동일하게 적용한다.

## 5. 수집·작성 기준과 실행 예산

콘텐츠 품질은 [편집 기준서](INSIGHT_EDITORIAL_OPERATING_STANDARD.md)를 따른다. 본 문서 때문에 기존 원고의 깊이를 줄이거나 주장 메모만 전체 기사로 표시하지 않는다.

- 협업사례는 연구 문제·입력·AI와 연구자 역할·검증·성과·한계를 설명한다.
- 트렌드는 연구자를 위한 쉬운 해설과 전문용어 풀이를 제공한다. 사례와 같은 원출처를 사용할 수 있으나 독자 질문과 원고를 구분하고 서로 연결한다.
- 원문 사실, 편집자의 해석·판단, 적용 아이디어·가상 예시를 구분한다.
- DOI·공식 발표 존재 확인은 원문 내용 검증이나 실험 재현 완료가 아니다.
- 그림은 본문 검토 후 별도 준비하며 권리·AI 생성 표시를 확인한다. 초기 자동 반입은 `no_image`를 유지하고 이미지 추가는 별도 검토한다.

기존 기간 확장 정책은 협업사례 30→60→90→180→365일, 최신 소식 30→60→90일, 기술 해설 30→90→365일이다. 실제 적용값은 승인된 설정 버전으로 고정해 회차에 기록하고, 상한에 도달하면 부족한 채 종료한다.

설정에 저장된 출처 요청 30회·120초는 수집 탐색 단계의 초기 안전 상한이다. 이를 AI 전체 원고 작성 시간이나 모든 클라우드 실행의 완료 보장으로 해석하지 않는다. 다음 예산은 Phase 0에서 단계별로 별도 확정한다.

- 탐색: 출처 요청·페이지 이동·재시도·시간·최대 결과 수.
- 작성: 한 회차의 작성 대상 수·모델 사용량·최대 실행 시간·재생성 횟수.
- PR/반입: 최대 파일·용량·글 수·동시 실행 수·DB 대기 시간.
- 전체 운영: 주간 사용량·비용 상한, 경고 수신자, 상한 초과 시 중지 동작.

출처 오류·호출 제한·사용량 부족을 ‘좋은 사례가 없다’로 처리하지 않는다. 무한 재시도·무한 기간 확장·자동 유료 사용량 추가를 금지한다. 실패를 기록하고 기존 게시·후보는 그대로 둔다.

## 6. 데이터 파일 계약 — 실행 가능한 원고를 받지 않는다

### 6.1 파일과 저장 위치

기본 전송 형식은 스키마를 검증할 수 있는 UTF-8 JSON이다. 리뷰 편의를 위한 설명 문서는 정해진 템플릿의 일반 텍스트로만 허용할 수 있다. JSON은 실행하는 코드가 아니라 읽어서 검사할 자료로 취급한다.

- MDX, JavaScript, Python, SQL, HTML 스크립트, 셸 명령, 패키지·빌드 설정을 콘텐츠 PR에 넣지 않는다.
- `eval`, 동적 import, 원고가 지정한 명령·의존성 설치·파일 실행을 하지 않는다.
- 심볼릭 링크, 경로 탈출(`..`), 임의 바이너리·압축 파일·대형 파일은 거절한다.
- `data/`는 현재 저장소 규칙상 가상·비식별 샘플용이다. 실제 수집 원고를 그곳에 넣지 않는다. 실제 콘텐츠 경로 또는 별도 비공개 저장소는 팀 승인 후 정한다.
- 이 문서의 필드·경로 제안만 보고 현재 API에 전송하지 않는다. 새 전송 계약과 변환기를 먼저 구현·테스트한다.

### 6.2 최소 계약 항목

2026-10-28 구현 현황: [전송 계약 v1](INSIGHT_TRANSFER_CONTRACT.md)의 로컬 JSON 검사와 내부 반입 로직의 가상 DB 검증까지 추가했다. 반입 로직은 웹·CLI·AWS에 연결하지 않았다. 아래 요구 중 묶음 접수 이력·동시성, 신뢰하는 실행기의 PR·커밋 추적, 승인 설정 대조, 실제 DB 반입은 미완료다. 기존 API의 입력 계약은 바꾸지 않았다.

다음은 새 전송 묶음의 설계 요구사항이며 **현재 `CandidateImportInput`에 그대로 추가할 수 있는 필드 목록은 아니다.** 현재 스키마는 알 수 없는 필드를 거절한다. 전송 봉투와 기존 API 입력 사이에 명시적인 변환이 필요하다.

| 묶음 | 필요한 정보 | 검사 원칙 |
|---|---|---|
| 전송 식별 | 스키마 버전, 묶음 ID, 회차 ID, 생성 시점, 파일 식별값 | 알 수 없는 버전 거절, 시간대 포함 |
| 실행 조건 | 출처·검색·기간·예산 설정 버전 또는 승인된 스냅샷 | 기준서와 불일치하면 보류 |
| 출처 | 제목, HTTPS URL, DOI(있는 경우), 발표일·정밀도·미상 여부, 실제 열람 범위·확인 시각 | DOI·URL 정규화, 미상 값을 생성일로 대체 금지 |
| 원고 식별 | `case`/`trend`, 제안 제목·주소, 분야·분류 태그, 원출처와 관련 원고 연결 | 같은 논문의 사례/해설은 허용하되 같은 유형의 중복은 별도 검사 |
| 주장 메모 | 주장, 근거 위치, 확인 범위, 미확인 사항 | AI가 적은 `verified`를 검증 완료로 신뢰하지 않음 |
| 전체 기사 | 본문, 쉬운 용어 풀이, 요약, 한계, 편집자 노트 | 주장 메모와 별도 보관. 전체 원고 계약 검증 전 조용히 버리거나 요약으로 대체 금지 |
| 권리·생성 이력 | 출처 이용 조건 확인 사항, 모델·작성 도구, 지시서 버전, 생성 시점 | 비밀정보·대화 전체·비공개 추론 기록 저장 금지 |
| 반입 추적 | 저장소, PR 번호, 승인 입력의 커밋 ID·파일 해시, 실행 프로그램 버전 | 값은 신뢰하는 실행기가 확보. 원고가 자칭한 값을 승인 증거로 사용 금지 |

SHA-256 같은 파일 해시는 ‘검토한 파일과 반입한 파일이 같은가’를 확인하는 값이다. 누가 승인했는지나 내용이 사실인지를 증명하지는 않는다. 승인·출처 검증과 함께 사용한다.

전체 기사와 근거 메모를 한 묶음으로 지원할 때에는 둘 다 반입되거나 둘 다 실패하도록 한다. 지원되지 않는 전체 기사를 누락한 채 성공 처리하지 않는다.

## 7. 콘텐츠 PR의 작성·검사·머지 기준

### 7.1 PR 범위

- 한 PR은 식별 가능한 한 회차의 소량 콘텐츠만 다룬다. 기능 개발·보안 설정 변경과 섞지 않는다.
- 신규 글·기존 글 수정 제안·중복 가능성을 구분한다. 원고 자동 삭제는 금지한다.
- 서비스 코드·DB migration·`.github/workflows/`·권한 설정·의존성·비밀 파일 변경이 섞이면 반입 대상에서 제외하고 실패 처리한다.
- 저장소의 `develop`은 기존 기능 PR 대상이다. 콘텐츠 전용 대상 브랜치·저장소는 팀 합의로 정하며 `main`에 직접 기능 커밋을 추가하지 않는다.
- 봇에 GitHub 접근이 필요하면 전용 GitHub App 등 짧고 제한된 자격증명을 우선 검토한다. 저장소 쓰기 권한이 자동으로 ‘특정 폴더만 수정 가능’을 뜻하지 않으므로 경로 검사·보호 규칙·머지 제한을 별도로 둔다.

### 7.2 PR에 적을 정보

기존 [.github PR 양식](../../.github/pull_request_template.md)을 유지하며 다음을 추가한다.

1. 회차·설정 버전·사용 출처·대상 기간과 후보 수.
2. 각 글의 유형·독자 질문·출처 링크·관련 글·중복 검토.
3. 실제 읽은 범위, 미확인 주장, 접근 실패, 권리 주의사항.
4. 자동 검사 결과, 사용량·비용을 확인할 수 없는 경우 그 사실.
5. 반입되더라도 미승인 후보이며 공개 게시가 아니라는 표시.

### 7.3 비밀키 없는 검사

PR 단계에서는 DB·AWS·모델 비밀키 없이 허용 경로, JSON 스키마, 필드·용량 상한, 출처 형식, 중복 식별값, 민감정보 패턴을 검사한다. 스캐너를 통과했다는 이유로 비밀정보·저작권·내용 오류가 없다고 보증하지 않는다.

검사기는 신뢰하는 기준 브랜치·고정 버전의 코드를 사용한다. PR 안의 검사기·의존성·설정을 가져와 실행하지 않는다. 높은 권한의 `pull_request_target` 등으로 미승인 PR 코드를 실행하지 않는다. 이 위험은 GitHub 공식 보안 문서에서도 설명한다. [GitHub PR 실행 보안](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

### 7.4 머지 조건

- 사람이 변경 파일과 원문 접근 범위·민감정보·권리 주의사항을 확인한다.
- 필수 검사와 리뷰는 최종 반입 대상 커밋에 대응해야 한다. 승인 뒤 원고가 바뀌면 다시 검사·리뷰한다.
- 자동 머지·봇 자기 승인·브랜치 보호 우회를 허용하지 않는다.
- PR 검토 통과는 **후보로 반입해도 되는가**의 판단이다. 글을 게시할 만큼 검증했는가는 관리자 페이지에서 별도로 판단한다.

## 8. AWS 반입 실행 기준

### 8.1 실행 위치와 호출 경로

초기에는 담당자가 승인된 파일을 지정해 미리 보기 후 반입한다. 이후 자동화는 보호된 브랜치의 머지 이벤트 또는 합의한 주기 실행으로 연결할 수 있다. 예약 수집과 머지 후 반입은 서로 다른 실행이다.

AWS EventBridge Scheduler는 ECS 작업의 일회·반복 예약과 시간대 설정을 지원한다. 이는 가능한 구성의 근거일 뿐 ECS 채택 결정은 아니다. [AWS 예약 실행 문서](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/tasks-scheduled-eventbridge-scheduler.html)

기존 웹 서버 프로세스 안에 예약 루프를 무조건 넣지 않는다. 여러 웹 프로세스나 재시작 때문에 같은 작업이 겹칠 수 있으므로 실행 경계·잠금·중복 방지를 정한다. 단계가 다른 두 예약 실행기를 동시에 켜서 같은 회차를 중복 생성하지 않는다.

### 8.2 신뢰할 입력 고정

1. 저장소·대상 브랜치·승인된 PR·실제 머지 결과를 확인한다. 단순 이벤트 수신이나 파일 속 `approved=true`는 승인 증거가 아니다.
2. 입력을 브랜치 이름이 아니라 확인된 커밋 ID와 파일 해시로 고정한다. 검사한 뒤 브랜치 최신본을 다시 내려받아 바꿔치기하지 않는다.
3. 콘텐츠 파일만 읽고 고정된 반입 프로그램으로 다시 검증한다. 자동 실행 시 전달된 PR 코드를 배포하거나 실행하지 않는다.
4. 개발/운영 환경·스키마 버전·건수 상한을 확인하고, 미리 보기 결과와 저장 대상이 일치하는지 검사한다.
5. 현재 importer의 기존 글 보존·중복·충돌·검증 초기화 로직을 재사용한다. 인증을 우회하거나 관리자 쿠키를 복사하지 않는다.

### 8.3 저장 상태와 동시성

- 모든 신규 반입은 미승인 초안으로 저장한다. 점수·검증된 Master ID·이미지 권리·읽기 검수·승인자·예약·게시 상태를 파일에서 수용하지 않는다.
- 알려진 DOI·정규화 URL·원고 유형을 기존 글과 대조한다. 같은 출처라도 사례와 해설은 다를 수 있으며 제목 유사성만으로 자동 병합하지 않는다.
- 이미 사람이 수정했거나 승인·게시한 글이 있으면 보존한다. 변경 제안은 별도 판본·충돌 목록으로 남기고 자동 교체하지 않는다.
- 커밋/파일 해시·묶음 ID를 반입 이력과 연결한다. 같은 입력이 재전달되어도 후보·판본·이력이 불필요하게 늘지 않도록 한다. 단순 사전 조회만이 아니라 DB 제약·트랜잭션·동시 실행 시험이 필요하다.
- 기본은 묶음 단위 원자적 처리이다. 뒤 항목이 실패하면 앞 항목도 확정하지 않는다. 부분 성공이 필요해지면 별도 합의와 재처리 계약을 만든다.
- `dry_run`은 실제 저장을 하지 않아야 한다. 자동 반입은 설정·정책 버전을 확인한 별도 명시적 저장 모드이며 미리 보기 옵션을 조용히 바꾸지 않는다.
- 기존 관리자 전용 importer는 전용 작업 계정·기계 인증을 제공하는 것과 다르다. DB 직접 역할 또는 좁은 전용 서버 경계 중 하나를 검토하며 후보·근거·판본·반입 이력에 필요한 최소 접근만 허용한다.

### 8.4 실패·복구·추적

- 반입 상태는 제안값으로 `검사 중/미리 보기 완료/저장 완료/실패/충돌/취소`를 구분한다. 실제 상태명·테이블은 기존 구조와 대조해 정한다.
- 커밋·해시·실행 ID, 신규·기존 보존·중복·충돌 건수, 시작/종료 시각과 안전한 오류 코드를 기록한다.
- 재시도 상한을 넘으면 중지하고 담당자에게 알린다. 성공을 기록하기 전에 DB 확정 여부를 확인한다.
- Git에서 파일을 되돌려도 이미 저장한 DB 후보가 자동 복구되는 것은 아니다. 반입 이력으로 영향 후보를 특정해 별도 보류·수정 절차를 따른다.
- 오류 원고는 삭제로 숨기지 않고 비공개 보류와 변경 이력을 남긴다. 기존 공개본은 유지하며 대량 삭제·운영 DB 초기화는 하지 않는다.

## 9. 비밀정보·권한·외부 입력 보안

### 9.1 DB 자격증명의 보관

Supabase에 직접 쓰는 것이 본질적으로 금지되는 것은 아니다. 이 초기안은 **외부 자료를 읽는 생성 AI에 DB 권한을 주지 않기 위해** PR과 반입 프로그램을 분리하는 것이다.

- `DATABASE_URL`의 비밀번호와 Supabase 서버 전용 키 모두 비밀정보이다. DB 연결 문자열과 Data API 키의 인증·권한을 혼동하지 않는다.
- Supabase `secret`/`service_role`은 높은 권한이며 RLS를 우회한다. 서버 실행이라는 이유만으로 AI·PR·브라우저에 전달하지 않는다. 공개 가능한 키는 공개라는 사실만으로 쓰기 권한을 주는 수단이 아니다. [Supabase API 키 보안](https://supabase.com/docs/guides/getting-started/api-keys)
- 기계용 PostgreSQL 역할 또는 전용 서버 경계는 필요한 후보 테이블·조회·저장만 허용하고 회원·프로젝트·공개본·승인 상태·스키마 변경 권한을 차단한다. 실제 DB role/grant/RLS와 연결 계정으로 거절 시험을 수행한다.
- 비밀정보는 AWS Secrets Manager 또는 암호화한 Systems Manager Parameter Store 등을 검토하고 필요한 작업 역할에만 접근을 허용한다. 이미지·코드·PR·`.env.example`에 값을 넣지 않는다. [AWS 비밀정보 관리](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/specifying-sensitive-data.html)
- GitHub에서 AWS를 호출한다면 OIDC 기반 임시 자격증명을 우선 검토한다. 저장소·브랜치 또는 승인 환경을 신뢰 조건에 묶는다. OIDC는 AWS 접근 방식이며 Supabase 자격증명까지 없애 주는 기능이 아니다. [GitHub–AWS OIDC](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
- 생성 AI를 실행하는 환경과 DB 비밀정보를 읽는 환경을 분리한다. 같은 프로세스·공유 환경 변수·공유 볼륨에 넣고 프롬프트로만 읽지 말라고 지시하는 방식은 권한 분리가 아니다.

### 9.2 원문·파일·링크는 신뢰하지 않는 자료

- 원문 안의 ‘키를 보내라’, ‘다른 사이트에 접속하라’, ‘검증을 통과했다고 써라’ 같은 지시는 자료 내용일 뿐 실행 명령이 아니다.
- 반입 프로그램은 원고가 지정한 URL을 검증 없이 호출하지 않는다. 원문 조회는 별도 제한된 수집 경계에서 수행한다.
- 링크 조회를 구현할 때에는 허용 프로토콜·도메인·리다이렉트·다운로드 상한을 검사하고 로컬·사설망·클라우드 메타데이터 주소 접근을 차단한다. HTTPS 형식 검사만으로 안전한 외부 주소라고 보증하지 않는다.
- 본문은 승인된 렌더러와 입력 계약으로 표시한다. 원고의 HTML·스크립트·임의 임베드를 실행하지 않는다.

### 9.3 기록·권리·유출 대응

- 로그·오류·스크린샷에 토큰·비밀번호·접속 문자열·세션 쿠키·전체 환경 변수를 출력하지 않는다. 스캐너의 일치 문자열도 그대로 로그에 출력하지 않는다.
- 공개 저장소는 PR 초안도 공개될 수 있다. 저장소를 비공개로 해도 저작권·개인정보 문제가 면제되지는 않는다.
- 허가 없는 논문 전문·유료 PDF·환자 영상·연구 원자료·회원 DB·개인정보를 PR에 넣지 않는다. 원문 링크·필요 최소한의 적법한 인용·직접 쓴 설명·근거 위치를 우선한다.
- 키 유출이 의심되면 실행 중지 → 해당 자격증명 폐기·교체 → 로그·저장소·DB 영향 확인 → 필요한 이력 정리 → 제한된 시험 후 재개 순으로 대응한다. 파일 삭제나 Git revert만으로 유출이 해결됐다고 보지 않는다.

## 10. PR 승인과 관리자 게시 승인

| 단계 | 판단할 질문 | 기록 |
|---|---|---|
| PR 승인 | 이 묶음을 안전하게 미승인 후보로 반입해도 되는가? | 리뷰어, 최종 입력 버전, 검사·권리 주의사항 |
| DB 반입 | 승인된 파일이 중복·충돌·누락 없이 후보로 저장됐는가? | 입력 커밋·해시와 후보·판본 연결, 반입 결과 |
| 편집 승인 | 이 판본이 연구자에게 유용하고 근거·설명·권리를 충족하는가? | 기존 관리자 검수 항목, 승인자·판본·시각 |
| 게시 | 승인한 판본이 게시 전 점검을 통과해 실제 공개됐는가? | 공개본 ID·URL·판본·화면 확인 |

기존 글의 공개본은 새 수정본이 재검토·재승인되기 전까지 유지한다. 트렌드 전용 게시 검증이 연결되지 않았다면 차단을 유지한다. PR을 통해 들어온 글이라는 이유로 기존 서버 검증을 우회하지 않는다.

현재 공개 화면의 정적 원고와 DB 원고가 분리되어 있으므로 DB의 `published` 상태만으로 사이트 반영 완료라고 보고하지 않는다. 일반 공개 조회 연결과 승인 판본 일치 검증을 별도 완료해야 한다.

## 11. 단계별 도입과 종료 조건

| 단계 | 수행 범위 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| Phase 0 | 최신 소스·저장소·클라우드·권한·계약·예산 확인 | 4절 결정 항목과 담당자 확정. 비밀정보는 기록에 제외 |
| Phase 1 | 클라우드 수동 1회 조사·작성, DB 권한 없이 파일 생성 | 출처·근거 메모·전체 기사 검토, 필드·권리·누락 확인 |
| Phase 2 | 소량 콘텐츠 PR, 비밀키 없는 검사, 사람 리뷰 | 코드 혼입·민감정보·잘못된 형식 거절, 최종 입력 고정 |
| Phase 3 | 개발 DB 수동 미리 보기·반입 | 미승인 상태, 전체 원고 보존, 기존 데이터 보존, 재실행·실패 복구 시험 통과 |
| Phase 4 | AWS에서 머지 후 자동 반입, 클라우드 정기 수집 별도 연결 | 기계 권한·이벤트 중복·시간대·중지·알림·비용 상한 검증, 팀 운영 승인 |
| Phase 5 | 관리자 검토와 승인 게시 연결 검증 | 기존 편집·권리·키워드 검증 및 공개 사이트 판본 일치 확인 |

각 단계의 별도 실행 승인을 받고 진행한다. Phase 4까지 성공해도 자동 게시를 허용한 것은 아니다. Phase 5는 기존 관리자 승인 절차의 연결이며 무인 승인 기능을 새로 만드는 단계가 아니다.

초기 운영은 주간 소량 후보를 대상으로 하고 검토 시간·오류·중복·사용량을 측정한다. PR이 지나치게 많아지면 비공개 S3 임시 저장과 관리자 검토 방식 등을 재검토하되, 수집 AI와 DB 권한 분리는 유지한다. 이는 후속 대안이며 지금 구현할 필수 요소는 아니다.

## 13. 운영 인수인계 체크리스트

- [ ] 팀 검토로 PR 방식·저장소 공개 범위·콘텐츠 경로·대상 브랜치를 확정했다.
- [ ] 클라우드 AI에 DB·AWS 비밀정보가 없고, 생성 환경과 반입 환경을 분리했다.
- [ ] 서비스 코드 변경과 콘텐츠 PR을 분리하고 자동 머지·권한 우회를 차단했다.
- [ ] PR 검사와 비밀정보를 사용하는 반입 작업을 분리했다.
- [ ] 기계 인증·최소 DB 권한·개발/운영 분리의 실제 거절 시험을 통과했다.
- [ ] 전체 기사와 주장 메모 계약, 트렌드 전용 승인 검증의 연결 상태를 기록했다.
- [ ] 승인 입력 커밋·해시·후보 판본의 연결과 재실행 안전성을 확인했다.
- [ ] 예산·재시도·동시 실행·시간대·알림·중지·회수 절차를 확정했다.
- [ ] 기존 공개본·사람 수정본과 정적 사이트의 반영 경계를 확인했다.
- [ ] PR 리뷰어·편집 승인자·운영 담당자가 결과와 남은 위험을 인수했다.
