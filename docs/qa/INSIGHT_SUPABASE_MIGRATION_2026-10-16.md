# 인사이트 개발용 Supabase 적용·검증 기록

확인일: 2026-10-16. 기능 브랜치: `feature/insight-foundation`.

> 후속 관리자 설정: 같은 날 사용자가 직접 제공한 본인 Discord 사용자 ID를 로컬 관리자 목록에 등록하고 개발용 인사이트 API를 활성화했다. 아래 1~6은 DB 적용 당시 기록이며, 이후 변경과 실제 로그인 미검증 상태는 7절에 구분해 기록했다.

## 1. 실행 권한과 대상

사용자가 Supabase에 `labbridge-dev` 프로젝트를 직접 생성하고, 실제 DB 암호와 Session pooler 연결 주소를 로컬 `.env`에 저장했다. 암호화 옵션을 추가한 뒤 **“주소 수정했어. 다음 단계 진행해줘”**라고 하여 개발용 DB의 최초 테이블 생성을 승인했다.

프로젝트 화면의 식별자와 서버가 접속할 대상이 일치하는지 검사했다. 연결 문자열·비밀번호·JWT·Discord 키는 이 문서와 실행 결과에 기록하지 않았다. `.env`는 Git 제외 상태이며 수정하지 않았다.

적용 전 확인:

- 지정된 개발 프로젝트의 Session pooler, PostgreSQL 포트 5432, 기본 DB `postgres`가 맞았다.
- 저장된 연결 주소에 TLS 필수 옵션이 반영됐다. 암호화 연결로 읽기 전용 조회가 성공했다.
- `public`의 기존 테이블 수는 0이었다. 인사이트 schema와 변경 이력 테이블도 없어 충돌이 없었다.
- 접속 계정의 schema 생성 권한을 확인했다. 최초 신규 생성이므로 백업할 기존 인사이트 데이터가 없었다. 기존 Supabase 내부 schema는 변경하지 않았다.

## 2. 실제 적용한 변경

Alembic의 `20261016_01` migration을 개발 DB에 적용했다. 변경 파일은 [최초 migration](../../backend/migrations/versions/20261016_01_insight_foundation.py)이다.

| 위치 | 테이블 | 역할 |
|---|---|---|
| `insight_private` | `sources` | 출처와 DOI 중복 방지 |
| `insight_private` | `candidates` | 초안·검토·승인·공개 상태 |
| `insight_private` | `revisions` | 승인 대상인 본문·근거·평가의 판본 |
| `insight_private` | `review_events` | 검토·승인·게시 이력 |
| `insight_private` | `publications` | 공개용 스냅샷과 중복 게시 방지 |
| `public` | `insight_alembic_version` | 적용한 DB 구조 버전 번호 |

`schema`는 테이블을 구분해 담는 DB 안의 폴더와 비슷하다. `public`만 보고 인사이트 테이블이 없다고 판단하지 않는다. Supabase Table Editor의 schema 선택 기능에서 `insight_private`를 확인하면 된다. 이름의 private만으로 보호되는 것이 아니라 아래 권한 회수와 서버 검사가 보호 장치다.

## 3. 구조·권한·데이터 검증

- 실제 DB의 migration 버전: `20261016_01`.
- 인사이트 테이블 5개를 확인했다. SQLAlchemy 모델과 실제 DB 구조를 Alembic으로 비교한 결과 차이는 **0건**이었다.
- `anon`, `authenticated` 두 DB 역할 모두 `insight_private` schema 사용 권한이 없고, 5개 테이블의 조회·추가·수정·삭제 등 table 권한도 없었다.
- Supabase Data API의 실제 HTTP 호출 테스트는 수행하지 않았다. 이번에 직접 확인한 것은 PostgreSQL 역할 권한이다. 대시보드 설정과 DB 권한, 서버 권한 검사는 서로 다른 검증이다.
- 실제 인사이트 테이블의 데이터는 **모두 0건**이다. 가짜 사례를 실제 게시물로 넣지 않았다.

## 4. 실제 PostgreSQL 테스트

전체 backend 테스트를 개발 DB의 PostgreSQL 동시성 검사와 함께 실행했다.

**결과: 29 passed, 0 skipped, 1 warning.**

기존에 건너뛴 PostgreSQL 검사도 이번에는 실행했다. 테스트 프로세스에서만 전용 테스트 설정을 명시하고, 가상 사례는 별도의 `insight_test_<임의번호>` schema에 저장했다. 두 작업이 같은 게시 명령을 동시에 요청해도 결과 게시물은 1개였다. 종료 시 테스트가 만든 테이블·데이터·schema만 삭제했다. 실제 `insight_private` 게시물은 생성·수정·삭제하지 않았다.

이 결과는 같은 명령의 동시 요청 2개에 대한 검사다. 장시간 부하·장애 복구·여러 서버에서의 운영을 모두 보증하는 결과는 아니다. 테스트 도구의 httpx 사용 중단 예고 경고 1건은 기존과 동일하게 남아 있다.

다른 환경에서 재현할 때는 별도 테스트 DB를 명시한다. 평소 `pytest`는 실제 DB를 사용하지 않고 PostgreSQL 검사를 건너뛴다. DB 비밀번호가 들어간 명령을 터미널 기록이나 문서에 붙이지 않는다.

## 5. 실제 DB를 사용하는 API 조회

별도 TestClient 프로세스에서만 기능 설정을 잠시 활성화하고, 실제 개발 DB로 조회했다. 사용자가 실행 중인 서버 설정이나 `.env`는 바꾸지 않았다.

| 검사 | 결과 |
|---|---|
| 공개 인사이트 목록 | 200, 빈 목록, 총 0건 |
| 로그인 없이 관리자 후보 목록 접근 | 401 |
| 존재하지 않는 공개 글 상세 | 404 |
| 기능 설정을 비활성으로 바꾼 뒤 목록 조회 | 404 |
| 서버 health | 200 |

이는 실제 DB를 사용하는 백엔드 내부 요청 검사다. 브라우저·실제 Discord 로그인·프론트 연결을 포함한 전체 사용 흐름 테스트는 아니다.

## 6. 남겨 둔 상태와 다음 단계

- `.env`의 인사이트 기능 설정은 **비활성 상태를 유지**했다.
- 관리자 Discord 계정을 임의로 지정하지 않았다. 기존 회원 저장은 여전히 메모리 방식이다.
- 공개 사례·트렌드 화면은 아직 정적 데이터이며 새 API와 연결하지 않았다.
- 수집·LLM·예약 worker·알림·운영 배포는 실행하지 않았다.
- 운영 DB용 migration 권한과 최소 권한 앱 계정의 분리도 후속 과제다. 현재 연결 계정을 운영용 최소 권한 계정으로 검증한 것은 아니다.
- 다음은 실제 관리자 계정 확인과 기능 활성화 후 **실제 사례 한 편을 수동으로 검토하는 단계**다. 가상 테스트 자료를 운영 콘텐츠로 재사용하지 않는다.

문제가 생기면 먼저 기능을 끄고 원인을 조사한다. `downgrade`는 자료와 이력을 삭제하므로 쉽게 되돌리는 버튼처럼 사용하지 않는다. 운영 적용 전에는 별도 백업·최소 권한·노출 경로·전체 흐름 검증이 필요하다.

## 7. 후속: 본인 관리자 등록과 개발 기능 활성화

사용자가 본인 계정 등록을 요청하고 Discord에서 복사한 사용자 ID를 제공했다. Client ID와 사용자 ID는 별개임을 설명한 후 진행했다. 로컬 `.env`의 `INSIGHT_ADMIN_DISCORD_IDS`에 해당 사용자 ID 하나만 넣었고, `INSIGHTS_ENABLED=true`로 변경했다. 개인 ID는 이 공유 문서나 `.env.example`에 복사하지 않았다. DB 암호·Discord OAuth·JWT 설정은 변경하지 않았다.

확인한 것:

- 저장된 관리자 목록은 1명이며 사용자가 제공한 ID와 일치한다. 앱의 Client ID는 관리자 ID로 사용하지 않았다.
- 허용 목록 함수 검사에서 지정된 ID는 허용됐고 다른 ID와 앱 Client ID는 403으로 거절됐다. 이는 실제 Discord 신원 인증을 대신하는 검사가 아니다.
- 새 설정을 읽은 TestClient의 공개 목록 조회는 실제 개발 DB에서 200·총 0건, 로그인하지 않은 관리자 조회는 401이었다. 실제 게시물은 추가하지 않았다.
- 실행 중인 로컬 서버의 Discord 로그인 시작 주소가 올바른 앱 Client ID, identify 범위, state를 넣어 Discord로 이동시키는지 확인했다. 사용자의 로그인 승인이나 실제 계정 조회는 대신 수행하지 않았다.
- 기본 회귀 테스트는 28 passed, 1 skipped였다. 별도 DB 실행 설정을 켜지 않아 PostgreSQL 검사는 이번 회귀 실행에서 건너뛰었으며, 앞선 29개 전체 통과 기록은 유지한다.
- 로컬 프론트는 200으로 응답했지만 실행 중인 백엔드 인사이트 API는 아직 404였다. 환경 파일을 읽는 새 프로세스 검사는 통과했으므로 사용 중인 백엔드는 재시작 후 새 설정을 확인해야 한다. 사용자 실행 프로세스를 임의 종료하지 않았다.

남은 확인: 사용자가 백엔드를 재시작하고 같은 브라우저에서 Discord로 로그인한 뒤 `/api/v1/auth/me`의 `discord_id`가 등록한 본인 번호인지 확인한다. 그 세션으로 관리자 후보 목록이 200인지 확인하기 전까지 실제 관리자 로그인 전체 흐름을 완료로 표시하지 않는다. 다른 브라우저와 쿠키는 공유되지 않을 수 있고, 서버 재시작 후 회원 메모리가 비므로 재로그인이 필요하다.

개발 API 활성화는 자동 수집·예약 worker·무인 게시·운영 배포 활성화가 아니다. 글을 등록·승인·게시하는 동작은 아직 실행하지 않았다.
