# WHAT THE LAB · 통합검색 100개 연쇄 질문 및 설계 검토

검토 대상: `/search`, 전역 헤더, 공개 인사이트·전문가·자유게시판·FAQ 간 연결. 코드 설계 검토 100항목이며 **100건의 브라우저 실행 테스트를 완료했다는 의미는 아니다.**

## 아키텍처 및 공개 범위

| 검색 구역 | 원천 | 공개 조건 | 상세 이동 | 전체 결과 |
|---|---|---|---|---|
| 인사이트 | `listInsights('case'/'trend')` | 메인 화면 노출 원고(시안 포함) | `/cases/{slug}`·`/trends/{slug}` | 구역 내 펼치기 |
| 전문가 | `GET /api/v1/experts?q=` | 공개·활성 전문가만 | `/experts/{id}` | `/experts?q=` |
| 자유게시판 | `GET /api/v1/community/posts?scope=public&q=` | 공개·숨김 아님 | `/community/{id}` | `/community?q=` |
| FAQ | `FAQS`·`FAQ_CATEGORIES` | 공개 정적 질문 | `/faq#id` | `/faq?q=` |

UI 우선순위는 **인사이트 → 전문가 → 자유게시판 → FAQ**이며, 섹션 간 전역 점수 정렬은 수행하지 않는다. 전문가·게시판은 백엔드 검색어 계약 및 서버 권한 정책을 그대로 활용한다.

## 검색 범위·의도

1. **Q. 사용자는 네 영역을 왜 따로 찾지 않아야 할까?**  
   **판단:** 헤더와 /search의 한 검색어로 네 결과 섹션을 동시에 조회한다.

2. **Q. 결과를 관련도 순으로 모두 섞으면?**  
   **판단:** 인사이트→전문가→자유게시판→FAQ 섹션 순서를 고정한다.

3. **Q. 섹션 안에서는 무슨 순서로 보여 줄까?**  
   **판단:** 인사이트·FAQ는 제목 단어 일치 우선, 인사이트 동률은 최신순이다.

4. **Q. 검색어가 비어 있다면?**  
   **판단:** DB 조회를 보내지 않고 검색 안내와 네 카테고리만 보여준다.

5. **Q. 공백만 넣으면?**  
   **판단:** NFKC·공백 정규화로 공백 검색은 빈 상태로 처리한다.

6. **Q. 검색어가 매우 길면?**  
   **판단:** 전문가 API와 동일하게 50자로 제한한다.

7. **Q. 영문 대소문자가 다르면?**  
   **판단:** 정적 인사이트·FAQ는 소문자 정규화해 비교한다.

8. **Q. 전각 문자나 유니코드 변형을 입력하면?**  
   **판단:** NFKC 정규화하여 동일한 표기를 최대한 일치시킨다.

9. **Q. 여러 단어를 입력하면?**  
   **판단:** 정적 섹션은 전체 필드를 합쳐 모든 단어가 포함된 항목을 찾는다.

10. **Q. API와 정적 검색의 매칭 방식이 다르면?**  
   **판단:** 섹션별 출처를 명시하고 각각의 기존 검색 계약을 준수한다. 유사도 보장 주장은 하지 않는다.

## 인사이트 일관성

11. **Q. 인사이트의 원천은 어디인가?**  
   **판단:** cases·trends가 직접 사용하는 listInsights 인덱스를 공유한다.

12. **Q. 사례와 트렌드 중 무엇이 먼저인가?**  
   **판단:** 인사이트 한 섹션에 합치고 제목·메타데이터 관련도와 날짜로 정렬한다.

13. **Q. 검색에 보이는데 상세 페이지가 없는 글은?**  
   **판단:** listInsights에 등록된 slug만 사용해 동일한 상세 경로로 이동한다.

14. **Q. 운영 DB의 게시 미완료 콘텐츠도 보여 줄까?**  
   **판단:** 아니다. 현재 공개 메뉴에 실제 표시되는 정적 인덱스만 대상으로 한다.

15. **Q. 미리보기 시안 글이 섞일 가능성은?**  
   **판단:** 메인 인사이트 목록 자체가 시안 글을 포함하므로 이를 원천 그대로 반영한다.

16. **Q. 제목만 검색하면 요약을 놓치지 않을까?**  
   **판단:** 제목·요약·분야·주제·도메인·태그를 모두 검색한다.

17. **Q. 관련도 높은 오래된 글과 최신 무관 글의 순서는?**  
   **판단:** 제목 일치 점수를 먼저, 동점만 게시 날짜로 판단한다.

18. **Q. 목록이 길면 UI가 너무 길어지지 않을까?**  
   **판단:** 처음 4건만 보여 주고 전체 펼치기를 제공한다.

19. **Q. 카드의 시각적 일관성은?**  
   **판단:** 기존 InsightCard editorial 변형을 재사용한다.

20. **Q. 인사이트 클릭 이후 전문가 발견은?**  
   **판단:** 원본 상세 페이지의 기존 전문가 연결 안내를 그대로 보존한다.

## 전문가 검색 연동

21. **Q. 실제 회원이 검색되는가?**  
   **판단:** 기존 GET /experts API의 결과만 표시한다.

22. **Q. 전문가가 비공개로 바꿨다면?**  
   **판단:** 서버의 e.is_public=TRUE 조건에서 자동 제외된다.

23. **Q. 정지 계정은?**  
   **판단:** 서버의 active 사용자 조건으로 제외한다.

24. **Q. 로그인하지 않은 사용자도 찾을 수 있나?**  
   **판단:** 기존 공개 전문가 API를 그대로 사용한다.

25. **Q. 소속·자기소개는 어떤 데이터를 쓰나?**  
   **판단:** 공개 검색 응답의 nickname·affiliation·introduce만 노출한다.

26. **Q. 전문기술의 동의어는 어떻게 처리하나?**  
   **판단:** 기존 expert_search_store의 분류표 alias 검색을 이용한다.

27. **Q. 평가 점수로 순위를 왜 매기지 않나?**  
   **판단:** 통합검색에서 LAB TRUST를 임의 순위로 활용하지 않는다.

28. **Q. 협업 중 상태를 보고 즉시 가능으로 단정해도 될까?**  
   **판단:** '진행 중 협업 없음'으로만 표현하고 가능 보장 문구를 쓰지 않는다.

29. **Q. 전문가에게 바로 협업 요청을 보낼까?**  
   **판단:** 아니다. 상세 프로필로 이동해 기존 직접 요청 흐름을 이용한다.

30. **Q. 상세 필터와 페이징이 필요하면?**  
   **판단:** 검색어를 유지해 /experts?q=...로 이동하고 기존 필터·더 보기를 활용한다.

## 자유게시판·개인정보

31. **Q. 게시글은 어디서 검색하나?**  
   **판단:** 기존 /community/posts API의 q 검색을 호출한다.

32. **Q. 게시글 내용까지 찾을 수 있나?**  
   **판단:** 백엔드의 제목·본문 icontains 검색을 활용한다.

33. **Q. 비공개 문의가 검색되면?**  
   **판단:** scope=public로만 호출하고 서버 visibility=public 필터를 준수한다.

34. **Q. 신고로 숨긴 글은?**  
   **판단:** 서버 hidden=False 필터 및 클라이언트 공개 확인에서 제외한다.

35. **Q. 관리자라면 비공개 글도 나올까?**  
   **판단:** 통합검색은 관리자 여부와 관계없이 scope=public을 고정한다.

36. **Q. 비로그인 사용자에게 검색이 되나?**  
   **판단:** 기존 공개 scope는 게스트 조회를 허용한다.

37. **Q. 게시글이 수정되면 검색 반영은?**  
   **판단:** 조회 시점마다 API 최신 목록을 다시 읽는다.

38. **Q. 고정 게시글은 관련도 순을 왜 보장하지 않나?**  
   **판단:** 기존 게시판 API 정렬을 재사용하며 현재 최신/고정 정렬을 따른다.

39. **Q. 글 전체를 통합 화면에 노출할까?**  
   **판단:** 아니다. 공개 메타데이터·excerpt만 출력한다.

40. **Q. 게시글과 댓글에서 검색 대상은?**  
   **판단:** 현재 게시글 제목·본문만 대상으로 하며 댓글 내용 전체 검색은 범위 밖이다.

## FAQ 연결

41. **Q. FAQ는 DB API가 필요한가?**  
   **판단:** 아니다. 현재 faq.ts의 공개 정적 질문·답변·키워드를 재사용한다.

42. **Q. 질문이 짧고 답변에만 단어가 있다면?**  
   **판단:** 답변 본문까지 검색 인덱스에 포함한다.

43. **Q. 키워드가 본문에 없다면?**  
   **판단:** FAQ 키워드에도 검색을 적용한다.

44. **Q. 동일 표현이 여러 FAQ에 있다면?**  
   **판단:** 질문 제목 일치를 우선 정렬한다.

45. **Q. FAQ 결과를 누르면 무엇이 열리나?**  
   **판단:** /faq#id로 이동해 기존 hashchange/마운트 로직이 답변을 펼친다.

46. **Q. 원본 FAQ의 검색 결과와 달라지면?**  
   **판단:** 같은 질문·답변·키워드 조건을 재사용하고 링크에 q를 보존한다.

47. **Q. FAQ 카테고리 정보를 보여 주나?**  
   **판단:** 기존 FAQ_CATEGORIES 레이블로 결과를 설명한다.

48. **Q. FAQ가 한 건도 없다면?**  
   **판단:** 검색 범위가 0건임을 표시하고 FAQ 전체 탐색 링크를 제공한다.

49. **Q. FAQ가 매우 많다면?**  
   **판단:** 기본 4건·더 보기로 시각적 길이를 제어한다.

50. **Q. FAQ가 업데이트되면?**  
   **판단:** 공유 FAQS 원본이 갱신되면 통합검색에도 반영된다.

## 네비게이션·상태 보존

51. **Q. 전역 헤더 아이콘은 무엇을 열어야 하나?**  
   **판단:** 헤더 통합검색 입력을 열고 /search?q=...로 이동한다.

52. **Q. 헤더에서 이전 메뉴 검색 문구가 남아 있나?**  
   **판단:** 검색 placeholder와 aria-label을 통합검색으로 변경한다.

53. **Q. 검색 URL을 복사해도 같은 결과를 볼까?**  
   **판단:** q 쿼리 파라미터 기반이므로 새로고침과 공유가 가능하다.

54. **Q. 검색결과에서 본문을 누르면?**  
   **판단:** 인사이트는 /cases/{slug} 또는 /trends/{slug}로 이동한다.

55. **Q. 전문가를 누르면?**  
   **판단:** /experts/{user_id}의 기존 공개 프로필을 연다.

56. **Q. 자유게시판을 누르면?**  
   **판단:** /community/{id}의 원본 게시글로 이동한다.

57. **Q. FAQ를 누르면?**  
   **판단:** 고유 id 해시로 FAQ 답변을 연다.

58. **Q. 더 많은 전문가/글 결과를 보고 싶으면?**  
   **판단:** /experts?q=... 및 /community?q=...로 원 검색어를 전달한다.

59. **Q. 모바일에서 한 번에 네 구역을 찾으려면?**  
   **판단:** 두 열 바로가기와 각 구역 앵커로 점프한다.

60. **Q. 브라우저 뒤로가기를 누르면?**  
   **판단:** 검색이 GET URL 기반이므로 기존 방문 기록과 일치한다.

## 보안·입력 처리

61. **Q. 검색어에서 스크립트가 실행될까?**  
   **판단:** React JSX 텍스트 노드 렌더링으로 HTML 주입을 막는다.

62. **Q. %와 _를 입력하면 SQL 와일드카드가 될까?**  
   **판단:** 전문가 저장소는 LIKE 이스케이프, 게시판은 icontains(autoescape=True)를 사용한다.

63. **Q. 검색어를 쿼리로 만들 때 어떻게 인코딩하나?**  
   **판단:** URLSearchParams로 생성하여 특수문자와 공백을 인코딩한다.

64. **Q. 비공개 연구명은?**  
   **판단:** 연구관리 API를 호출하지 않으므로 검색에서 다루지 않는다.

65. **Q. 관리자 작성 중 인사이트 문서는?**  
   **판단:** 공개 인사이트 화면과 같은 정적 인덱스만 사용한다.

66. **Q. 게시판 운영자 메뉴 범위가 노출될까?**  
   **판단:** admin/inbox/moderation scope를 절대 요청하지 않는다.

67. **Q. 개인별 검색 이력을 저장할까?**  
   **판단:** 이번 기능에는 검색 이력 저장 기능을 도입하지 않는다.

68. **Q. 무단 로그인 쿠키 사용은?**  
   **판단:** 기존 requestApi의 쿠키 계약을 유지하되 공개 조회만 요청한다.

69. **Q. 외부 링크로 리다이렉트될 위험은?**  
   **판단:** 결과 href는 내부 slug/id 및 상수 경로로만 구성한다.

70. **Q. 검색 품질을 올리겠다며 개인정보를 인덱싱할까?**  
   **판단:** 현재 단계에서는 절대 추가하지 않는다.

## 로딩·오류·경계 상황

71. **Q. 한 데이터 소스만 지연되면?**  
   **판단:** 독립된 상태로 나머지 섹션은 표시를 계속한다.

72. **Q. 전문가 API만 실패하면?**  
   **판단:** 전문가 구역만 오류·재시도 버튼을 표시한다.

73. **Q. 게시판 API만 실패하면?**  
   **판단:** 게시판 구역만 오류·재시도 버튼을 표시한다.

74. **Q. 검색 중 화면은?**  
   **판단:** 골격 로딩 카드와 '검색 중'을 표시한다.

75. **Q. 네트워크 요청이 끝없이 멈추면?**  
   **판단:** 16초 타임아웃으로 로딩을 끝내고 다시 시도를 안내한다.

76. **Q. 검색어가 급히 바뀌면 이전 결과가 섞일까?**  
   **판단:** useEffect의 AbortController 정리와 query-key 리마운트로 방지한다.

77. **Q. 네 섹션이 모두 0건이면?**  
   **판단:** 상단 전체 결과 없음 안내와 섹션별 전체 보기 링크를 표시한다.

78. **Q. 한 API 실패 시 총합을 0으로 단정할까?**  
   **판단:** 전체 수 대신 일부 검색 실패 문구를 제공한다.

79. **Q. 빈 페이지에서 API가 실행되나?**  
   **판단:** query가 없으면 effect가 바로 종료한다.

80. **Q. 이전 요청의 응답이 늦게 도착하면?**  
   **판단:** abort 상태를 검사하고 새 query UI에 오래된 결과를 쓰지 않는다.

## UI·접근성·모바일

81. **Q. 첫 시선은 어디로 가야 하나?**  
   **판단:** 고대비 네이비 히어로와 하나의 검색창에 집중하도록 한다.

82. **Q. 결과 순서를 시각적으로 이해할까?**  
   **판단:** 01~04 번호와 각 영역의 섹션 제목을 사용한다.

83. **Q. 작은 모바일 화면에서 카드가 넘치면?**  
   **판단:** 모바일 1열, sm/md 이상에서 2~4열로 적응한다.

84. **Q. 키보드만으로 검색할 수 있나?**  
   **판단:** form GET 제출, 버튼·링크 기본 포커스 동작을 사용한다.

85. **Q. 검색 입력에 레이블이 있나?**  
   **판단:** sr-only label과 role=search를 둔다.

86. **Q. 결과 로딩을 스크린리더가 알 수 있나?**  
   **판단:** status와 aria-live를 사용한다.

87. **Q. 무채색 배경에서 링크를 알아볼까?**  
   **판단:** 카드 hover/링크 강조, 구획 경계, 명확한 텍스트 CTA를 둔다.

88. **Q. 오류를 색만으로 표시하나?**  
   **판단:** 텍스트 설명과 '다시 시도' 버튼을 함께 쓴다.

89. **Q. 긴 제목과 설명이 카드 높이를 무너뜨릴까?**  
   **판단:** line-clamp로 길이를 제어한다.

90. **Q. 다른 화면과 디자인이 단절되나?**  
   **판단:** 기존 PageContainer, InsightCard, 브랜드 계열 색과 반응형 규칙을 재사용한다.

## 운영·유지보수·확장

91. **Q. 새 인사이트가 등록되면?**  
   **판단:** 공개 case/trend 리스트 갱신으로 검색 인덱스에도 자동 반영한다.

92. **Q. 새 전문가가 공개되면?**  
   **판단:** 실시간 GET /experts 검색 결과에 나타난다.

93. **Q. 새 게시글이 공개되면?**  
   **판단:** 실시간 GET /community/posts 검색 결과에 나타난다.

94. **Q. FAQ가 추가되면?**  
   **판단:** 공유 FAQS 정의에서 자동 노출된다.

95. **Q. 검색 소스가 100만 건으로 늘어나면?**  
   **판단:** 현재는 경량 통합 UI이며 서버 검색·색인 서비스 통합이 후속 확장 과제다.

96. **Q. 모든 결과를 다운로드해 클라이언트에서 필터링하나?**  
   **판단:** 전문가·게시판은 서버 필터와 제한된 미리보기 페이지만 받는다.

97. **Q. 결과 수가 왜 서로 다를 수 있나?**  
   **판단:** 정적 콘텐츠 인덱스와 두 API의 검색 계약이 각각 다르므로 정상적으로 구분 표시한다.

98. **Q. 품질 회귀는 어떻게 발견하나?**  
   **판단:** 순서·정규화·링크·공개 범위·오류 상태에 대한 Node 회귀 테스트를 둔다.

99. **Q. 코드 수정 후 모든 시나리오를 실행했다고 말할 수 있나?**  
   **판단:** 아니다. 100개는 설계 질문·수동 검증 기준이며 자동 테스트/브라우저 검증과 구별한다.

100. **Q. 후속 개선 우선순위는?**  
   **판단:** 실사용 로그 기반의 검색 품질 개선, 다국어 동의어, 댓글 검색, 서버 통합 색인을 별도 검토한다.
