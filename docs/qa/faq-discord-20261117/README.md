### 안내의 진실성

근거: `frontend/src/lib/faq-discord.ts; frontend/src/components/community/faq-discord-guide.tsx`

**Q001. 이 화면은 실제 Discord 캡처인가?**  
아니다. 코드에 근거한 설명용 안내도로 명시했다.

**Q002. 그렇다면 실제 전송 성공으로 오해하지 않는가?**  
모든 장면 하단에 실제 캡처 아님·입력·전송되지 않음 표시를 둔다.

**Q003. 표시만으로 부족하면 어떻게 하는가?**  
재현한 조작 항목은 button 대신 span, 입력값은 dl로 표시한다.

**Q004. 실제 동작하는 버튼은 무엇인가?**  
단계 선택·이전·다음만 안내 상태를 바꾼다.

**Q005. 그 단계 전환이 실제 작업 상태를 바꾸는가?**  
컴포넌트는 로컬 index만 보관하며 API를 호출하지 않는다.

**Q006. 예시 사람이나 협업 번호가 실제처럼 보이지 않는가?**  
보낸 사람·받은 사람·협업-번호와 예제 데이터만 사용한다.

**Q007. 예시 화면이 Discord 외형을 보증하는가?**  
간소화한 제품 토큰 기반 카드이며 실제 앱 외형으로 주장하지 않는다.

**Q008. Discord 설정 메뉴가 바뀌면 무엇이 틀릴 수 있는가?**  
승인·DM 허용 외부 UI는 복제하지 않고 실제 앱 확인을 안내한다.

**Q009. 기존 사이트 캡처와 섞이면 오해하지 않는가?**  
상단 출처 범례와 각 안내도 캡션으로 두 유형을 구분한다.

**Q010. 그렇다면 외부 연동 검증까지 완료인가?**  
아니다. 인증된 Discord·Google·운영 DB 검증은 미실행으로 기록한다.

**Q013. 서버 참가 실패를 어디에서 다시 시도하는가?**  
프로필 설정의 알림 연결 링크를 안내한다.

**Q014. 재연결했다면 DM 수신도 보장되는가?**  
아니다. 수신 동의·DM 허용·차단 상태가 별도 조건이다.

**Q015. 연결됨 상태를 어떻게 검증하는가?**  
테스트 DM으로 실제 수신을 확인하도록 한다.

DM 허용·메시지 요청·스팸·봇 차단과 사이트 설정을 확인한다.

**Q020. 가입 완료 화면의 환영 DM 문구는 믿어도 되는가?**

**Q021. 새 협업 요청 알림은 어디로 가는가?**  
조건부 개인 DM과 사이트 알림이며 사이트에서 응답한다.

**Q022. 그 요청이 작업 요청과 같은가?**  
아니다. /요청은 확정·시작된 협업 안의 작업이다.

**Q023. 작업 알림도 개인 DM인가?**  
아니다. notify_task는 skipped DM과 채널 안내를 사용한다.

**Q024. 일정 알림은 어떤가?**  
일정도 사이트 알림·협업 채널 안내이며 DM을 중복 발송하지 않는다.

**Q025. DM 수신을 끄면 채널 멘션도 꺼지는가?**  
아니다. 별도 Discord 서버·채널 알림 설정을 설명한다.

**Q026. 멘션 메시지를 보냈다면 휴대폰 푸시는 보장되는가?**  
기기·Discord 설정과 외부 상태에 따라 달라 보장하지 않는다.

**Q027. 협업 채널은 정말 두 사람만 볼 수 있는가?**  
다른 일반 회원에게 비공개지만 서버 소유자·관리자의 접근은 예외다.

**Q028. 같은 이름 채널을 골라도 되는가?**  
번호·이름만 추측하지 말고 사이트가 제공하는 협업별 링크를 사용한다.

**Q029. 게시판 댓글도 Discord로 전송되는가?**  
아니다. 게시판 알림함과 협업 알림을 구분한다.

**Q030. DM이 오지 않으면 사이트 알림도 사라지는가?**  
아니다. 사이트 알림은 별도로 저장되므로 현재 기록을 확인한다.

**Q033. 연구회원만 작업을 보낼 수 있는가?**  
두 역할 모두 상대에게 보낼 수 있다.

각 작업의 requested_by·assignee 관계로 결정된다.

**Q035. 받은 사람에게 무슨 버튼이 보이는가?**  
완료·기한 얘기하기를 보여 주는 개인 패널이다.

**Q036. 보낸 사람은 무엇을 할 수 있는가?**

**Q039. 취소한 작업을 누가 되돌리는가?**  
취소한 사람, 즉 작업을 보낸 사람이 되돌린다.

**Q040. 그렇다면 프론트 버튼만 권한을 보장하는가?**  
서버 공통 함수도 권한 검사한다. 이번 PR은 권한 코드를 변경하지 않는다.

### 기한 협의와 완료

근거: `backend/app/discord_gateway.py; backend/app/routers/workspace_tasks.py; backend/app/task_text.py`

**Q041. 받은 사람이 기한을 직접 확정하는가?**  
아니다. 기한 얘기하기는 제안이다.

**Q042. 제안할 때 날짜가 필수인가?**  
날짜는 선택, 이유는 필수다.

**Q043. 날짜를 비우면 무엇을 뜻하는가?**  
현재 기한이 어렵다는 제안이며 기존 기한을 지우지 않는다.

**Q044. 그 제안에 보낸 사람은 어떻게 답하는가?**  
기한 변경 또는 지금 기한 유지로 답한다.

**Q045. 기한 변경 창은 무엇을 미리 채우는가?**  
제안된 날짜가 있으면 해당 날짜를 먼저 채운다.

**Q046. 새 기한을 비우면 어떻게 되는가?**  
기한 변경에서는 기한 없음이 된다. 다시 요청의 비움과 구분한다.

**Q047. 기한 유지를 선택하면 이유가 필수인가?**  
선택 사항이며 사이트에 협의 기록이 남는다.

**Q048. 완료를 실수로 누르면 누가 되돌리는가?**  
완료한 사람, 즉 받은 사람이 되돌린다.

**Q049. 보낸 사람이 결과 보완을 요구하면 새 작업인가?**  
완료된 같은 작업을 다시 진행 중으로 바꾸며 이유가 필수다.

**Q050. 원래 기한이 지났는데 다시 요청 날짜를 비워도 되는가?**  
유효한 새 기한이 필요하므로 기존 기한 유지 기본값의 예외를 안내한다.

### 작업 목록과 오류

근거: `backend/app/discord_gateway.py; backend/app/task_text.py; frontend/src/lib/faq.ts`

**Q051. 받은 작업 전체는 어느 명령으로 찾는가?**  
/받은요청은 해당 협업의 받은 진행 중 작업을 표시한다.

**Q052. 다시 요청된 작업은 어디에 있는가?**  
받은 목록의 내가 답할 것으로 구분된다.

**Q053. 기한 협의에 답할 작업은 어디에 있는가?**  
보낸 목록의 내가 답할 것으로 구분된다.

**Q054. 완료 작업도 모든 목록에 보이는가?**  
보낸 목록에 최근 완료 7일을 포함하며 받은 목록과 다르다.

**Q055. 최근 완료보다 오래된 기록은 사라지는가?**  
목록 표시 범위와 저장 기록은 다르며 사이트에서 확인한다.

**Q056. 본문과 선택 메뉴의 개수 제한이 같은가?**  
본문 15개, 드롭다운 25개로 달라 각각 안내한다.

**Q057. 제목 링크와 드롭다운은 같은가?**  
제목은 원래 채널 메시지, 선택 메뉴는 개인 관리 패널로 연결된다.

**Q058. 오래 열어 둔 개인 메뉴가 안 되면 어떻게 하는가?**  
10분 후 만료 가능성을 설명하고 명령·관리 버튼을 다시 실행한다.

**Q059. 상대가 먼저 처리한 뒤 버튼을 누르면 어떻게 하는가?**  
이미 처리·삭제된 상태를 다시 확인하고 반복 저장을 피하도록 안내한다.

**Q060. 명령어 자체가 없으면 사용자가 봇 설정을 바꿔야 하는가?**  
사이트에서 우회 처리하고 운영팀에 문의하도록 한다. 토큰·관리자 설정을 요구하지 않는다.

**Q070. 삭제를 잘못 눌렀을 때 작업처럼 되돌리기 버튼이 있는가?**

### 연동 데이터와 동기화

근거: `backend/app/task_sync.py; backend/app/schedule_notice.py; backend/app/google_sync.py; backend/app/notification_sender.py`

**Q071. Discord 작업은 사이트와 별도 데이터인가?**  
같은 create_task 등 저장 함수를 사용하며 사이트 작업 기록에 저장된다.

**Q072. 저장 후 채널 메시지는 어떻게 연결되는가?**  
discord_message_id를 저장해 원래 메시지를 이후 갱신한다.

**Q073. 웹에서 변경한 작업도 같은 메시지에 반영되는가?**  
task_sync가 기존 메시지를 갱신하고 필요한 상대 멘션을 보낸다.

**Q074. 메시지 갱신 실패는 작업 저장 실패인가?**  
별도 실패일 수 있다. 사이트 최신 기록부터 확인하도록 안내한다.

**Q075. Discord 일정도 같은 방식인가?**  
공통 일정 저장 함수를 쓰고 schedule_notice가 채널 메시지를 관리한다.

**Q076. 제목·메모만 고치면 새 멘션을 보내는가?**  
원래 메시지와 사이트 알림은 갱신하지만 새 멘션은 보내지 않는다.

**Q077. Google에 직접 수정한 내용이 원본으로 역반영되는가?**  
원본 수정은 사이트·Discord에서 하도록 안내하며 양방향 동기화를 약속하지 않는다.

**Q078. Google 연동이 없으면 작업·일정도 사용할 수 없는가?**  
별도 기능이다. 연결된 경우에만 Google 반영 과정을 설명한다.

**Q079. Google 반영은 즉시인가?**  
별도 처리이며 외부 서비스 상태에 따라 지연될 수 있다.

**Q080. 사이트 기록이 없다고 생각해 재등록하면 어떤가?**  
중복 가능성이 있어 사이트 저장 여부부터 확인하도록 안내한다.

### 협업 상태와 보관

근거: `backend/app/discord_waiting.py; backend/app/collab_waiting.py; backend/app/collab_ending.py; backend/app/review_store.py`

**Q081. 협업 확정 즉시 모든 기능이 열리는가?**  
미래 시작일이면 채널 대화만 가능하고 작업·일정 등록은 시작일부터다.

**Q082. 시작일은 누가 변경하는가?**  
사이트에서 요청하고 상대가 사이트·Discord에서 응답한다.

**Q083. 시작일 미루기는 무제한인가?**  
최대 14일, 수락된 변경은 협업당 한 번이다.

**Q084. 시작일이 바뀌면 종료일도 바뀌는가?**  
같은 일수만큼 옮겨 기간 길이를 유지한다.

**Q085. 기간 연장도 Discord 버튼으로 수락하는가?**  
아니다. 조기 완료와 함께 웹 링크로 응답한다.

**Q086. 기간 연장과 조기 완료 조건은 같은가?**  
연장은 한 번 최대 30일, 조기 완료는 열린 작업·남은 일정 등 차단 조건을 검사한다.

**Q087. 종료 뒤 채널은 바로 사라지는가?**  
안내 후 읽기 전용으로 잠그고 2일 후 삭제를 예약한다.

**Q088. 읽기 전용은 파일 다운로드도 금지하는가?**  
기존 파일 받기는 가능하며 새 메시지·파일·반응 등을 제한한다.

**Q089. 사이트 기록이 Discord 파일을 영구 백업하는가?**  
아니다. 삭제 예정일 전에 필요한 파일을 직접 받아야 한다.

**Q090. 중단·취소의 평가 정책은 같은가?**  
중단당한 사람만 평가하고 직접 중단한 사람·시작 전 취소는 제외한다. 전문가가 중단한 협업의 연구회원 평가는 공개 지수 대상일 수 있다.

### 탐색·접근성·검증

근거: `frontend/src/components/community/faq-page.tsx; frontend/tests/faq-discord.test.cjs; frontend/scripts/check-faq-discord-ui.cjs`

**Q091. 새 FAQ는 기존 검색에서 빠지지 않는가?**  
공통 FAQS에 추가해 FAQ 검색·통합검색이 같은 자료를 사용한다.

**Q092. 기존 직접 링크를 깨뜨리지 않는가?**  
기존 37개 id를 유지하고 관련 질문 링크의 대상 존재를 검사한다.

**Q093. 필터가 직접 링크의 질문을 숨기면 어떻게 되는가?**  
기존 해시 복구 경로를 유지하며 브라우저 검사에 충돌 시나리오를 추가했다.

**Q094. 안내 전환이 키보드로 가능한가?**  
네이티브 버튼·aria-pressed·aria-controls와 보이는 포커스를 제공한다.

**Q095. 단계 변경은 보조기기에 전달되는가?**  
현재 단계 이름·번호를 aria-live polite로 알린다. 실제 스크린리더 검증은 별도다.

**Q096. 모바일에서 이미지를 작게 축소하는가?**  
텍스트 기반 반응형 카드·줄바꿈으로 구성하고 44px 단계 버튼을 사용한다.

**Q097. 시각 검증 폭은 어떻게 정했는가?**  
1440·768·390과 추가 320px, 페이지 가로 넘침을 검사하도록 했다.

**Q098. 각 안내도의 모든 단계도 확인하는가?**  
15종 전체 장면의 제목·선택·마지막 버튼 상태를 브라우저 검사에 포함했다.

**Q099. 이 환경에서 실제 브라우저 검사는 성공했는가?**  
로컬 브라우저는 socket 권한 제한, Cloud Browser는 로컬 서버 접근 불가로 미실행이다. PR CI로 검사를 제공한다.

**Q100. 그렇다면 100문 검토는 100회 실서버 테스트인가?**  
아니다. 본 문서는 소스·설계 검토 100문이며 실행 테스트와 외부 미검증 범위를 분리한다.

## 실행 검증과 남은 범위

- 로컬: 프론트엔드 181개 테스트 통과, TypeScript·ESLint·프로덕션 빌드 통과. 린트는 기존 파일 경고 3개가 있으며 FAQ 변경 파일 오류·경고는 없다. PR CI 결과는 PR 본문을 기준으로 확인한다.
- `faq-discord.test.cjs`: 링크·명령어 검색·서버 정책 일치·렌더링 출처 표시·전송 UI 부재·기존 이미지 보존 검사.
- `check-faq-discord-ui.cjs`: 실제 Next.js FAQ의 4개 폭, 모든 안내 단계, 검색/분류/해시/통합검색, 페이지 오류·변경 요청 부재를 확인. API 응답은 브라우저 안에서 격리해 운영 서비스에 접근하지 않는다.
- GitHub CI는 읽기 권한만 사용하고 캡처를 artifact로 보관한다. 캡처는 FAQ의 **설명용 안내도를 렌더링한 화면**이며 실제 Discord 캡처가 아니다.
- 외부 Discord/Google 인증·봇 실전송·운영 DB·실제 스크린리더·기기 푸시는 미검증이다.
- 로컬 실행 제한으로 시각 검수는 CI 캡처 결과 확인 전까지 미검증으로 기록한다. 자동 통과와 수동 디자인 승인은 구분한다.
