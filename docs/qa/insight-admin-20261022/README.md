# 인사이트 전용 관리자 화면

확인일: 2026-10-22 / 사용자 요청: 본인 인사이트 관리자 권한 확인, 전용 관리자 화면, 우상단 계정 메뉴 진입점.

## 구현 범위와 운영 경계

- 화면: `http://localhost:3000/admin/insights`
- 로그인한 계정의 계정 아이콘 → **인사이트 관리자**. 모바일에서도 같은 아이콘을 사용합니다.
- 서버가 `users.is_admin` 또는 기존 `INSIGHT_ADMIN_DISCORD_IDS` 허용 목록을 판단합니다.
- 화면에서 메뉴를 숨기는 것만으로 보호하지 않습니다. 모든 조회·수정·승인·게시 API에서 기존 서버 인증·권한·Origin 검사를 유지합니다.
- 후보 목록·제목/DOI 검색·상태 필터·페이지 이동·상세 편집·근거 검사·본문 미리 보기·수정/검토/승인/게시 이력을 제공합니다.
- 일반 회원/프로젝트 관리자, 실제 수집 실행, AI 호출, 예약 worker, 정정·철회와 다인 검수는 구현하지 않았습니다.
- 기존 후보 일괄 입력 API와 로컬 미커밋 변경을 보존했습니다. 이번 화면은 일반 폼의 단건 입력이며 38건 fixture 반입 완료가 아닙니다.

## 본인 계정 확인 결과의 의미

사용자가 이전에 알려준 본인 Discord ID를 **현재 설정의 개발용 공통 Supabase에서 조회**했습니다.
서버 인사이트 관리자 허용 목록에는 포함되지만, 조회 시점 해당 ID의 회원 행은 없었습니다.
따라서 실제 해당 계정의 로그인·회원 생성 이후에 메뉴와 권한을 확인해야 합니다.
이 결과는 일반 관리자 `users.is_admin=true`를 부여했다는 뜻이 아닙니다.
실제 계정 생성·권한 변경·다른 계정 조회는 실행하지 않았습니다. 실제 ID·키·쿠키는 이 기록에 넣지 않습니다.

## 화면 사용 순서

1. 기존 방식으로 백엔드 8000, 프론트 3000을 실행하고 본인 Discord 계정으로 로그인합니다. API 주소와 화면은 같은 `localhost` 호스트를 사용합니다.
2. 우상단 계정 메뉴에서 `인사이트 관리자`를 엽니다. 일반 회원에게는 메뉴를 표시하지 않으며 직접 주소 접근 시에도 권한 안내 화면을 보입니다.
3. **새 후보 등록** 또는 목록의 후보를 선택합니다. 모바일에서는 선택 후 편집 영역으로 이동합니다.
4. **본문·근거**에 제목·주소·요약·분야·사례 유형과 주장 8개를 작성합니다. 각 주장에 원문 위치·근거 종류·검토 상태를 구분합니다.
5. **출처·평가**에서 실제 출처와 접근 수준, 서지 확인, 평가 7개와 이유, 운영 승인된 키워드 ID, 이미지 정책을 기록합니다. 기존 후보의 DOI/출처 URL은 변경하지 않습니다.
6. **초안 저장**합니다. 기존 후보를 수정할 때는 이유가 필요하며 새 판본을 생성하고 이전 승인을 무효화합니다. 초안에는 최소 주장 1개가 필요하고 승인 시 필수 주장 8개를 모두 검사합니다.
7. **승인·게시**에서 저장된 판본의 서버 근거 검사 결과와 게시용 미리 보기를 확인합니다. 차단 사유는 현재 첫 번째 문제이며 보완·저장 후 다시 확인합니다.
8. 작업 이유를 적고 **검토 요청**합니다. 검토 대기 상태에서 편집·권리를 직접 확인한 체크박스를 선택한 뒤 **승인하기**를 누릅니다.
9. 제목·주소·출처·판본·기술 ID·예약 시각을 보여 주는 확인창에서 **이 판본 승인**을 선택합니다. 승인만으로 게시하지 않습니다.
10. 승인된 판본과 게시 가능 시각을 다시 확인하고 별도 **게시하기 → 승인본 게시**를 실행합니다. 실제 공개 동작이므로 원고 검토 후 운영자가 직접 실행합니다.

예약 입력은 **한국 시간(Asia/Seoul)**으로 해석합니다. 날짜가 지나도 자동 게시되지 않습니다.
예약 시각 이후에는 새로고침하고 수동으로 게시합니다. 실제 예약 worker 활성화는 별도 단계입니다.

게시는 기존 **공개 API 스냅샷** 저장입니다. 현재 정적 `/cases`, `/trends` 목록·상세에
새 API 글을 함께 표시하는 연동은 아직 별도 단계이므로 이 화면에 그 한계를 표시했습니다.
게시 후 수정 저장은 차단하고 공개 API 결과 조회 링크를 제공합니다.

| `frontend/src/lib/api.ts` | 기존 쿠키 요청 방식 유지. 401/403 판별용 상태 코드와 읽을 수 있는 입력 오류 메시지 보존 |

409 수정 충돌에서는 로컬 입력을 덮어쓰지 않습니다. **서버 최신본 다시 조회**를 누를 때
미저장 변경을 버릴지 확인합니다. 창 닫기·새로고침과 화면 내 다른 페이지 링크 이동 시에도 확인을 요청합니다. 브라우저 자체의 뒤로/앞으로 버튼을 이용한 모든 SPA 이동을 차단하는 것은 이번 범위가 아닙니다.
쓰기 응답이 끊겼다면 결과를 먼저 재조회하고 자동으로 같은 작업을 재전송하지 않습니다.
게시 명령의 고유 번호는 같은 후보·승인 판본 기준으로 유지하며 서버의 고유 제약도 그대로 사용합니다.

## 실제 수행한 검증

- 백엔드 전체 **86 passed, 1 skipped**. 별도 PostgreSQL 동시성 설정이 없어 기존 전용 검사 1개는 생략했습니다.
- 새 관리자 API 검사 4개: 서버 권한, 공통 관리자/인사이트 허용 목록, 제목·DOI 검색과 문자 `%`/`_` 처리, 상태·페이지 집계, 읽기 전용 근거 검사 및 판본 갱신.
- 프론트 자동 검사 **26개 통과**: 신규 도우미 6개와 기존 인사이트 읽기/이미지 20개.
- TypeScript 검사 통과, 수정 프론트 ESLint 오류 0. 기존 헤더 `<img>` 사용 권고 경고 2개는 남았습니다.
- 격리된 소스 복사본에서 Next.js 프로덕션 빌드 성공. 실행 중인 개발 서버의 `.next`를 빌드로 덮어쓰지 않았습니다. 기존 가입 완료 화면의 미사용 변수 경고 1개도 별도 기존 항목입니다.
- 실제 Supabase에서는 새 목록 검색·집계 SQL만 **읽기 전용 트랜잭션**으로 검사했습니다. 조회한 후보 0건이며 후보·회원 데이터를 변경하지 않았습니다.

### 브라우저 흐름 검증

실제 Next.js 화면을 가상 계정·메모리 SQLite의 별도 FastAPI 서버에 연결했습니다.
모든 `/api/v1` 호출을 검증 서버로 전달했으며 실제 8000 Supabase에 테스트 쓰기를 보내지 않았습니다.

- 비로그인·일반 회원의 관리자 접근 차단과 메뉴 은닉
- 관리자 메뉴 이동, 계정 메뉴 Escape, 탭 키보드 이동
- 1440/768/390px 가로 넘침 없음
- 명시적 편집·권리 확인 후 검토 요청·승인 확인창
- 승인 후 수정 저장 시 승인 무효화
- 서버 게시 후 응답만 유실된 상황에서 상태 재조회, 게시 요청/게시 이력 각각 1개
- 실제 입력 폼으로 새 초안 저장, 미검토 승인 차단
- 수정 409 충돌 시 로컬 입력 보존, 명시적 최신본 재조회
- 모바일 확인창·포커스·Escape, 후보 선택 후 편집 영역 이동
- 미저장 상태에서 내부 페이지 링크 이동을 취소하면 입력과 현재 주소 유지

최종 자동 결과는 [verification.json](verification.json)에 기록합니다.
화면 캡처의 계정·논문·점수는 **검증용 가상 자료**이며 실제 콘텐츠가 아닙니다.

## 남은 검증과 하지 않은 일

- 사용자의 실제 Discord 로그인·가입 이후 메뉴와 관리자 API 접근은 사용자가 직접 확인해야 합니다. 테스트의 가상 로그인은 실제 Discord E2E가 아닙니다.
- 실제 Supabase 회원/후보 추가·수정·승인·게시·권한 변경을 하지 않았습니다.
- PostgreSQL 다중 관리자 동시 편집 E2E·실제 기기 터치·화면낭독기·200% 확대 검증은 미완료입니다.
- 기존 정적 공개 화면의 API 연결, 실제 수집/AI 처리, 트렌드 입력 정책, 예약 worker, 게시 후 정정/철회, 다인 검수는 완료하지 않았습니다.
- 커밋·push·PR·병합·배포는 이번 요청에 없어 실행하지 않았습니다.
