UG는 보기 쉽게 묶는 메뉴, CAP는 실제 전문가 기술, FIELD는 연구 분야야. 전문가 1명이 여러 기술을 가질 수 있고, 같은 기술을 여러 전문가가 가질 수 있어. 그래서 가운데 연결 테이블이 필요해.

02. ERD — 데이터베이스 관계도

그림 안의 상자는 DB 테이블, 상자 안의 항목은 컬럼이야. 선 위의 1:N은 “한 건이 여러 건과 연결된다”는 뜻이야. 가로로 스크롤하면 전체 관계를 볼 수 있어.

선은 FK가 PK를 참조하는 논리적 관계를 나타내며, 물리적인 테이블 배치는 이해를 위한 예시야. 회색 원본 JSON은 아직 운영 DB 마이그레이션에 반영되지 않았어.

중요: 현 데이터의 search-aliases.json은 axis + term_id로 CAP와 FIELD를 함께 참조하지만, DB에서는 CAP 검색어 테이블과 FIELD 검색어 테이블을 분리하는 방식을 추천해. 그래야 각각 FK로 존재 여부를 검사할 수 있어.

03. 어떤 테이블이 왜 필요한가?

이름만 보고 외우기보다 어떤 상황에서 쓰이는지 이해하면 쉬워.

테이블쉽게 말하면관계·구현 포인트
EXPERT_PROFILE전문가 한 명의 기본 프로필한 전문가가 많은 기술·분야를 가질 수 있음. 실제 서비스의 사용자/인증 테이블과 식별자 계약 필요
CAPABILITY전문가가 수행할 수 있는 세부 기술 사전CAP023 같은 고유 ID를 기준으로 저장
UI_GROUP검색창·가입 화면에서 보여주는 큰 선택 그룹UG와 CAP는 1:1이 아니라 연결 테이블을 통해 관리
UI_GROUP_CAPABILITY어떤 CAP가 어떤 UG에 포함되는지 기록복합 PK 또는 UNIQUE(group_id,capability_id)
EXPERT_CAPABILITY어떤 전문가가 어떤 기술을 보유하는지 기록전문가 ↔ 기술 N:M 연결, 자기 신고/검증 상태 구분
RESEARCH_FIELD연구 분야의 공통 사전FIELD002 등 분류표의 고유 ID 유지
EXPERT_RESEARCH_FIELD전문가의 연구 경험 분야·희망 협업 분야 기록relation_type으로 experience / collaboration 구분
CAPABILITY_CATEGORY / RESEARCH_FIELD_CATEGORY세부 기술·분야를 묶는 대분류CAP의 C01~C11, FIELD의 F01~F10 참조
CAPABILITY_SEARCH_TERM / FIELD_SEARCH_TERM같은 의미의 다른 검색어를 관리하는 사전EXACT·PREFERRED와 RELATED는 검색 정책에서 다르게 처리

04. 실제 Mock Data 한 명이 DB로 들어가면?

실제 생성된 샘플 전문가 MOCK_EXP_001를 예로 들어볼게. 이름·소속·경력은 모두 가상 데이터야.

현재 JSON에서
skillIds = ['CAP022', 'CAP023', 'CAP024']
experienceFieldIds = ['FIELD002', 'FIELD011']
collaborationFieldIds = ['FIELD002']
DB에 저장할 때
EXPERT_PROFILE 1행
EXPERT_CAPABILITY 3행
EXPERT_RESEARCH_FIELD 경험·협업 분야 각각 연결

기술 ID를 사람이 이해하는 이름으로 바꾸면

CAP ID기술명어떤 일?
CAP022이미지 분류이미지 전체에 범주·상태를 부여
CAP023객체 탐지·위치 추정이미지 내 대상의 존재와 위치를 탐지
CAP024이미지 분할·영역 추출픽셀·영역 단위로 이미지 대상을 분리

검색 시 내부 처리

연구자: “객체 탐지” 선택
→ CAP 마스터: object_detection → CAP023
→ EXPERT_CAPABILITY에서 capability_id = CAP023 검색
→ EXPERT_PROFILE에서 공개 가능한 전문가만 반환
→ 전문가 카드 및 상세 화면에 결과 표시
→ 협업 요청 버튼에는 해당 expert_id 전달

위 예시는 CAP023을 가진 전문가가 검색 후보가 된다는 뜻이야. 실제 의학 분야 경험, 협업 가능 여부, 요청 가능 여부는 별도의 조건으로 확인해야 해.

05. DB 담당자와 반드시 결정할 사항

주제권장 방향확정 필요
전문가 ID운영은 UUID 또는 기존 사용자 DB PK 사용. MOCK_EXP_001은 테스트용 표시값회원/전문가 식별자 연동
UG 가입 칩UG만 선택한 것을 CAP 전체 보유로 자동 확대하지 않기UG 선택을 선호 작업 그룹으로 별도 저장할지 결정
전문가 ↔ 기술교차 테이블의 FK + 복합 UNIQUE, self_declared/verified 상태 구분검증 주체와 검증 기준
전문가 ↔ 분야경험 분야와 희망 협업 분야를 relation_type으로 구분한 분야에 두 유형 동시 허용
분류표 상태pending_review는 운영 활성 데이터와 분리. 승인된 항목만 정식 필터 노출승인 담당자 및 배포일
검색 동의어CAP/FIELD 검색어를 분리해 정확 FK 보장. normalized term의 중복 정책 명시정규화·오타·관련어 검색 정책
삭제·변경사용 중인 CAP/FIELD는 하드 삭제보다 비활성·대체 ID 기록마이그레이션 방법
도구 정보PyTorch, SQL 등은 CAP 역량과 별개. 필요하면 EXPERT_TOOL 추가이번 MVP 포함 여부
요청 연계직접 협업 요청 시스템에 전문가 PK 전달, 권한 검사는 서버 담당요청 API 계약
이 자료는 설계 제안서야. 실제 팀의 데이터베이스 테이블과 완전히 같다는 의미가 아니고, 인증·사용자 테이블과의 FK는 DB 담당자가 현재 코드와 합의해서 확정해야 해.

예상 검증 시나리오

① 존재하지 않는 CAP ID를 전문가에게 연결하면 DB가 거부해야 함
② 전문가·기술 연결의 중복 저장 방지
③ UG 하나를 골라도 그 안의 CAP 전체 보유로 표시되지 않음
④ 경험 FIELD와 희망 FIELD를 별도 검색 가능
⑤ PENDING 항목을 정식 검색에서 제외하는 정책 검증
⑥ 전문가 비공개 상태에서는 API 결과에서 제외
